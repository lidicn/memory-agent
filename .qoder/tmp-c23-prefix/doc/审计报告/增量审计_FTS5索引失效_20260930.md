## 一、核心发现：FTS5 关键词索引每次重启后完全失效【新增·高】

### 位置

`src/memory_agent/store.py:681-720`（启动建表块）与 `:3956-3987`（检索入口）

### 现象

启动块**无条件**执行以下逻辑：

1. `DROP TRIGGER IF EXISTS` 三个触发器
2. `DROP TABLE IF EXISTS agent_memories_fts`
3. `CREATE VIRTUAL TABLE agent_memories_fts USING fts5(..., content=agent_memories, content_rowid=rowid, tokenize=trigram)`
4. 重建 ai/ad/au 三个触发器
5. 注释写着「触发器已保证增量同步；不再每次启动全量 rebuild」，随即打印「FTS5 关键词索引就绪」

**关键错误**：`content=agent_memories` 是 **external-content FTS5** —— 索引表本身**不存原始数据**，只存倒排索引。`DROP TABLE` + 重建后，新表**索引为空**。触发器（AFTER INSERT/UPDATE/DELETE）只对**此后发生**的写操作同步，**不会回填历史行**。

注释「触发器已保证增量同步」只对增量成立，忽略了「重建后历史索引归零」这一事实。正确做法是重建后执行一次 `INSERT INTO agent_memories_fts(agent_memories_fts) VALUES(rebuild)`。

### 实证复现（本地 SQLite 3.45.3，合成数据）

与 store.py 同构复刻（external-content FTS5 + 三触发器 + 无 rebuild）：

```
== 重启后（DROP+CREATE，无 rebuild）==
  MATCH study  -> []          ← 历史数据检索不到
  MATCH lamp   -> []
== 执行 rebuild 后 ==
  MATCH study  -> [(1,)]      ← 恢复
  MATCH lamp   -> [(1,)]
== 新增一行后（触发器自动同步）==
  MATCH kitchen -> [(3,)]     ← 仅新数据可检索
```

结论：**重启后历史行 MATCH 命中为空**，`rebuild` 后立即恢复；新增行因触发器仍可检索。

### 影响

1. **混合检索的第二路（关键词 FTS）在每次进程重启后对全部历史记忆失效** —— 只剩向量路。中文专名/子串检索（注释明确说 trigram 是为此选的）尤其依赖 FTS。
2. **日志误导**：启动打印「FTS5 关键词索引就绪」，实际是空索引，运维完全无感 —— 与项目反复强调要避免的「静默失效」一致。
3. `search_agent_memories_fts()`（store.py:3956）在 FTS 表存在但为空时不抛异常，只返回空列表，调用方「回退纯向量」，**丢结果且无告警**。

### 修复建议

在 `executescript(...)` 之后、`print(就绪)` 之前补一行：

```python
conn.execute("INSERT INTO agent_memories_fts(agent_memories_fts) VALUES('rebuild')")
```

首次建表时该语句为空操作；仅在已有数据时回填，代价 O(索引)。若担心大库耗时，可改为「仅当 FTS 行数为 0 且主表非空时 rebuild」。

### 与 20260918 报告 P1-1 的差异（重要）

该报告 P1-1 称「FTS 每次启动 DROP + rebuild」，据此把问题定性为**性能**（「O(全量) 的隐藏启动开销」「启动要几十秒」）。
**实际代码中不存在 `rebuild` 调用**，所以问题不是启动慢，而是**索引为空、检索失效**。方向相反，严重度更高（功能性失效 vs 性能开销）。建议以本报告为准。

## 二、次要发现：迁移块 except:pass 范围超出已登记项【部分新增】

`store.py` 启动迁移块共 **10 处** `except Exception: pass`（行号 621/628/636/643/726/731/736/741/746/1495）。

已登记项仅覆盖 `perception_events.event_id`（20260918 报告 P1-1，现已用 duplicate column 过滤修好）。**其余 9 处仍是无差别 pass**：

```python
try:
    conn.execute("ALTER TABLE agent_memories ADD COLUMN source TEXT NOT NULL DEFAULT 'ma'")
except Exception:
    pass  # 列已存在        ← 若失败原因是「表不存在/磁盘满/锁」，同样被吞
try:
    conn.execute("ALTER TABLE agent_memories ADD COLUMN member_id TEXT NOT NULL DEFAULT ''")
except Exception:
    pass  # 列已存在        ← 同上
```

**风险**：`member_id`（隐私归属维度）若因非预期原因补列失败，会静默留空 → 该维度隔离失效且无任何迹象。建议与已修好的 `event_id` 一致，改用 `if duplicate column not in str(exc).lower(): print(...)`。

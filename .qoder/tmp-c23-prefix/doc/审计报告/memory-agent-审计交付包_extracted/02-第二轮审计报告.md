# memory-agent 第二轮深度审计报告

> 审计对象：`https://github.com/lidicn/memory-agent`（main 分支）
> 审计方式：**沙箱实测** —— 真跑测试、真起运行时、真构造数据对比，非静态阅读
> 本轮焦点：在第一轮已确认缺陷之外，深挖**稳定性**与**功能性**的深层根因

---

## 一、本轮最重要的发现：一个根因，多条功能线同时失效

### 🔴 P0-5　绞杀者模式迁移断裂 —— 生产运行时绑定的是**未写完的**实现

这是本轮的核心结论。它解释了第一轮里那 34 项"算法输出为 0"中相当大的一部分，也解释了第一轮未能定位根因的模板分析失败。

**证据链：**

`src/memory_agent/insights/__init__.py` 的导入顺序：

```python
# 从旧版实现导入所有内容，保持向后兼容
from ..insights_legacy import *        # ← 先导入完整实现（3900+ 行）

# Phase 4: InsightService 切换到新框架
from .api import InsightService        # ← 再覆盖成新实现（未写完）
```

`runtime.py:35` 从 `.insights` 导入，`runtime.py:69` 实例化——**拿到的是被覆盖后的新实现**。

而 `insights/__init__.py` 自己的文档写明迁移状态：

```
Phase 3（进行中）：迁移 Service 层业务逻辑
Phase 4（计划中）：完全替换旧版
```

**即：生产引用已在 Phase 4 的位置，实现却还停在 Phase 3 的中途。**

**实测 —— 真实运行时（`AppRuntime`）绑定类与缺失方法：**

```
真实运行时 AppRuntime.insights 绑定类: memory_agent.insights.api.InsightService
生产运行时缺失的关键方法: 10/10
   ✗ _tags_of          ✗ _usage_one        ✗ _usage_by_attr
   ✗ _count_by_filter  ✗ _fallback_name    ✗ _iter_all_events
   ✗ _cache_get        ✗ _cache_put        ✗ _rhythm          ✗ _parse
```

全量比对：legacy 实现有而生产类缺失的私有方法共 **37 个**，其中 **10 个被生产代码真实调用**。

---

### 这个根因造成的功能性后果（逐条实测）

#### 后果 1：行为推断能力完全失效 —— 实测 10 项测试转绿

`activity_inference.py` 有 3 处调用 `insights._tags_of()`，该方法不存在 → `AttributeError` → 被 `except Exception: pass` 静默吞掉 → 返回空 `set()`。

于是所有事件 `tags=[]`，所有序列规则（书房工作 / 就寝 / 房间移动）首步 tag 永远匹配不上。

**A/B 对照实验（决定性证据）：**

| 场景 | 结果 |
|---|---|
| 现状（生产类无 `_tags_of`） | `persisted=0, candidates=0, detail=[]` |
| 注入 legacy 实现后 | `persisted=1`，正确识别 `study_work`（置信度 0.85）、`transit` 0.4 进候选 |

**影响面量化**：临时注入该单一方法后跑全量测试，**10 项测试明确转绿**：

```
test_activity_inference::test_sequence_match_in_order
test_activity_inference::test_mine_sequences
test_activity_inference::test_sleep_sequence_with_time_window
test_process_mining::test_mine_process_service_persists_anomalies_and_emits_rules
test_rule_recall::test_audit_counts_matched_and_near_miss
test_rule_recall::test_audit_skips_days_without_all_anchors
test_rule_recall::test_audit_emits_relaxed_candidate_rule
test_rule_recall::test_audit_mixed_reasons_uses_dominant
test_rule_recall::test_audit_reports_room_move_rule_recall
test_rule_recall::test_audit_distinguishes_missing_event_from_timing
```

#### 后果 2：模板分析（duration / count 两类指标）全部输出"计算失败"

`templates.py` 的 `_compute_entity()` 按 metric 分发到 `_usage_one` / `_usage_by_attr` / `_count_by_filter`——三个方法**全部不存在**。

**实测直接调用真实模板渲染路径：**

```
✗ 抛异常: AttributeError: 'InsightService' object has no attribute '_usage_one'
```

异常在 `templates.py:539` / `:561` 被 `except Exception` 兜底成：

```python
cur = {"error": f"计算失败: {exc}"}
```

**即：用户不会看到报错，只会看到模板里每个设备都显示"计算失败"。这正是最坏的一类 bug——功能完全不可用，但表面看起来在正常工作。**

#### 后果 3：实体中文名兜底失效

`templates.py:597` 调 `ins._fallback_name(label)`，方法缺失 → 实体解析失败时连名字兜底也没有，直接进"设备已失效或待重匹配"分支。

#### 后果 4：缓存层失效

`identity.py:157/163/180/182` 调 `_cache_get` / `_cache_put`，方法缺失 → 身份解析缓存完全不生效，每次全量重算。

---

### 为什么第一轮没抓到这个根因

第一轮我把它归入"34 项算法输出为空"的模糊集合，未能定位。本轮通过**逐事件追踪**（验证 `tags=[]`）→ **定位 `_tags_of`** → **发现异常被静默吞** → **比对 legacy 发现 37 个方法缺失** → **追溯 `__init__.py` 导入覆盖**，才挖到真正的根因。

这也印证了第一轮的核心判断：**62 处 `except: pass` 静默异常让缺陷无法自曝**，必须逐层追踪才能定位。

## 二、稳定性审计结论

本轮针对稳定性做了四项实测，**结论是：存储与 HTTP 层基本健康，未发现新的严重稳定性缺陷。**

| 审计项 | 方法 | 实测结果 |
|---|---|---|
| SQLite 并发安全 | 8 秒压测：2 写线程 42708 次 + 7 读线程 33623 次 | **0 异常**。机制正确：单连接 + `threading.RLock` + `check_same_thread=False` + `timeout=30.0` + WAL |
| 内存无界增长 | 扫描模块级可变容器 | 仅 2 处。`_PROMPT_CACHE` 有容量限制（`len>8` 即 clear），**非无界** |
| HTTP 超时覆盖 | 扫描 41 处 httpx 调用 | 33 处显式带 `timeout=`；`ha_client.py` 虽用无参 `httpx.Client()` 构造，但**每个请求都传了 timeout**（5/10/30/60s）；`llm_client.py` 用 `httpx.Timeout(self.timeout)` 配置。覆盖到位 |
| 慢调用占锁 | 检查锁内 IO | 未发现持 SQLite 锁做网络调用的写法 |

**遗留隐患（低优先级，未确认为实际故障）**：`llm_client.py:124` 的 `close()` 用 `loop.create_task(self._client.aclose())` 发后不管，未持有 task 引用，理论上存在被 GC 提前回收、连接未优雅关闭的风险。仅在关闭路径触发一次，影响面小。

## 三、两轮审计合并后的修复路线

**关键洞察：P0-5 与 P0-1 会在同一次启动中共存。** 实测启动日志同时打印：

```
加载实体目录失败: 'Config' object has no attribute 'db_query'   ← 第一轮 P0-1
AppRuntime.insights 缺失 10/10 关键方法                        ← 本轮 P0-5
```

两条缺陷都指向同一个真相：**`insights` 包的新实现尚未具备生产可用性，却已被切换为生产引用。**

| 优先级 | 缺陷 | 建议 |
|---|---|---|
| 🔴 **最高** | **P0-5 迁移断裂** | **立即把 `insights/__init__.py` 的 `InsightService` 切回 legacy 实现**，让 Phase 3 完成前生产跑在完整实现上。这是 1 行改动，可一次性恢复行为推断、模板分析、实体名兜底、缓存四条功能线 |
| 🔴 | P0-1 参数顺序 | `InsightService(self.store, self.config)` |
| 🔴 | P1-2 `_acp_kind` None 守卫 | `scope = scope or {}` |
| 🔴 | P1-1 monotonic 哨兵值 | 哨兵改 `float("-inf")` 或判 `None` |
| 🟠 | P0-2/3/4 MCP 工具问题 | 补实现 / 修权限判定 / 删重复定义 |
| 🟡 | 静默异常 | 62 处 `except: pass` 至少改为 `LOG.debug`，否则下个 P0 还会藏住 |
| 🟡 | CI 真正跑起来 | 补 `pytest.ini`（`asyncio_mode=auto`）+ 注入 `JWT_SECRET` |

**给维护者的一句话**：Phase 3 还没写完，但生产引用已经跳到了 Phase 4。把 `InsightService` 指回 legacy，是当前投入产出比最高的一个改动——一行代码，换回四条功能线。

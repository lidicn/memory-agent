## 决策事项 1：ADM token 合并方案

### 背景

当前 MA 存在多套 token 体系：
- `butler_token`：管家（DB）调用 MA 的窄接口
- `app_token`：应用级 token，用于 MCP/API
- `mcp_token`：MCP 工具调用鉴权
- `acp_token`：ACP（AutoFlow 协议）鉴权
- `arena_token`：AutoFlow 竞技场专用

DB→MA 当前有 4 路并发调用（MCP + vision REST + butler 窄接口 + app_token），鉴权面分散，维护成本高。

### 申请决策

是否批准将 `butler_token` 和 `app_token` 合并为统一的 `service_token`，保留 scope 区分（butler / app / mcp / acp / arena）？

### 方案细节

- **合并范围**：butler_token + app_token → service_token
- **过渡期**：旧 token 继续有效 30 天，期间双轨运行
- **scope 设计**：service_token 带 scope 字段，区分调用方权限
- **MA 侧改动**：统一 token 签发/校验逻辑，兼容旧 token
- **DB 侧改动**：DB 切换到新 token，旧 token 设过期时间

### 影响

- 优点：鉴权面收口，维护成本降低，ADM 联动更清晰
- 风险：过渡期需确保 DB 不中断；旧 token 废弃需 DB 配合
- 工时：MA 侧 2-3 小时，DB 侧待定

## 决策事项 2：vMA-1.3 多模态统一 PoC 是否启动

### 背景

vMA-1.3.0 多模态记忆统一是路线图上下一个大版本，但挂了 PoC 门。当前数据模型分散在：
- `events` 表（HA 事件）
- `behavior_events` 表（行为事件 + 场景图）
- `agent_memories` 表（agent 记忆）
- `voice_answer_cache` 表（语音缓存）
- `learning_feedback` 表（学习信号）

多模态统一需要设计一个统一的数据模型，可能涉及建新库或在现有库上加视图。

### 申请决策

是否批准启动 vMA-1.3 多模态统一的 PoC？PoC 内容：
1. 设计统一数据模型（事件 / 行为 / 记忆 / 语音的统一抽象）
2. 副本库全量迁移演练（不碰生产库）
3. 评估性能影响和迁移风险

### 影响

- 优点：数据模型统一，为 vMA-2.0 知识图谱打基础
- 风险：PoC 可能发现现有数据模型难以统一，需要大改
- 工时：PoC 2-3 天，正式开发 1-2 周（PoC 通过后）

## 决策事项 3：越权清理后 DB 收件箱模式的具体协议

### 背景

DCD 2026-09-29 裁定：MA 直推 `butler/trigger/gu_anheng_alert` 违反"各仓只推自己域名主题"。修订方案：
- 方案 A：改为投递 DB 的公共收件箱 `butler/inbox/notify`（DB 显式开放、ACL+schema+限流兜底）
- 方案 B：发布 MA 自己的 `ma/insights` 事件（不 retained，DB 订阅）

### 申请决策

选择方案 A 还是方案 B？或者两者并行（MA 推 ma/insights，DB 按需转发到收件箱）？

### 影响

- 方案 A：DB 侧需要开放收件箱并定义 schema，MA 侧改动小
- 方案 B：MA 侧改动小（改主题名），DB 侧需要订阅新主题
- 建议：方案 B（ma/insights），因为 MA 只推自己域名主题是基本原则，DB 订阅是被动消费

## 决策事项 4：test_openshs_bench 修复方向

### 背景

`infer_activities` 之前从"规则匹配"重构为"时间段启发式标记"，返回"夜间活动"/"晨间活动"等通用标签。但 `benchmarks/openshs_bench.py` 的 ground truth 仍是旧活动名（sleep/cook/study），导致 F1=0.0。

### 申请决策

修复方向选择：
- **方案 A**：更新 benchmark ground truth，适配新的通用标签（"夜间活动"等）
- **方案 B**：在 infer_activities 中加兼容层，同时输出旧标签（sleep/cook/study）和新标签
- **方案 C**：回退 infer_activities 到规则匹配（不建议，重构是有原因的）

### 影响

- 方案 A：benchmark 改动小，但 benchmark 的语义变了（不再测具体活动识别，而是测时间段标记）
- 方案 B：infer_activities 复杂度增加，但 benchmark 语义不变
- 建议：方案 A，因为新逻辑是有意设计的，benchmark 应该适配新逻辑

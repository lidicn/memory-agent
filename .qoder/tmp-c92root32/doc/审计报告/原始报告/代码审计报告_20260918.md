## 一、P0：鉴权与协议面

### [P0-1] ACP 主路径 `NameError`：initialize/prompt 直接崩，且崩溃被 fail-open 掩盖

- **位置**：`src/memory_agent/acp_server.py:302`（`async def acp_handle(rt, payload)`）与 `:325`、`:397`（内部调用 `_acp_kind(rt, scope)`）；`api/acp_routes.py:142-168`
- **失败场景**：ACP 客户端连上即 500；`_acp_kind` 的 `except Exception: pass`（`:121-131`）在另一条路径上把异常吞成「按 `acp` 处理」，于是同一个作用域判定既可能崩、可能静默放宽权限。**权限判定的默认值来自异常处理分支**，这是本项目最危险的一处设计选择。
- **修复方向**：把 `_acp_kind` 改为同步纯函数并显式定义未知作用域 → 拒绝；`acp_handle` 签名与之对齐；补一条 ACP 全链路 smoke 测试（当前无 CI，见 §五）。

### [P0-2] `dbg_` 调试令牌绕过所有校验返回 `{"debug": True}`

- **位置**：`src/memory_agent/api/app.py:248`、`:258-259`
- **失败场景**：中间件对 `dbg_` 前缀 token 直接放行，且没有 `_debug_allowed()` 之类的环境/来源限制 → 任何拿到（或猜到）该前缀的主体即获得全接口访问，并绕开 6 类 token（user/butler/arena/app/debug/device）的作用域设计。
- **修复方向**：调试令牌必须显式启用（配置 + 仅 loopback/内网段）、生产模式下启动即拒绝创建；把 debug 从「跳过检查」改成「一种有 scope 的主体」。

### [P0-3] `/api/members/` 前缀全方法放行 + `update_member(member_id, **body)` → 成员档案任意写

- **位置**：`src/memory_agent/api/app.py:190`（前缀白名单不区分方法）；`api/member_routes.py:73-88`
- **失败场景**：白名单让未认证请求命中成员更新；`**body` 展开使调用方能塞入任意列（含 `face_feature`、`role`、`trusted`）→ **改谁的档案、改谁的人脸特征**都可被外部驱动。
- **修复方向**：前缀白名单必须带方法且只读；handler 改显式字段白名单（PATCH 语义），敏感列需二次认证。

### [P0-4] 令牌比较使用字符串相等 + 资源面绕过统一入口

- **位置**：`src/memory_agent/api/face_routes.py:26`、`src/memory_agent/api/vision_routes.py:24-29`（`auth == f"Bearer {token}"`）；`mcp_server.py:2322-2331` 与 `:846-854`（resources 不经 `_tracked_call_tool`）
- **失败场景**：① 非常量时间比较（时序侧信道，虽在本场景权重低，但不统一）；② resources 走另一条代码路径 → 审计日志、scope 检查、限流全都跳过，**读操作不留痕**。
- **修复方向**：`hmac.compare_digest` 统一封装；resources 与 tools 共用同一个带审计的入口。

### [P0-5] `session_id` 由调用方自报即获得特权记忆访问

- **位置**：`src/memory_agent/mcp_server.py:1643-1671`；`agent_memory.py:386`（`privileged = session_id in config.privileged_sessions`）
- **失败场景**：任意 MCP 客户端在参数里填一个特权 session id（session id 可从正常响应里观察到）即可读/写其它 agent 的记忆命名空间——**跨主体隔离仅取决于一个自报字符串**。
- **修复方向**：`session_id` 必须由 token 反查（`subject → session`），入参只允许在已授权集合内做收窄。

### [P0-6] `mcp_scopes` 未知工具默认可读 → 新增工具自动获得放行

- **位置**：`src/memory_agent/mcp_scopes.py:59-65`（未知工具 → `READ` → allowed）
- **证据（配套）**：`WRITE_TOOLS` 缺 17 个已注册工具；`query_behavior_events` 是**注册了但表里不存在的幽灵工具名**。
- **失败场景**：新加写工具若忘了登记 `WRITE_TOOLS`，即被当作读工具对所有 scope 开放。**分类表用「例外清单」而非「显式声明」**，安全属性随代码演进单调退化。
- **修复方向**：启动时断言「所有已注册工具 ∈ (READ_TOOLS ∪ WRITE_TOOLS)」，缺失即拒绝启动；未知工具 → deny。

### [P0-7] `/api/config/test` 用已存密码去连调用方指定的主机（SSRF + 凭据外泄）

- **位置**：`src/memory_agent/api/config_routes.py:370`
- **失败场景**：请求体给 host/port，后端回退使用库中保存的 `ha_db_password` 发起连接 → 攻击者把它指向自己的 MySQL 即可**收割密码**（协议层还可能留下握手凭据），同时获得内网端口探测原语。
- **修复方向**：测试端点只接受「本次请求显式提供的完整凭据」，禁止回退已存密钥；host 走白名单 + 私网策略；连接加超时与审计。

### [P0-8] 后端密钥按「位置」而非「身份」回填 → 跨厂商密钥错发

- **位置**：`src/memory_agent/api/config_routes.py:227`、`:96-129`
- **失败场景**：调整配置项顺序即把 A 厂商的 key 发给 B 厂商 endpoint（密钥外泄给第三方，且报错表现为「鉴权失败」极难归因）。
- **修复方向**：以 `(provider, kind)` 为主键存储与读取；启动时校验条数与 id 集合一致。

### [P0-9] ACP 会话按客户端提供的 `sessionId` 建键，无属主绑定

- **位置**：`src/memory_agent/acp_server.py:330-366`
- **失败场景**：猜测/复用他人 sessionId 即可续接他人会话（拿到上下文与流式结果）。
- **修复方向**：会话记录 `owner_subject`，每次操作断言匹配；新会话 id 用 CSPRNG。

### [P0-10] ✅ 部署面：仓库根以 rw 挂进 root 容器 + chroma 端口无认证对外发布

- **位置**：`docker-compose.yml:42-46`（`./src:/app/src`、`./data:/data`、`.:/repo:rw`，注释说明「在线更新」用途）、`:78-79`（chroma `8082:8000`）、`Dockerfile`（无 `USER`，且安装了 `git`）
- **配套**：`Caddyfile:4,9-31` 在 `:80/:443` 全接口监听且 `auto_https off`，无鉴权、无 rate limit、无安全响应头；无 `.dockerignore`；`deploy_nas.sh:11` 先 `git checkout -f` 再做任何校验，且全程无数据备份。
- **失败场景**：① 容器内任意代码执行 = 直接改写宿主仓库源码，下次 `deploy_nas.sh` 的 `git checkout -f` 会把它当「远端代码」再拉一遍或反过来**抹掉未提交的运维改动**（无备份）；② chroma 是明文向量库端口，`8082` 发布到宿主即让任何内网主机可读全部记忆向量、绕过 `mirror_dirty`/信任度/撤销机制；③ `auto_https off` + 无鉴权 → 记忆内容与令牌在内网明文传输；④ 无 `.dockerignore` → `data/`、`.env`、测试脚本（含摄像头口令，见 §五）全部进镜像层。
- **修复方向**：去掉 `.:/repo:rw`（在线更新改走镜像重建或只读挂载 + 显式发布流程）；`USER 10001:10001`；chroma 移除 `ports`（只走 compose 网络）；Caddy 开 TLS 并加 basic auth/IP allowlist + `X-Frame-Options` 等头；补 `.dockerignore`；`deploy_nas.sh` 先 `pgrep`/校验工作树干净 + 备份 `data/` 再切分支。

## 二、P1：存储层正确性

### [P1-1] 迁移用 `ALTER TABLE ... ADD COLUMN x TEXT UNIQUE` + `except Exception: pass` → 该列永不存在

- **位置**：`src/memory_agent/store.py:408`（`perception_events.event_id TEXT UNIQUE`）；同类模式 `:416`（FTS 每次启动 DROP + rebuild）
- **证据**：SQLite **不支持** 在 `ADD COLUMN` 上加 `UNIQUE`，这条语句恒失败；外层 `except Exception: pass` 让失败静默。FTS 重建只在彻底失败时才 `print`。
- **失败场景**：`event_id` 列在现有部署里根本不存在，任何依赖它的查询/去重落到 `except` 分支 → 感知事件重复入库、幂等失效；每次启动重建 FTS 是 O(全量) 的隐藏启动开销，数据量上来后启动要几十秒且期间检索为空。
- **修复方向**：`SCHEMA_VERSION`（见 P1-3）驱动的显式迁移表；`ADD COLUMN` 不带约束、约束用随后 `CREATE UNIQUE INDEX`；迁移失败必须让进程拒绝启动；FTS 只在版本变化时重建。

### [P1-2] 主写路径与镜像/缓存路径不一致，导致三份副本长期分叉

- **位置**：`store.py:3458-3469`（`expire_overdue_agent_memories` 的 UPDATE **不写** `mirror_dirty`）、`:3471-3481`（`record_agent_feedback` 在 `self._lock` **之外**读）、`:2452`（`SELECT * FROM members` 带着 `face_feature`，该列在 `:473` 才加入）
- **证据**：记忆同时存于 SQLite / FTS5 / chroma，靠 `mirror_dirty` outbox 收敛；但过期 UPDATE 不标脏，且反馈写入无锁读。
- **失败场景**：① 过期记忆在镜像里仍「活着」→ 被检索并回填给 agent（撤销失效，用户要求忘记无效）；② 反馈并发丢更新，信任度漂移；③ `SELECT *` 使 `face_feature`（人脸向量）被顺带读出并流向不知情的调用方（配合 §三 P0-1 的 `list_members`）。
- **修复方向**：任何改记忆状态的写都走同一个 `_mark_dirty()` 辅助函数（用测试断言「所有 UPDATE memories 的语句必须紧邻标脏」）；`record_agent_feedback` 进锁或用 `UPDATE ... WHERE` 单语句完成；`SELECT` 一律显式列名。

### [P1-3] `_lock` 只保护连接创建，不保护 execute/commit；共享连接 `check_same_thread=False`

- **位置**：`store.py:9`（docstring 明确声称「单连接 + RLock」契约）与 15+ 个违背它的方法；`:1968-1998`（幂等键 check-then-write 无锁）
- **失败场景**：跨线程共享连接下并发 execute 抛 `sqlite3.ProgrammingError`/`InterfaceError`，或事务互相踩；幂等键的 check-then-write 竞态 → **重复写入同一条记忆**（agent 重试时最常见）。`SCHEMA_VERSION = 1` 只写不读，说明迁移体系从未启用。
- **修复方向**：要么每线程一连接（`threading.local`）+ WAL + `busy_timeout`，要么把 `_lock` 包到所有 execute/commit；幂等改 `INSERT ... ON CONFLICT DO NOTHING` 由 DB 保证；docstring 与实现要么对齐要么删掉。

### [P1-4] `persons` 以字符串数组写入，但所有读取方要求 dict

- **位置**：`store.py:1459`、`:2039`、`:2100`、`:2156`（写侧）；读侧统一 `if not isinstance(p, dict): continue`
- **失败场景**：写进去的在场人员被读侧**整批静默丢弃** → 「谁在家」类查询返回空，下游（管家在场判断、洞察）得到「家中无人」的错误事实。
- **修复方向**：单一 `_serialize_persons/_deserialize_persons`；读侧遇到非 dict 应记 ERROR（数据格式坏了要被看见），不是 `continue`。

### [P1-5] `LIKE '%member:{name}%'` 未转义通配符 → 跨成员检索

- **位置**：`store.py:2202`、`:3498`
- **失败场景**：`name` 含 `%` 或 `_` 时匹配范围扩大（`%` 即「全部」）→ **返回其它成员的记忆/事件**，PII 越权；agent 侧无法察觉，因为结果看起来「相关」。
- **修复方向**：改结构化列（`member_id` 真列 + 索引）或至少 `LIKE ? ESCAPE '\'` + 转义；补一条跨成员隔离测试。

### [P1-6] 分页与截断语义错误

- **位置**：`store.py:2768`、`:2780`（`query_events` 默认 `limit=500`、超出静默 clamp 到 5000；`ORDER BY ts ASC LIMIT ? OFFSET ?` 且 ts 精度为秒）；`:1495`（成员过滤在 SQL LIMIT **之后**用 Python 做）
- **失败场景**：① 秒级 ts 无 tiebreaker → 分页边界事件重复或漏；② 先 LIMIT 再过滤 → 「某成员的第 2 页」经常是空页，调用方误判该成员无数据；③ clamp 不报错 → 上层统计基于被截断的数据。
- **修复方向**：`ORDER BY ts, rowid`；过滤条件进 SQL；截断时返回 `truncated: true` 字段。

### [P1-7] 热路径查询无索引 + 审计写同步阻塞事件循环

- **位置**：`store.py:2019`、`:2076`（在场热查询，只有 `idx_be_day_room`（`:245`）可用）；`mcp_server.py:662-677`、`:896-898`（每个工具调用后 `INSERT audit` + `commit` 直接在事件循环上）
- **失败场景**：数据量增长后在场查询变全表扫描；同步 commit 阻塞 loop → 所有 MCP/SSE/ACP 客户端同时卡顿（MCP 服务是单进程 asyncio）。
- **修复方向**：为 `(server_ts)` 与 `(room, server_ts)` 建索引；审计写改队列 + 批量异步落库（`asyncio.to_thread`）。

## 三、P1：MCP 服务面与工具契约

### [P1-8] `list_members` 返回原始行，含 `face_feature` 向量

- **位置**：`mcp_server.py:1284-1289`；对照 `:2253`（resources 路径会 `pop("face_feature")`）
- **失败场景**：**生物特征向量随工具结果流出**（agent 上下文、日志、甚至转述给用户）。生物识别数据出境是合规硬风险，且向量可被离线反演匹配。
- **修复方向**：出参统一过 `member_public_view()`，白名单字段；加一条「任何工具结果不得含 `face_feature`」的断言测试。

### [P1-9] `get_behavior_insights` 调用签名不匹配，被 `except: pass` 吞掉

- **位置**：`mcp_server.py:1376`：`get_behavior_insights(days, ", ".join(...))`；定义 `def get_behavior_insights(self, compare_days: int = 7)`
- **失败场景**：`TypeError` → 静默 → 该工具**永远返回空/降级结果**，但 `ok` 字段仍为真（假成功）。
- **修复方向**：对齐签名；`except Exception` 收窄到具体异常并记 ERROR。

### [P1-10] 幂等键命名空间不足 + ContextVar 绑错任务 + 全文件零超时

- **位置**：`mcp_server.py:864-890`（键为 `f"{name}:{idem_key}"`，不含主体/会话）、`:846-854`、`:2322-2331`（SSE 的 ContextVar 绑在 POST 任务而非 session 任务）、`:1941,1996,2023,2033,2042,2094,2169,2195`（8 个同步 `def` 工具）、全文件无 `asyncio.wait_for`
- **失败场景**：① 不同 agent 用同名幂等键互相吞写；② SSE 流里审计/归属信息错位（写到别人的账上）；③ 同步工具在事件循环里执行 → 一次慢查询冻结整个服务；④ 无超时 → 单个 chroma/HTTP 卡住即挂死整条 tool 调用链。
- **修复方向**：键加 `subject + session + name`；ContextVar 在 session 任务内 set；同步工具走 `to_thread` 或改 async；所有外部调用 `wait_for`。

### [P1-11] 工具 schema 与 handler 语义不一致（多处）

- **位置**：`src/memory_agent/tool_schema.py:397-408`（`query_events` 声明逗号字符串 / `limit 500` / `days 0`，handler 实为 list / 200 / `days or 7`）、`:278`（`activities: string`，handler 要 `list`）、`:896-903`（`bypass_limits`）
- **证据**：`insights.py:3241` 的 `set("cooking,sleeping")` 把字符串当集合，字符级拆分 → 结果恒为空并被缓存；`vision_service.py:1106-1196` 只把 `bypass_limits` 回显，不产生任何行为。
- **失败场景**：LLM 严格按 schema 传参（字符串、`days: 0`）→ 语义与 handler 相反；空结果被缓存后长期返回错误洞察；`bypass_limits` 让调用方以为已提高限额（装饰性参数）。
- **修复方向**：schema 由 handler 签名自动生成（或加一致性测试：schema 每个字段必须被 handler 消费且类型匹配）；`activities` 两侧都接受并归一；装饰参数删除。

## 四、P1：感知、记忆推理与洞察

### [P1-12] 相似记忆判定：duplicate / conflict 阈值反了

- **位置**：`src/memory_agent/agent_memory.py:124-128` ✅；对照 `:283`（`merge_semantic_memory` 用的是**相反**规则）
- **证据**：✅
  ```python
  if meta.get("topic_key") == topic_key:
      if sim >= dup_sim:   out["duplicate"] = True
      elif sim <= con_sim: out["conflict"]  = True
  ```
  配合 `:153-163` 的测试注释「sim=0.667(<=0.85) → conflict」，可见作者实际把「中等相似」当冲突。
- **失败场景**：同 topic 但**几乎无关**（sim 很低）的记忆被标为 conflict 进 pending_review，而真正的高相似重复也走同一队列 → 人工审核被无关项淹没；两条路径（`:124` 与 `:283`）规则相反，同一对记忆在不同入口得到不同结论。
- **修复方向**：统一为一个函数 `classify_neighbor(sim, dup_sim, con_sim)`，语义定死为「高相似=重复、中相似带反向文本=冲突（需 NLI/关键词判定，不能只看相似度）」；修正测试夹具（`:153-163` 目前把反向规则锁为预期，子审计亦确认 `tests/test_agent_memory.py` 整体锁定了错误公式，见 §五）。

## 六、跨项目设计根因（本项目侧）

1. **默认值来自异常处理**：`_acp_kind` 的 `except: pass → "acp"`、`mcp_scopes` 未知工具 → READ、`tool` 调用签名 TypeError → 静默降级、`isinstance` 判断恒 False → 保护逻辑跳过。**当 `except Exception` 出现在鉴权/分类路径附近，它定义的实际安全策略就取代了设计文档**。建议 lint 规则：`mcp_server.py`/`acp_server.py`/`api/*` 内禁止裸 `except Exception`。
2. **例外清单式权限模型**：`WRITE_TOOLS` 靠人工维护、漏登即读；`dbg_` 前缀靠「不检查」实现；资源面绕开统一入口。**新增能力时安全属性单调退化**，只有显式声明 + 启动期完整性断言才能防退化。
3. **同一份数据三份副本（SQLite / FTS5 / chroma），但「谁负责收敛」没有单一 owner**：`mirror_dirty` 是正确的设计，错在它是**可选的**（部分 UPDATE 不标脏）。凡是「多副本 + outbox」，必须让 outbox 标记成为写路径不可绕过的一环（同一事务内完成）。
4. **契约靠注释维持**：docstring 声明的「单连接 + RLock」（`:9`）被 15+ 方法违反；schema 声明与 handler 类型不符；工具返回 `ok: true` 而内部 TypeError；`bypass_limits` 无效果。项目缺一个「schema ↔ handler」与「返回值 ↔ 真实状态」的一致性闸门——这类断言测试成本极低、收益最高。
5. **时间处理没有单一真相源**：naive 本地（`ha_client.py:167-194`）与 UTC 补偿（`ha_db.py:143-159`）方向相反、`now_local(8)` 硬编码（`insights.py:3887,3463`）、`tz_offset_hours=0.0` 夹具掩盖。三个项目（含 butler、AutoForge 的 UTC `now()` vs `"08:00"`）犯的是同一个错，说明**缺一份跨仓共用的时间规范**。
6. **可观测性偏「有日志」而非「能报警」**：静默 clamp、静默丢事件（P1-17）、假成功、僵尸 run 全都不会产生任何指标异常。建议把「数据被截断/窗口为空/迁移失败/schema 不匹配」显式做成计数器并告警。

## 三、已确认缺陷（实测复现）

### P1-4　到家时间预测取的是"当天最后事件"，非到家时间

**位置**：`src/memory_agent/behavior_predictor.py:57-61`
**覆盖**：`behavior_predictor.py` 126 行，**0% 测试覆盖**

```python
# 提取每天的到家时间（每天第一次出现该人的时间）   ← docstring 声明
for ev in events:
    ...
    if day not in daily_arrivals:
        daily_arrivals[day] = hour     # ← 取的是「遍历顺序里第一个」
```

函数内部**不做排序**，而唯一调用方 `store.list_behavior_events` 的 SQL 是：

```sql
SELECT * FROM behavior_events ... ORDER BY server_ts DESC LIMIT ?   -- 逆序
```

DESC 输入下，"遍历到的第一个"= **当天最晚的事件**，而非文档声明的"第一次出现"。

**实测复现**（构造 3 天数据：每天 08:00 离家 / 19:00 到家 / 23:00 睡前）：

| 输入顺序 | 函数返回 predicted_hour | 真实到家时间 |
|---|---|---|
| DESC（**当前实际**） | **23.0** | 19.0 |
| ASC（若调用方改排序） | **8.0** | 19.0 |

**误差 4 小时**，且置信度照常返回 0.3、sample_days 照常返回 3——**调用方无从分辨结果错没错**。

**为什么危险**：这是个隐式排序契约。函数既不排序，也不在签名里声明排序要求。哪天有人把 `ORDER BY` 改成 ASC（很常见的改动），结果会从"偏 4 小时"变成"取到离家时间"，**而 0% 覆盖意味着测试不会红**。

**影响面**：`api/behavior_routes.py:799` 与 `mcp_server.py:2622` 两条调用路径，WebUI 与 MCP 工具都受影响。

**修复建议**：函数内显式按 `server_ts` 升序排序后再取每天首条（或按业务语义改为"取 17:00 后第一条"），并在 docstring 里写明排序前置条件；补一条覆盖该函数的单测。

### P1-5　身份融合：未匹配信号稀释已匹配候选者，熟人判成陌生人

**位置**：`src/memory_agent/identity_fusion.py`（fusion 主函数，约 280-360 行）
**覆盖**：`identity_fusion.py` 180 行，**0% 测试覆盖**

**根因**：归一化分母 `total_weight` 把**未匹配信号**的源权重算进去，但分子不含它们的贡献：

```
score(A) = Σ(匹配信号 conf × 权重) / Σ(全部信号权重)   ← 分母含未匹配信号
```

同时 `stranger_score` **不除** `total_weight`，两者量纲不一致。

**实测复现**（默认权重 `arcface:0.6 / ha_face:0.3 / manual:0.1 / elimination:0.2`，阈值 high=0.8 / med=0.5）：

| 场景 | 输入信号 | chosen | conf | 等级 |
|---|---|---|---|---|
| A | 仅 ARCFACE→A(0.9) | **A** | 0.897 | **HIGH** |
| B | +HA_FACE 未匹配(0.9) | **None（陌生人）** | 0.900 | **LOW** |
| C | +HA_FACE 未匹配(0.5) | A | 0.598 | NEEDS_REVIEW |
| D | +HA_FACE 未匹配(0.2) | A | 0.598 | MED |

场景 A→B：A 从 0.897 **被稀释到 0.598（降 33%）**，而陌生人得分 0.900 反超 → **识别结果从"确认是 A"翻转为"陌生人"**。

**语义荒谬处**：**多来一路"没认出来"的信号，反而让已经认出来的结果被推翻**。信号越多越不可信，与融合的初衷相反。

**影响面**：身份识别是人脸→成员归档的上游，误判为陌生人会污染 `behavior_events.persons_json`，进而影响下游全部行为分析。

**修复建议**：分母只累加**投向该候选者**的权重；`stranger_score` 与候选者得分统一量纲。补单测——该模块当前 0% 覆盖。

### P2-4　到家后活动预测：同日事件不连续时重复计天

**位置**：`src/memory_agent/behavior_predictor.py:113-115`

```python
# 只记录每天第一次出现
if not arrival_times or arrival_times[-1][0] != day:
    arrival_times.append((day, dt))
```

只与**上一条记录**比较，而非查重。实测（3 天数据、同日交错排列）：

```
输入: [09-01, 09-02, 09-01, 09-02, 09-03]（同日不相邻）
记录: [09-01, 09-02, 09-01, 09-02, 09-03]  → 5 条，同日重复计入
应有: 3 条
```

后果：`activity_counts` 被重复计数放大，Top-N 活动排序失真。当前调用方（DESC 排序、同日连续）恰好不触发，**属脆弱假设而非当前故障**——一旦上游改排序即暴露。

## 五、其他探针结果

### R2-1　孤儿函数：从 1346 精确化到 68

第一轮 PyCG 报 1346 个零入度节点，已说明**大部分是装饰器注册导致的误报**（PyCG 看不见 `@mcp.tool()`、路由装饰器）。本轮用 AST 排除 `tool/resource/prompt/route/get/post/property` 等注册型装饰器，并用"名字是否在其他位置出现"二次过滤，降到 **68 个**。

节选：`behavior_predictor.detect_pattern_deviation`、`candidate_promotion.check_promotion_criteria`、`entity_resolution.is_match`、`history.query_range`、`identity.resolve_one`、`face_node_registry.unregister`

`connect()` 后不持锁直接 `execute` 的可疑点 **0 处**。项目已系统性用 `_db()` / `transaction()` 收口，这一项做得扎实。

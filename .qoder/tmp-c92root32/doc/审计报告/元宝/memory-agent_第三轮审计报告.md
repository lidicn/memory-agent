## 三、变体扩散：P1-4 的同族搜索

按 `variant-analysis` 四步法，把 P1-4 的根因抽象为：

```
函数内不做排序，却用「if key not in dict: dict[key] = value」取"第一个"
→ 实际取到的是「遍历顺序的第一个」，与 docstring 声明的"第一次出现"（时间最早）不等价
```

**第一步：全库扫描该模式** → 命中 8 处。

**第二步：更宽的顺序依赖扫描**（函数内无 `sorted` 却出现 `取[0]` / `取[-1]` / `取遍历首个`）→ 76 处候选。

**第三步：逐处 triage**

| 位置 | 判定 | 依据 |
|---|---|---|
| `behavior_predictor.py:60` | **缺陷（P1-4）** | 第二轮已确认 |
| `daily_profile.py:35` | **缺陷（P1-6）** | 本轮确认，见下 |
| `change_attribution.py:95/101/137` | **正确范例** | 显式 `sorted(events, key=lambda e: e.get("server_ts",""))` 升序后取首个 |
| `presence_fusion.py:88` | 安全 | 注释明确声明"同房间取最新一条，占用是瞬时快照"，语义即最新 |
| `arena.py:83` | 安全 | 上游 `order="asc"` 显式升序；且取首个是为编号，非时间语义 |
| `signal_learning.py:57` | 安全 | 聚类分组，结果与顺序无关 |
| `ha_client.py:445` | 安全 | 房间分组初始化，与顺序无关 |

**结论**：8 处命中 → 2 处真缺陷、1 处正确范例、5 处顺序无关。76 处宽口径候选中，仅这 2 处构成"时间语义 + 顺序敏感 + 上游 DESC"的致命组合。

> 注：该扫描已固化为 `ma_audit.py` 的 R3-1 探针，但固化版的 AST 匹配条件比手工 grep 更严（要求赋值右值为纯变量且左值以字典名起始），只命中 3 处。**triaging 结论基于手工扫描的 8 处**，固化为探针时匹配条件需放宽。

## 四、P1-6　回家时间基线取"最晚出现"，与同文件另一处口径相反

**位置**：`src/memory_agent/daily_profile.py:35`　（`compute_return_time_baseline`）

```python
# docstring: 每天第一次出现的小时
if day not in daily_hours:
    daily_hours[day] = hour      # ← 取「遍历顺序第一个」
```

### 铁证：同一文件内两处口径相反

| 位置 | 代码 | 语义 |
|---|---|---|
| 第 35 行（**基线**） | `if day not in daily_hours: ...` 取遍历首个 | DESC 下 = **每天最晚** |
| 第 98 行（**今天**） | `today_events[-1]` + 注释 **"DESC 排序，最后一个是最早的"** | DESC 下 = **每天最早** ✅ |

作者在第 98 行明确知道输入是 DESC 并正确处理，却在同文件的第 35 行漏掉了同一前提。上游 `store.list_behavior_events` 的 SQL 确为 `ORDER BY server_ts DESC`。

**后果**：基线用"最晚出现"口径（如 23:30 睡前活动），今天用"最早出现"口径（19:00 到家），两者直接相减。

**实测复现**（3 天，每天 19:00 回家 + 23:30 最后活动）：

```
baseline median_hour = 23.5   ← 应取 19.0
今天 current_hour    = 19.0   ← 正确
check_return_time_anomaly → anomaly=True, deviation_hours=4.5, baseline_mad=0.0
```

**每天必然误报异常**——MAD=0（基线三天都是 23.5）使阈值极窄，正常到家也判定为异常。

## 五、变异测试：把缺陷按"能否被测试抓到"定级

方法：对缺陷点施加语义变异 → 跑全量 1096 项测试 → **存活** = 测试抓不到 = 盲区。

| 变异点 | 施加的变异 | 结果 | 判定 |
|---|---|---|---|
| P1-4 `behavior_predictor:60` | 取首个 → 无条件覆盖 | **存活** 1096 passed | 测试盲区 |
| P1-5 `identity_fusion` | 归一化分母 ×1.5 | **存活** 1096 passed | 测试盲区 |
| P1-6 `daily_profile:35` | 取首个 → 无条件覆盖 | **被杀** 1 failed | 测试能抓到 |
| 对照组 `store.now_local` 改名 | 改名使其 NameError | **被杀** | 验证测试确实在执行 |

对照组被杀，证明这套测试真的在跑——变异测试本身可信。

### 但 P1-6 "被杀"不等于"安全"

杀掉它的是 `tests/test_daily_profile.py::test_daily_first_occurrence`：

```python
def test_daily_first_occurrence():
    """测试每天只取第一次出现的时间。"""
    events = [
        {"server_ts": "2026-09-15T20:00:00", ...},   # ← ASC
        {"server_ts": "2026-09-15T22:00:00", ...},   # 同一天第二次，应忽略
        ...
    ]
    assert abs(baseline["median_hour"] - 20.0) < 0.01
```

**这个测试写得很对**——它明确断言了"每天只取第一次"的正确语义。但它喂的是**升序（ASC）**数据，而生产喂的是**降序（DESC）**。

于是形成一个诡异局面：

> 函数实现在 ASC 下正确、在 DESC 下错误；
> 测试用 ASC 验证通过；
> 生产用 DESC 实际出错。

函数从未声明这个排序前置条件。`spec-to-code-compliance` 的视角下，这是 **docstring 与实现的契约缺口**，而测试恰好站在了契约正确的一侧，把生产侧的偏差完全掩盖了。

**这比"完全没测"更危险**：0% 覆盖的模块至少知道有风险；有测试、测试通过、测试还断言了正确语义——却因为测试数据的顺序与生产相反，反而给了虚假的安全感。

## 六、三方法对比：本轮与前三轮的方法论定位

| 方法 | 能抓什么 | 抓不到什么 |
|---|---|---|
| 静态扫描（ruff/bandit） | 语法级反模式、危险 API | 语义缺陷（P1-4/P1-5 全静默通过） |
| 属性测试（Hypothesis） | 崩溃类缺陷 | **语义错误**——第二轮 9 函数 × 200 例零崩溃，却漏掉两个 P1 |
| 覆盖率导引 | 定位未测区域 | 已测但喂错数据的情况（P1-6） |
| **变异测试** | 量化测试有效性 | 单独看"被杀"会误判为安全（P1-6） |
| **变体扩散** | 同族缺陷批量复制 | — |

**本轮的关键方法论收获**：变异测试的"存活/被杀"只是信号，不是结论。**"被杀"必须追查是哪些测试杀的、测试的输入假设与生产是否一致**——否则会把 P1-6 这类缺陷误判为已覆盖。

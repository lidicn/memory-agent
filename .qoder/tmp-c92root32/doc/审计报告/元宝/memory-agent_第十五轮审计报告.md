## 二、关键判据：缓存类问题的核心是「key 空间是否有界」

R15-1 报出 2 处"有写入但无失效"的缓存：

| 缓存 | 初判 |
|---|---|
| `vision_service._light_cache` | 无 pop/clear → 疑似泄漏 |
| `candidate_promotion.cached` | 无失效 → 疑似泄漏 |

### `_light_cache`：证伪

```python
self._light_cache: dict[str, tuple] = {}   # entity_id -> (monotonic, on|None)
```

- 只有 TTL 判定（`now - cached[0] < _LIGHT_CACHE_TTL_S`），无淘汰
- 但 **key 是 `entity_id`，由 HA 配置决定 → 空间有界**
- 永不清理 ≠ 无限增长

### 与第十轮 P3-4 的对比（这才是重点）

| | `_light_cache` | `_CLIENT_POOL`（P3-4） |
|---|---|---|
| key | `entity_id` | `(base_url, headers含token)` |
| key 空间 | **有界**（配置固定） | **无界**（token 轮换即新增） |
| 判定 | 非缺陷 | P3 |

**同样的"无淘汰"，一个安全一个有害**——差别不在代码写法，而在 key 空间的数学性质。这是本轮最有复用价值的判据。

### `cached`：证伪

`candidate_promotion.py:1077` 的 `cached` 是**局部变量**（`cached = self._cache.get_json(...)`），不是缓存容器。探针误把变量名当缓存名。

## 三、R15-2 缓存 key 完整性：3 处均证伪

### `infer_activities`

```python
ckey = ("infer_activities", tuple(room_filter or ()),
        start_iso[:16], end_iso[:16],
        tuple(sorted(activities)) if activities else None)
```

**key 完整**：含 room_filter、start/end（分钟粒度对齐）、activities。入参 `days/rooms/start/end/activities` 全覆盖。注释还解释了为何用 `[:16]` 截断——`days` 模式下窗口终点逐秒变化会让 key 抖动。

### `get_behavior_insights`

```python
ckey = ("get_behavior_insights", int(compare_days or 7))
```

**key 只含 `compare_days`，不含日期。** 窗口每天都变却用同一个 key——初看是缺陷。

**但证伪**：TTL 为 60 秒（`insight_cache_ttl` 默认 60.0）。窗口日变导致的最坏后果是**返回 60 秒前的陈旧数据**，而这是缓存的正常语义。

### `llm_ask` 的 `ask_cache_key`

初看 key 不含 `model` 参数（用户可传 `model_override`）。

**证伪**：缓存只覆盖**确定性路径**（`intent == "device_usage"` 且走 `render_device_usage` 模板渲染），该路径**不调用 LLM**。故 `model` 不参与结果，不需要进 key。

| 缓存 | TTL | 容量上限 | 淘汰 |

| `store.voice_answer_cache`（SQLite） | — | ✅ 软上限 | 超限时删最旧 10% |

`voice_answer_cache` 的软上限实测：

```
插入 5000 次 → 5000 条
插入 50000 次 → 5000 条
插入 500000 次 → 5000 条     ← 稳态有界
```

单条插入场景下稳态在 `MAX ~ MAX + MAX/10` 之间。批量插入会短暂超限（软上限非硬上限），可接受。

**这是全项目第二个"治理质量很高"的模块**（第一个是第十三轮的 `LEGACY_CONTRACT_MEMBERS` 契约转发）。

## 八、贯穿十五轮的三条方法论

### 1. 探针静默失败比返回错误更危险

- 第五轮：`ast.alias` 漏计 → 68 孤儿虚高
- 第十二轮：函数名跨轮覆盖 → R12 全 0（假"无风险"）
- 第十三轮：heredoc 引号转义失败 → 注入静默失败
- **第十二轮差点输出"高复杂度函数 0 个"**，而真实是 14 个风险区、含 P2-9

已固化：探针独立成文件优先、函数名加轮次前缀、跑通验证再并入。

### 2. 必须理解被检测系统的实际执行路径

| 轮次 | 硬匹配的误判 | 真相 |
|---|---|---|
| 七 | "无锁即竞态"（24→1） | asyncio 单线程，无 await 则不竞态 |
| 八 | "写有校验读没有"（3 假阳性） | `dispatch` 按 expose 拦，mcp 工具走不到 getattr |
| 十三 | "内部 helper 无规范化"（7 处） | 契约转发，设计如此 |
| 十四 | "`except: pass` 即致命"（57 处） | 多为探测链/资源清理的正确容错 |
| 十五 | "无淘汰即泄漏"（2 处） | key 空间有界则无害 |

**共鸣**：批量语法匹配 → 批量假阳性。噪音过滤比检测本身更耗工作量。

### 3. 项目自身的注释是最精准的规则集

第一轮用项目自己写的三处时区警告注释做种子，揪出了漏网的 P1-3。**比任何通用规则集都准。**

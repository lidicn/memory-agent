## 三、先说方法论：本轮最大的收获是给自己的探针纠错

R7-2 初版报 **24 处**"模块级共享可变状态被无锁修改"。逐层筛下来：

```
24 处原始命中
  └─ 函数内确无任何锁：        16 处   （其余 8 处用了 *_LOCK，探针正则漏判）
      └─ 判定为真竞态风险：     6 处   （其余 10 处是 async 且读-写间无 await）
          └─ 实测确认：         1 处   → P2-6
```

**关键判定规则**（这条比任何单个发现都重要）：

> asyncio 是**单线程**。async 函数内，若"读"与"写"之间**没有 await**，事件循环不会切走，**不可能**发生竞态——即使无锁也安全。
>
> 只有两种情形是真风险：
> 1. async 函数内读→**await**→写（会被切走）
> 2. 同步函数在 `to_thread` 线程池里跑（真多线程）

按这条筛完，10 处"无锁 async 无 await"全部证伪。**如果只按"有没有锁"判断，会造出 10 个假 bug。**

## 四、P2-6　`_CONV` 对话上下文在并发下丢失更新

**位置**：`src/memory_agent/api/debug_routes.py`

```python
# 第 183-184 行（读）
if run.conversation_id and run.conversation_id in _CONV:
    messages = list(_CONV[run.conversation_id])
    messages.append({"role": "user", "content": run.instruction})
...
# 第 313-314 行（写）—— 中间隔着整个 LLM 工具循环，数十次 await
if run.conversation_id:
    _CONV[run.conversation_id] = messages
```

### 为什么是真竞态

`_execute_run` 是 async 函数，中间有**大量 await**（LLM 调用、工具执行）。两个使用**同一 `conversation_id`** 的并发 run 会：

1. A 读 `_CONV[c]` → 拿到 messages（N 条）
2. A await（LLM 调用，可能数秒）
3. B 读 `_CONV[c]` → 拿到同一份（N 条）
4. B 完成，写回（N+2 条）
5. A 完成，写回（N+2 条）← **B 的追加被覆盖**

`_CONV` 与 `_RUNS`、`_CONV_ORDER` 全是模块级 dict/list，**无任何锁**。

### 实测复现

复刻"读 → 让出 → 拼接 → 覆盖写"结构，6 线程 × 3000 次：

```
期望 18000 条，实得 3089 条 → 丢失 14911 条（83%）
```

### 定级 P2 而非 P1 的理由（如实说明）

触发需同时满足：**同一 conversation_id + 并发发起两个 run**。这是调试接口（`/api/debug/llm/run`），常规单人调试很少并发；且后果是**上下文丢失**而非崩溃或数据损坏。

但代码里明确支持续轮（`conversation_id` 参数、第 183 行注释"续轮：加载既有对话上下文并追加本次指令"），多轮并发调试是合理使用场景。

### 修复建议

给 `_CONV` / `_CONV_ORDER` / `_RUNS` 加一把 `threading.Lock`（或 asyncio.Lock），或改为"读取时拷贝、写入时用 `setdefault` + append"的组合。同一 conversation 串行化也可。

## 六、R7-1 锁覆盖不对称：8 处全部证伪

初版报 8 个类"有的方法持锁有的不持锁"。逐个核查后**全部是探针误判**——探针把 `with self._db()` 这类**间接持锁**（`_db()` 内部 `with self._lock`）当成了"未持锁"。

典型：`learning_store.py:72 LearningStore`。探针标记 `insert_signals`、`list_signals` 等 5 个方法"未持锁"，实际它们都用 `with self._db() as conn:`，而 `_db()` 是 `@contextmanager`，内部 `with self._lock:`。

**这个项目在数据库层的锁纪律是干净的**——`LearningStore` 的注释甚至写明了修复依据：

> 第六轮审计 CRITICAL-2：连接是本实例的单例共享对象，FastAPI 会在多个线程里调用它；execute 与 commit 之间无锁 → 甲线程的 commit 会把乙线程未写完的半截事务一并提交。

说明作者系统性处理过。**同一个作者，数据库加锁了，全局 dict 没加**——这正是 P2-6 存在的背景。

## 四、P3-9　JWT 脱敏正则漏匹配两段式 JWT（新缺陷）

**位置**：`src/memory_agent/feedback_pack.py:32`

```python
_JWT_RE = re.compile(r"eyJ[A-Za-z0-9_-]+\.eyJ[A-Za-z0-9_-]+\.[A-Za-z0-9_-]+")
```

正则要求**三段**（header.payload.signature）。

### 实测

| 输入 | 是否脱敏 |
|---|---|
| 三段真实长度 JWT | ✅ `<REDACTED-JWT>` |
| **两段式 JWT**（header.payload，无签名段） | ❌ **原样输出** |

### 为什么这是真问题

JWT 的 **payload 段（第二段）才是敏感信息的载体**——它 Base64 编码了 `sub`、`is_admin`、`exp` 等声明。两段式 JWT 虽然没有签名段，**payload 仍然是完整可读的**。

未签名/签名被剥离的 JWT 在实际日志中并不罕见（客户端截断、日志中间件处理、错误堆栈截取）。这类字符串**携带完整的用户身份信息却逃过脱敏**。

### 定级 P3

- 需两段式 JWT 恰好出现在反馈包/日志中
- 影响的是信息泄漏面，非直接功能故障
- 身份证、API Key、银行卡等其他脱敏规则均正常工作

### 修复建议

放宽正则为两段或三段均可：

```python
_JWT_RE = re.compile(r"eyJ[A-Za-z0-9_-]+\.eyJ[A-Za-z0-9_-]+(?:\.[A-Za-z0-9_-]+)?")
```

## 五、P4-4 版本固定：可复现性风险

| 文件 | 策略 |
|---|---|
| `pyproject.toml` | 13/13 依赖**仅用 `>=`**，无 `==` 或 `~=` |
| `Dockerfile` | 仅 `chromadb==0.5.23` 固定，其余不固定或仍用 `>=` |

**风险**：依赖上游发布破坏性更新时，构建产物会漂移，且难以回溯"当时装的到底是什么版本"。

这在本次审计中**已被实际观察到**：沙箱环境多次重置后重装依赖，`starlette` 从某版本变成 1.7.0、`pydantic` 变成 2.13.5——不同时间构建的环境行为可能不同。

**建议**：生成锁文件（`pip-compile` / `uv lock`）并在 Dockerfile 中使用。

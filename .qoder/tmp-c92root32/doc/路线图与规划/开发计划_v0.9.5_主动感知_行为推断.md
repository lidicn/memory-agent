## 一、目标与边界

把「主动感知」中 **MA 不可替代的部分**落到可运行：从 `behavior_events` 产出 **canonical 行为状态**（工作/睡觉/移动），**挖掘新的事件序列模式**（LLM 自进化），并作为 **"谁"的身份权威源**。实时反应（毫秒级规则、推送、联动）由管家负责，本计划**不做**。

设计原则（沿用方案 C / 分工建议书）：
1. **MA 不做实时流**：MA 是批量轮询 HA MariaDB + 人脸推送，无 websocket 实时流；实时反应天然归管家。
2. **权威 vs 易逝**：管家产"易逝实时假设"为反应，MA 产"持久行为真相 + 长期模式"为记忆；MA 对行为真相拥有权威，管家对实时反应拥有权威。
3. **不重造身份**：`ma/presence`（ArcFace）是"谁"的唯一权威源，管家经此消费，MA 不接管家的人体传感器流。

## 四、核心引擎规格（activity_inference）

### 4.1 事件模型
MA 内部的设备/状态事件统一为：`{ts, entity_id, room, type(door/light/climate/presence/face), state}`。来源为 `behavior_events`（HA 采集产物），非实时流。

### 4.2 有序序列规则（sequence rule）
```
rule = {
  name, order_sensitive: true,
  steps: [ {entity, state, within_min, after_prev_min?}, ... ],
  time_window: "21:00-23:59"(可选),
  infer: "user_asleep" | "study_work" | "transit",
  confidence: 0.0-1.0
}
```
匹配算法：维护每房间最近 N 分钟事件滑动窗口；新事件入窗后，按 `steps` 顺序（含 `after_prev_min` 间隔约束）回溯匹配；全部命中且时间窗符合 → 产出 canonical 状态。

### 4.3 多传感器融合与去抖
- **PIR 去抖**：同一 `presence` 实体连触发合并为一次（窗口 `pir_debounce_sec`）；
- **身份归一**：`face` 事件经 `ma/presence` 归一为 member；PIR 只给"有人"不绑定 member；轨迹归属结合最近 `ma/presence` 身份；
- **置信度**：门磁+灯+空调多源命中 → 高置信；仅单 PIR → 低置信（低于 `activity_conf_threshold` 不写权威状态，仅作候选）。

### 4.4 产出
- canonical 行为状态写 `behavior_states`（权威，供 `GET /api/behaviors`）；
- 低于阈值的识别仅进 `candidate_rules`（待人工审核，不污染权威状态）。

## 五、序列模式挖掘（研究员扩展，任务 C）

复用 v0.8 记忆研究员的安全闸与调度：新增 `direction=sequence`，从 7 天 `behavior_events` 聚合并**自动发现高频有序事件序列**（非预定义），生成候选规则入 `candidate_rules` 表（staging）。用户审核采纳后，经 `POST /api/insight_routes` 导出接口以结构化 JSON 交付管家规则库（对应管家 v1.7 M5，实现方为 MA）。

> 此即分工建议书定义的"LLM 自进化"落点：MA 挖模式、管家消费规则。RE 防重复原则：管家不自建挖掘，只消费 MA 候选规则。

## 六、意图/习惯层（任务 D）

从 `behavior_states` 的重复活动序列，按 member+时间聚合，推断长期意图（习惯），写入：
- `member-schedule`：作息类（如"lidicn 工作日通常 22:30 睡"）→ 作管家融合先验；
- `agent_memories`（source=ma, staging）：行为偏好类。

复用 v0.8 的 Chroma 语义去重与 staging 审阅流，避免重复建机制。

## 七、数据流

```
HA 事件 → behavior_events(批量采集) → activity_inference(滑动窗口+序列匹配+融合)
  → behavior_states(canonical 权威状态) → GET /api/behaviors(管家消费)
                                        ↘ 低于阈值 → candidate_rules(待审)
researcher(direction=sequence, 7天) → candidate_rules → 用户审核 → 导出管家规则库
behavior_states(聚合) → 意图/习惯 → member-schedule / agent_memories → 管家先验
ma/presence(ArcFace) ──┐
                        ├─→ GET /api/behaviors(身份融合)
behavior_states ────────┘
```

---

## 八、回归清单

1. `GET /api/behaviors` 返回结构含 member/location/activity/confidence/ts，且身份来自 `ma/presence` 而非管家人体传感器。
2. 有序序列规则（门开→关→灯亮…）能正确按序匹配，逆序不误判。
3. PIR 连触发被去抖合并，不重复产出状态。
4. 低于 `activity_conf_threshold` 的识别只进 `candidate_rules`，不污染 `behavior_states`。
5. 研究员 `direction=sequence` 能产出候选规则且不超预算（复用 v0.8 安全闸）。
6. 候选规则审核采纳后可经导出接口交付（结构化 JSON），管家可消费。
7. 意图/习惯写入 `member-schedule` 且被管家 `GET /api/insights/member-schedule` 可见。
8. 禁止 `deploy_nas.sh`；改动 scp + docker restart 生效。

## 十、风险

| 风险 | 应对 |
|---|---|
| 与管家重复建设（管家自建行为推断） | 分工建议书已约定：管家只消费 `GET /api/behaviors`，不自建；MA 对行为真相权威 |

| `behavior_events` 延迟（批量采集）导致 canonical 状态滞后 | MA 状态定位为"权威记忆"非"实时触发"；实时反应由管家 websocket 承担 |
| 研究员序列挖掘成本 | 复用 v0.8 立体安全闸（日预算/单元上限/超时/退避）+ 凌晨低峰 |

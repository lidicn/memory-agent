## Part 2 ·【主动感知】v2.0 路线图

> 设计原则（沿用 Miloco 范式 + MA 本地优先定位）：
> 1. **Gate→Identity→Omni 四层感知**：边缘 AI 事件先过滤（Gate），人脸/身份先融合（Identity），VLM 只在"边缘无信号或需语义"时补（Omni）。
> 2. **STATIC 快路径 / DYNAMIC 慢路径**：确定性告警走无 LLM 快路径；需语义规划才交 Agent。
> 3. **记忆候选区晋升**：单帧观察不污染长期记忆。
> 4. **建议语义去重 + 单飞分发**：避免刷屏。
> 5. **反馈闭环 fail-closed**：误识别可打包成 bad-case。

### Phase 0 · 感知信号接入（白菜收益，约 2–3 天）

| # | 任务 | 落地 | 验收 |
|---|---|---|---|
| 0.1 | **订阅客厅盒侧 AI 事件** | `ha_client` 增量监听 `event.chuangmi_*_（unkonw_face/known_face/key_area_human/long_time_no_human/pet_event/babycry_event/gesture_event/day_to_night/night_to_day/into_fav_area/out_fav_area）`，落新表 `perception_events`（统一 `source=edge_ai` + `kind` + `payload`） | HA 触发人脸/人形 → `perception_events` 1s 内出现对应行 |
| 0.2 | 统一感知总线 | `perception_events` 同时容纳三类来源：`edge_ai`（客厅盒侧）、`vlm`（VLM 结果）、`sensor`（现有 HA 采集）。`behavior_events` 继续存"人+动作"语义产物，二者通过 `room/ts` 关联 | 三类来源可同窗查询 |
| 0.3 | 书房/小黄人降级策略 | 两基础款无 AI → 保留现有 VLM 巡检（vision_service），但**仅在 `motion_tracking`=on 或边缘无信号时**拉帧（省 VLM 调用，呼应 Miloco Gate） | 书房夜间空闲时段 VLM 调用下降 ≥50% |

> 对应 Miloco 学习：感知管线"Gate"= 边缘事件已结构化，直接跳过 VLM；学 `perception-pipeline.md` 的"分布式独立推理+全局身份共享"——客厅边缘 AI 即 per-camera 独立推理。

### Phase 1 · 感知分层管线（约 3–4 天）

| # | 任务 | 落地 | 验收 |
|---|---|---|---|
| 1.1 | **Gate 层** | 边缘 AI 事件（人脸/人形/宠物/哭声/昼夜）即"已发生事实"→ 直接结构化进 `behavior_events`，**不调 VLM** | 客厅有人/陌生人 → 零 VLM 调用即出行为事件 |
| 1.2 | **Identity 层三路融合** | 客厅 `known/unknown_face` 事件 + TV ArcFace（`/api/events/face`）+ VLM 外观匹配（`resolve_appearance_to_member`）→ 统一 `{person, confidence, via}`，输出到 `behavior_events.persons` | 同一人三路信号 ≥2 路一致即定身份 |
| 1.3 | **Omni 层按需补语义** | 仅当"边缘无人形事件 或 需'在干嘛'语义"（如小黄人/书房、或客厅需场景描述）时拉 go2rtc 帧调 VLM；VLM 输出 `scene/action` 注入总线 | 小黄人有人 → 触发一次 VLM 描述动作 |
| 1.4 | 去重/去抖 | 边缘事件已去抖；VLM 沿用现有冷却+场景哈希；新增 **Miloco 式建议语义去重**（bge 句向量）防重复 | 同类"客厅有人"1 窗口仅 1 条 |

> 对应 Miloco：`Gate→Identity→Omni` 四层（`perception-pipeline.md`）；身份 `face/body` 融合 + 五态状态机（`person-identity.md`）——MA 用"三路融合 + 阈值"替代五态机。

### Phase 2 · 记忆晋升与家庭画像（约 3 天）

| # | 任务 | 落地 | 验收 |
|---|---|---|---|
| 2.1 | **视觉行为事实候选区晋升** | 单帧观察先进 `candidates`（参考 Miloco `candidates.json`），需 N 次证据/跨天一致才 `promote` 进 `agent_memories`（topic_key=`habit:/vision/`） | "爷爷每晚看书"需 ≥3 天证据才成长期记忆 |
| 2.2 | **家庭画像注入感知** | 把成员习惯（`agent_memories` 中 `habit:`）注入 VLM prompt 与感知规则判定，形成"感知→记忆→感知"正反馈（照搬 Miloco `home_profile_loader.py` + `before_prompt_build` 思路） | VLM prompt 含"父亲高血压宜淡"→ 推荐食谱时主动纠偏 |
| 2.3 | 原子写 + 权重截断 | 家庭档案 `profile.md` 用临时文件+rename 原子替换 + 权重降序 token 截断（照搬 Miloco `home_profile/store.py`） | 并发写不读半截；超长自动截断高权重优先 |

> 对应 Miloco：`home-profile.md`（候选区晋升、加权截断、双路消费）。

### Phase 3 · 主动规则引擎（约 4 天）

| # | 任务 | 落地 | 验收 |
|---|---|---|---|
| 3.1 | **感知规则 DSL** | 自然语言"当客厅出现陌生人时…"，消费 `perception_events` + VLM；复用现有 `activity_inference` 序列规则框架 | 陌生人出现 → 规则命中 |
| 3.2 | **STATIC / DYNAMIC 拆分** | STATIC（确定性，无 LLM）：陌生人→推送告警、昼夜切换→记录；DYNAMIC（需语义）：交给 Agent 规划（经 `AgentDispatcher`） | STATIC 路径端到端无 LLM 调用 |
| 3.3 | **duration 滑窗去抖** | 把 Miloco `duration_seconds + duration_ratio` 滑窗搬进感知规则与 `activity_inference`，防单事件误触发 | 人形事件闪 1 帧不误报 |

> 对应 Miloco：`rule-automation.md`（STATIC/DYNAMIC + 四层 RuleRunner + 滑窗去抖）；`task-management.md` 状态机。

### Phase 4 · 主动分发与反馈闭环（约 3 天）

| # | 任务 | 落地 | 验收 |
|---|---|---|---|
| 4.1 | **统一分发单飞** | 主动洞察/告警经 `AgentDispatcher` 式收口：同 session 单飞、同类合并、优先级淘汰（MA 已有 idempotency + circuit breaker，补"会话单飞"） | 同房间同类告警不刷屏 |
| 4.2 | **建议语义去重** | bge 句向量相似度去重（复用现有 embedding），embedder 失败降级精确匹配 | 重复"客厅有人"被抑制 |
| 4.3 | **反馈闭环 fail-closed** | VLM 误识别 → 现有 👍👎 → 旁路快照+omni trace 打包（照搬 Miloco `build_feedback_pack` + `snapshot_context` 旁路落盘），脱敏失败宁可丢 trace（"宁可缺 trace 也不泄 PII"） | 误识别可导出本地 tar.gz bad-case 包 |

> 对应 Miloco：`event-feedback.md`、`dispatch` 单飞、`perception-pipeline.md` 建议语义去重。

### Phase 5 · 周期任务与看护（约 3 天，利用客厅 smart_care / 哭声）

| # | 任务 | 落地 | 验收 |
|---|---|---|---|
| 5.1 | **持久意图 + 周期归档** | 照搬 Miloco `task`+`task_record`：如"老人起夜记录""每日客厅有人时段"，日/周/月归档，自愈+唯一索引幂等 | 跨日自动归档旧行开新行 |
| 5.2 | **看护规则映射** | 客厅 `long_time_no_human` / `smart_care` / `baby_woke_up` → 看护提醒（老人长时间无人在家→提醒；婴儿醒→推送） | 触发看护提醒且不骚扰（状态机防重复） |

> 对应 Miloco：`task-management.md`（持久意图、周期归档、三类统计 progress/duration/event）。

### 并行轨道 · 感知底座（推荐引入 Frigate，见 Part 3）

书房/小黄人**完全没有本地 AI**，长期靠 VLM 取帧既贵又慢。建议在 Phase 0 同期评估 **Frigate**（本地目标检测，Coral/CPU，推 HA/MQTT），让三款相机统一获得 person/face/pet/vehicle 本地实时检测，把 Miloco 式"Gate"前移到本地、零云成本。

## Part 3 · Miloco 学习够吗？还需要调研其他开源项目吗？

### 3.1 Miloco 给的是什么（已足够用于"设计范式"）

Miloco 提供的是**架构范式与工程套路**，且已映射到 MA 具体模块（见上表）：
- 感知四层 `Gate→Identity→Omni` → MA 的"边缘事件 Gate + 三路身份 Identity + VLM Omni"
- 记忆候选区晋升、加权截断、双路消费 → MA 的 `agent_memories` staging 升级
- STATIC/DYNAMIC 规则 + 四层状态机 + 滑窗去抖 → MA 的 `activity_inference` 升级
- 建议语义去重、分发单飞、反馈 fail-closed → MA 现有 idempotency/circuit breaker/👍👎 升级

**这些足以指导 v2.0 的顶层设计与逐模块落地，不需要再"学一遍 Miloco"。**

### 3.2 Miloco 的盲区（正是 MA 当前最缺的）

Miloco **假设摄像头直连 VLM**（云、按窗推理、贵、非 always-on），其"感知"短板恰恰是 MA 需要的 **always-on 本地实时检测**：
- 客厅虽有免费盒侧 AI，但 MA 没接（Phase 0 补）；
- 书房/小黄人**无任何本地 AI**，纯 VLM 巡检定频、贵、慢、且受光线门槛限制（暗场景直接跳过）。

Miloco 不解决"如何在无云 VLM 前提下让所有摄像头实时感知"——它自己也是靠 VLM。

### 3.3 还需调研的开源项目（结论：需要，且优先级高）

| 项目 | 为什么值得调研 | 与 Miloco 的关系 |
|---|---|---|
| **Frigate**（本地 NVR + 目标检测） | 开源本地 person/object/vehicle 检测事实标准，Coral/CPU 推理，推 HA/MQTT/REST，能给三款相机（尤其书房/小黄人）**统一本地实时检测**，把"Gate"前移到本地、零云成本 | 补 Miloco 不做、MA 最缺的"本地眼睛"；Miloco 是"大脑/编排"参考，Frigate 是"眼睛/感知"参考，**互补** |
| **Double Take**（人脸识别伴侣） | 常与 Frigate 搭配，把检测结果中的人脸匹配到名字，输出 `match`/`unknown` 到 MQTT | 补 MA 身份层（尤其书房/小黄人无盒侧人脸时的本地人脸识别） |
| Home Assistant 原生 AI Task / Assist | 已在用（HA Assist 接入 MA）；其 `event` 实体正是客厅盒侧 AI 的载体 | 不必另起，复用 |
| Node-RED | 已在用（TTS/微信通知编排） | 不必另起 |

**建议**：Miloco 调研已完成、可直接用于 v2.0 设计；但**在动 Phase 0/并行轨道前，应再补一次 Frigate（+Double Take）专项调研**——重点看：① 能否直接消费 go2rtc 的 rtsp 流（避免改摄像头配置）；② 检测事件如何进 HA/MQTT 与 MA 的 `perception_events` 对齐；③ Coral/CPU 算力与延迟。这能决定"书房/小黄人要不要上 Frigate"以及 v2.0 的感知底座选型。

### 3.4 一句话结论

> Miloco 教会我们"主动感知该怎么编排"（范式已够）；但"感知本身怎么在本地便宜地发生"它没解决，需补 **Frigate** 调研。两者结合 = MA v2.0 的"本地眼睛(Frigate) + 编排大脑(Miloco 范式) + 记忆中枢(MA 已有)"。

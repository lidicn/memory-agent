## 三、v0.7.5 MCP 连接层加固（P0 安全项，v0.8 前置门）

### 为什么必须排在 v0.8 之前

v0.8 要引入两件**放大风险**的能力：**记忆研究员**（后台自治、自动写入）与
**mem0 式 UPDATE/INVALIDATE**（改写存量记忆）。这与 v0.7 提前做备份/DR 是同一个道理——
**在让自动化 Agent 动存量记忆之前，先把「谁能动、动过什么」管起来**。
当前状态是：任何一枚 `mcp_` 令牌即拥有 53 个工具的完全读写权，且**运行完全无审计**。

### 任务（P0，全部为收敛性改动，不改变既有契约）

1. **工具级 scope 授权** ✅ *已交付*：令牌记录增 `scopes`（`read` / `write`）。
   **关键实现决策**：scope 判定下沉到 MCP 工具分发层（`mcp_server._tracked_call_tool`），
   而非 ASGI 中间件——中间件读取并回放 ASGI body 会让 `/mcp` 的 Mount/Route 转发挂起（实测所有
   `tools/call` 超时）。分发层拿到工具名与令牌 scopes，`write` 类工具无权限时返回 `isError` 的
   `CallToolResult`（明确 `DENIED`，非 200 包裹体）。**新令牌默认只读**，写工具需显式授权；
   **存量令牌自动补 `read+write`**（保证现有 Agent 不断连），WebUI 标注「继承」提示收紧。
2. **操作审计** ✅ *已交付*：dispatch 层记录 `{ts, token_name, tool, scope, duration_ms, ok, error_text}`，
   落库（`mcp_audit` 表，保留 30 天）+ 只读查询入口 `GET /api/mcp/audit` + WebUI「调用审计」卡片。
   与内存统计 `MCP_CALL_STATS`（效率快照）分工明确：本表是带身份的可追溯链路。
3. **kind 身份隔离** ✅ *已交付*：MCP 只认 `mcp_`/`debug`、ACP 只认 `acp_`/`arena`。
   `mcp_auth.py` 校验 `kind in ("mcp","debug")`，`acp_`/`arena_` 令牌访问 `/mcp` 一律 403（实测 -32003）。
4. **Origin/Host 纵深防御** ✅ *已交付*：`MCP_ALLOWED_ORIGINS` 白名单校验（默认关闭，不破坏现有客户端），
   不把全部防护压在一个 Bearer 上。

同主题已交付（审计 PROJECT-20260914-001 分支，非本版新增）：
- **M6 / AC1** URL token 默认关闭（`MCP_ALLOW_URL_TOKEN=1` 才开）
- **O8** debug 端点 traceback 脱敏
- **A2 JWT 撤销（jti 黑名单）+ A4 登录爆破防护**（WebUI 侧）

### 验收门（2026-09-15 容器内回归全部通过 ✅）

- 只读令牌调用写工具返回明确 `DENIED`（isError 的 `CallToolResult`，非 200 包裹体）✅
- `acp_`/`arena_` 令牌访问 `/mcp` 被拒（403 `-32003`）✅
- 任一工具调用可在审计中查到「谁 / 何时 / 哪个工具 / 耗时 / 成败」（`mcp_audit` 表）✅
- 53 个工具**全量回归**：读工具在只读令牌下行为不变 ✅（实测 `list_members` 正常返回）

详细任务分解、改动点与回归清单见 `开发计划_v0.7.5_MCP连接层加固.md`。

## 四、v0.8 主动记忆（依赖 v0.7.5 完成）

1. **记忆研究员（定向 + 安全闸 + 定期）** ✅ *已交付*（4 天）【Letta sleep-time 范式 + DISCOVER + 复用现有 `analysis_template`】：后台定时洞察引擎，**LLM 只「解释/命名」已被规则提纯的信号**（复用 `behavior_insights`/`infer_activities`/`anomaly_report` 预聚合产物，绝不直接读原始事件），以收敛 token 与算力（对比无脑 dump 原始事件成本降约 100 倍）。
   - **四轴定向坐标系（Insight Job）**：`方向(direction) × 时间窗(window) × 区域(area) × 对象(member)`。方向限定为有限类别（作息节律/设备异常/习惯固化/成员差异/跨设备联动/能耗），不开放 LLM 自由探索；时间窗默认近 7 天、硬上限 ≤30 天并带「上周同期」对照；区域按 room 维度（含全屋）；对象按成员（含全部成员）。
   - **底座复用**：扩展现有 `analysis_template`（`BehaviorInsight`）加 `direction/area/member/schedule/budget/enabled` 字段，从「手动 run」升级为「可定期自动跑的 Job」，不新建平行表。
   - **立体安全闸**：全局日 token 预算断路器（到顶即停并写审计）、单 Job 单元上限（4 轴笛卡尔积爆炸防护）、单次调用输入/输出上限（超长预聚合产物截断）、超时取消（复用 30s 上限）、连续失败退避暂停。
   - **存储分工**：Job 配置落 SQLite；已生成洞察用现有 Chroma `agent_memory` collection 做语义去重（dup_sim>0.92 则 UPDATE 而非新增）。
   - **staging 闭环 + 成本可观测**：洞察进 `pending_review`，30 天无人审自动归档；每次 Job 跑完记录 token/单元/命中率并在 WebUI 展示。
   - 遵循 Letta 三原则：**后台自治**、**只写自己的区**（agent_memories，source=ma，staging 起）、**产出可回滚**（一键驳回）。
   > 依赖：写入动作需受 v0.7.5 scope 约束并被审计；若 v0.7.5 未验收，本项延后至其收口。详见 `开发计划_v0.8_主动记忆.md`。
2. **mem0 式记忆操作** ✅ *已交付*（2 天）【直接抄 mem0，Apache-2.0】：写入管线从「dup_sim>0.92 判重」升级为：
   ```
   新内容 → 向量近邻召回同 topic 旧记忆 →
     ├─ 无相似 → ADD
     ├─ 相似且兼容/补充 → UPDATE（旧条目更新，保留演变链 prev_id）
     ├─ 相似且矛盾且新更可信（source 置信/时间新） → INVALIDATE 旧 + ADD 新
     └─ 模糊区间 → LLM 判定（复用 arena 三层判定的降级模式）
   ```
   解决「孩子22点睡→23点半睡」并存打架的问题。
3. **洞察粒度反馈** ✅ *已交付*（1 天）：洞察卡片 👍👎 → 反哺模板权重与成员档案。（记忆页 👍👎 + `trust`/TTL 回路 + `/api/agent/memories/feedback`；**成员档案反哺** = `GET /api/members/{id}/insight-feedback` + 成员详情「相关洞察反馈」区块；**方向/模板权重反哺** = `GET /api/researcher/direction-feedback` + 定向洞察页「方向洞察质量」卡片）

### 为什么单独成版（而非并入 v0.8/v0.9）

主动感知是**跨项目主题**：管家 v1.7 负责实时反应层（HA websocket 规则引擎 + 推送），MA 负责**权威记忆 + 发现 + 身份层**。MA 没有实时事件流（仅批量轮询 HA MariaDB + 人脸推送），故实时反应天然归管家；MA 产出的是分钟级 canonical 行为真相与长期模式，作为管家实时融合的先验与权威源。

### 三层分工（防重复铁律）

| 层 | 归属 | 职责 |
|---|---|---|
| 实时反应层 | **管家** | 规则引擎（毫秒级）→ 推送 / 联动 / 实时位置 |
| 权威记忆 + 发现层 | **MA** | canonical 行为状态（工作/睡觉/移动）+ 挖掘新模式（LLM 自进化）+ 长期习惯 |
| 身份层 | **MA** | `ma/presence`（ArcFace）是"谁"唯一权威源 |

MA 对"行为真相"拥有权威，管家对"实时反应"拥有权威；同一事件流两种用途，**管家不得自建行为推断 / 时间规律 / 人脸识别**，全部消费 MA 接口。

### 数据流决策（2026-09-13 补充 · 已采纳）

用户拍板：**MA 直连保底 + butler 推送富化**。细化如下，约束 v0.8 与 v0.9.5 的实现：

- **实时/主动感知归 butler，完整历史行为事件流归 MA**（互补非替代）。MA 记忆自洽、可降级，**绝不硬依赖 butler 存活**。
- **MA 保留现有 HA 直连 ingest**（被动日志，非感知）；重命名口径统一，当前 `HA_DB_ENABLED=false` 走 REST 兜底不变。
- **butler 不重复轮询 HA**；其主动感知到的高价值事件经**扩展 butler_token 写入窄接口**（`POST /api/events`，受 v0.7.5 scope 约束）推给 MA 的 `add_events` 合并入 `behavior_events`。
- **MA 绝不做 on-demand 实时 HA 查询**（洞察离线批处理，不需要此刻状态）。
- 单一事实源 = HA；butler 与 MA 皆为消费者，butler 额外做「主动」、MA 额外做「记忆+洞察」。
- 理由：MA 纵向模式依赖**全量**事件流；butler 主动感知会漏被动长尾，故 butler 推送仅作富化增强、非 MA 数据源依赖。

# 调研笔记：同类开源项目（2026-09-10）

> 目的：为 MA 下一轮路线图找可借鉴/可直抄的开源方案
> 范围：Agent 记忆层、智能家居 LLM 生态、视觉/人脸管线、房间级在场定位
> 结论速览：**3 个可直接抄的算法级方案（mem0 记忆操作、Graphiti 时间有效性、ESPresense 固件），3 个理念级借鉴（Letta sleep-time、Frigate 事件驱动、HA LLM API），4 个明确不抄**

---

## 一、Agent 记忆层（与 MA agent_memory 直接对标）

### 1.1 mem0（mem0ai/mem0，~53K stars，Apache-2.0）⭐ 最值得抄

**它做什么**：LLM 应用的通用记忆层——提取/整合/检索三段式管线，user/session/agent 三级作用域，向量+图+关键词混合检索。

**值得直抄的核心**：**记忆操作语义**。写入时不是简单判重，而是 LLM 将新内容与已有记忆比对后产出四选一决策：
```
ADD      新事实 → 新增
UPDATE   与已有记忆冲突且新更可信 → 更新旧条目（保留演变链）
DELETE   新信息证明旧记忆失效 → 标记失效
NOOP     无新信息 → 不动
```
**对照 MA 现状**：MA 只有 `agent_dup_sim>0.92` 判重，缺 UPDATE/INVALIDATE——「孩子22点睡」演变成「23点半睡」会变成两条并存记忆，检索时互相打架。mem0 的方案（Apache-2.0）可直接参考实现，且 MA 已有的 trust/staging/feedback 管线比 mem0 更完善，只补操作语义即可。

### 1.2 Graphiti（getzep/graphiti，MIT）⭐ 时间模型值得抄

**它做什么**：Zep 开源的时序知识图谱引擎，实体-关系三元组带**双时间戳**（事件发生时间 valid_at / 系统记录时间 ingested_at），事实有 valid_from/valid_to 生命周期，过期事实不删而是失效，可回溯任何时点的记忆状态。

**对照 MA**：`member-schedule`（作息规律）和洞察本质是「随时间演变的事实」，现在只有覆盖式更新。抄它的**时间有效性字段设计**（不用上它的 Neo4j 图数据库，SQLite 加两列即可）：作息变化可追溯（「上学期22点睡→这学期23点半」），管家拿到的先验也能带时效。

### 1.3 Letta / MemGPT（Apache-2.0）——理念背书

**核心概念**：**sleep-time compute**——后台 agent 在空闲时自主重组记忆、提炼经验，无需用户交互。这正是 MA 已规划的「记忆研究员（LLM 定时研究家庭数据）」的学术范式。抄它的「后台自治 + 只动自己的记忆区 + 产出可回滚」三原则，不抄它的框架（MA 不是通用 agent 框架）。

### 1.4 MemOS（MemCube：内容+来源+调度元数据）——验证方向

研究原型，不建议引入。但其「记忆是一级资源，带 provenance 可调度」的思想与 MA 的 `agent_memories`（source/trust/ttl/state）高度一致——**说明 MA 的记忆表设计走在正确路线上**。

## 二、智能家居 LLM 生态

### 2.1 HA 官方 LLM API（developers.home-assistant.io/docs/core/llm/）

HA 已官方开放「暴露 API 给 LLM」的机制（Assist + conversation agent + LLM tools）。**借鉴点**：MA 未来可以注册为一个 HA conversation agent——让 HA 原生语音/Assist 直接用上 MA 的家庭记忆，扩大 MA 消费面。这是 v1.0 候选项。

### 2.2 home-llm（acon96/home-llm）

为 HA 定制微调的小型本地 LLM（完全离线的对话控制）。**借鉴点**：断网/LLM 网关挂掉时的本地兜底思路；MA 的洞察查询目前强依赖云端 LLM，可考虑规则合成已具备（`_synthesize_answer` 不依赖 LLM，方向已对）。

### 2.3 hass-agent-llm（aradlein）

HA 自定义集成，扩展原生对话平台做自然语言控制。与 MA 定位不冲突（它是「控制」，MA 是「记忆」），可作 HA 侧集成的参考实现。

## 三、视觉 / 人脸管线

### 3.1 Frigate（NVR，内置人脸识别）

常驻视频流检测 + zone 划分 + MQTT 事件推送 + HA 深度集成，2026 版已**内置人脸识别**。**借鉴点**：
- **zone 概念**：MA 的「房间」粒度太粗，一个摄像头画面内可分 zone（客厅就餐区 vs 沙发区）
- **事件驱动 vs MA 的拉取轮询**：Frigate 常驻检测只在状态变化时发事件，MA 是定时拉帧+光线门槛。MA 现有方案成本低（无 GPU 要求），**不建议整体迁移**；但未来若 VLM 费用成为痛点，可用 Frigate 当「便宜的前置门」（只判有人/无人，有人才触发 VLM）
- 与 MA 不冲突：Frigate 输出设备级事件流，MA 输出语义行为（在干嘛），层次不同

### 3.2 Double Take / CompreFace

多后端人脸识别统一网关 / 开源人脸识别服务。**结论：不引入**——MA 已有 TV ArcFace 节点池 + VLM 外观匹配双层，且管家已确认单路上报原则；再引第三方人脸服务只会增加链路。

## 四、房间级在场定位（管家侧，跨项目建议）

### 4.1 ESPresense（ESPresense/ESPresense）⭐ 给管家的「直接抄」

ESP32 刷固件即成房间级 BLE 定位节点，MQTT 输出，HA 集成成熟（mqtt_room 每房一节点模式 / Companion 密集覆盖模式）。**管家 v1.5 P1-2 计划自研 ESP32 蓝牙扫描固件——建议直接用 ESPresense 固件替代自研**，省 2 天开发且更成熟。另有 Bermuda BLE Trilocation（HA 集成）可选。

### 4.2 room-assistant

BLE/WiFi 在场检测，活跃度已不及 ESPresense/Bermuda。**不推荐**。

## 五、学术参考

- **DISCOVER**（arXiv:2503.01733）：从智能家居传感器数据**无监督**挖掘个人日常模式——MA 洞察引擎是规则驱动，此文方法论可作为「记忆研究员」的算法组件（先聚类挖掘，再让 LLM 解释命名）。
- **OpenSHS 数据集**：带标注的智能家居活动数据集，若要评估 MA 活动推断准确率可用作基准。

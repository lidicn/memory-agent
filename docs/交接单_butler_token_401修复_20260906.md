# 交接单：butler_token 窄接口 401 未登录修复

> 发起方：豆包管家（doubao-butler）
> 接收方：memory-agent
> 日期：2026-09-06
> 优先级：P0
> 状态：已完成（已验证，MA 侧无需改动）

## 一、问题描述

memory-agent 的 butler_token 窄接口（Bearer 鉴权）当前返回 **401 未登录**，导致豆包管家无法获取成员在场、作息摘要等关键数据。

## 二、复现步骤

```bash
# butler 容器内已配置 MEMORY_AGENT_BUTLER_TOKEN（len=47）
TOKEN=$(docker exec doubao-butler printenv MEMORY_AGENT_BUTLER_TOKEN)

curl -s -w "\nHTTP=%{http_code}\n" \
  "http://192.168.2.200:8086/api/vision/presence?room=客厅&minutes=10" \
  -H "Authorization: Bearer $TOKEN"

# 返回：{"ok": false, "error": "未登录"}  HTTP=401
```

## 三、影响范围

butler 侧以下方法全部走 butler_token 窄接口，当前全部失败：

| butler 方法 | MA 端点 | 用途 |
|------------|---------|------|
| `get_members()` | GET /api/members | 成员列表（含 profile） |
| `get_member_profile(name)` | GET /api/members | 按名取成员画像 |
| `presence(room, minutes)` | GET /api/vision/presence | 最近 N 分钟在场成员 |
| `member_schedule(name, days)` | GET /api/insights/member-schedule | 作息实测摘要 |
| `update_member_profile(name, profile)` | PATCH /api/members/{id} | 画像写回 |
| `member_id_by_name(name)` | GET /api/members | 按名查 id |

**业务影响**：
- 决策层（v0.9）的"成员在场"当前只能从 butler 本地 `dialog_turns` 推断（极不准确，用户不说话就检测不到在场）
- 决策层无法获取用户作息习惯（如"通常 7 点起床"），导致"睡过头"类推理缺乏基线
- butler 的 profile 模块无法与 MA 同步成员画像

## 四、butler 侧代码位置

`butler/integrations/memory_agent.py`：
- `_butler_headers()`（L218）：使用 `self.s.memory_agent_butler_token`
- `_butler_get()`（L221）：GET 请求
- `_butler_patch()`（L274）：PATCH 请求
- 窄接口方法均调用上述两个底层方法

**MCP 通道正常**（`MEMORY_AGENT_TOKEN`），`list_memories`/`analyze_camera`/`add_memory`/`retrieve`/`ask_memory`/`revoke_memory` 可用。问题仅限 butler_token 的 REST 窄接口。

## 五、需要 memory-agent 完成的事项

1. **排查 butler_token 鉴权中间件**：确认 `MEMORY_AGENT_BUTLER_TOKEN` 是否在 MA 端配置/注册，Bearer 鉴权逻辑是否正确解析该 token
2. **确认窄接口白名单**：以下端点应允许 butler_token 访问（无需 session cookie）：
   - `GET /api/members`
   - `GET /api/vision/presence`
   - `GET /api/insights/member-schedule`
   - `PATCH /api/members/{id}`
3. **返回格式统一**：建议统一为 `{ok: true, data: {...}}` 或 `{ok: false, error: "..."}`，butler 侧已做 `_unwrap` 兼容
4. **验证**：修复后用上述 curl 命令验证，返回 200 + 成员数据

## 八、MA 侧处理记录（排查 + 验证）

**结论：MA 侧鉴权中间件与白名单实现正确，无需改动；原 401 系 butler 运行时容器缺少 `MEMORY_AGENT_BUTLER_TOKEN` 所致，现已与 MA 端令牌一致，所有窄接口验收通过。**

### 8.1 排查

1. **MA 端令牌配置正确**：`.env` 与运行容器 env 中 `BUTLER_TOKEN=btl_xmonyKUdtA9JDSOv0cQ9ch49720VbCJpa_SHEBtaBFQ` 一致。
2. **中间件逻辑正确**（`src/memory_agent/app.py` `AuthMiddleware`）：
   - `Bearer <tok>` → `_butler_matches()` 用 `secrets.compare_digest` 常量时间比对 `get_config().butler_token`，命中返回 `{butler:True}`；
   - 白名单 `_butler_allowed()` 覆盖 `GET /api/members`、`/api/vision/presence`、`/api/insights/member-schedule`，且 `PATCH /api/members/{id}` 经 `path.startswith("/api/members/")` 前缀放行。
3. **根因**：报障时 butler **运行容器**的 `MEMORY_AGENT_BUTLER_TOKEN` 为空（compose 第 43 行已写入该值，但运行中的容器是在该 env 加入 compose 之前创建、未重建，故 `printenv` 为空）→ butler 发出 `Authorization: Bearer `（空）→ MA 返回 401。
4. **当前状态**：butler 运行容器 env 已含正确令牌，且与 MA `BUTLER_TOKEN` 完全一致。

### 8.2 验证（直接对 `http://192.168.2.200:8086` 用该令牌实测）

| 请求 | 结果 |
|------|------|
| `GET /api/vision/presence?room=客厅&minutes=10` | **200** `{"ok":true,"room":"客厅","count":0,"items":[]}` |
| `GET /api/members` | **200** `{"ok":true,"members":[...],"total":3}` |
| `GET /api/insights/member-schedule?name=lidicn&days=14` | **200** `{"ok":true,"summary":{...}}` |
| `PATCH /api/members/{id}`（带令牌，空 body） | **400**「没有可更新的字段」→ 已通过鉴权中间件到达 handler，非 401/403 |
| `PATCH /api/members/{id}`（**不带**令牌） | **401**「未登录」→ 鉴权拒绝生效 |

> 注意：复现命令里 `room=客厅` 若以原始中文直接拼进 URL 会触发 HTTP 400（请求行含非 ASCII）。butler 代码经 httpx `params=` 自动编码，实测无碍。

### 8.3 返回格式兼容性

MA 窄接口实际返回为**扁平格式**（`{ok:true, items:[...]}` 而非 `{ok:true, data:{...}}`）。butler 侧 `MemoryAgentClient._unwrap()`（`butler/integrations/memory_agent.py`）已做 `data.get("data", data)` 兜底，两种格式均可解析，无需 MA 侧调整。

### 8.4 后续建议

- butler 侧若重建容器，务必基于**已含 `MEMORY_AGENT_BUTLER_TOKEN`** 的 `docker-compose.yml`（现第 43 行已就位）；否则会再次 401。
- MA 侧 `BUTLER_TOKEN` 与 butler 侧 `MEMORY_AGENT_BUTLER_TOKEN` 须保持同一值（当前 `btl_xmonyKUdtA9JDSOv0cQ9ch49720VbCJpa_SHEBtaBFQ`）。

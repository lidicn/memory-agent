# MA ↔ AF 联动契约 v1（草稿）

> 状态：**草稿 v0.1**，MA 席位起草 2026-11-17。待 ADM-链主评审 → DCD 裁定 → 冻结。
> ⛔ 非冻结版不得被落码方当依据；本文所有接口名/字段名为**提案**，不是现网读数。
> 依据：AF-PM 2026-11-17 三场景（晚间熄灯／离家检查／该判没判→候选规则）＋`doc/架构设计/MA能力面-供AF联动清单-v1.md`（提交 `2ffaa32`）＋ AF 侧技术坚持（门面入 MCP 工具面、不做裸 REST）。

---

## 一、范围

本契约只定两件事：

1. **门面工具**（AF→MA，走 MCP `/mcp`）：3 枚聚合工具，把"一个场景要的全部事实"一次取齐。
2. **事件族**（MA→AF，走 MQTT）：新增主题与其载荷版本化规则。

**不属本契约**：MA 现有 92 枚原子工具、199 条 HTTP 端点的既有语义与鉴权。AF 现有 `af_adapters/ma.py` 的直调路径不变、继续可用；门面是**加法**，不是替代。

**设计原则**：一次调用返回一个场景所需的全部事实，AF 不做 N 次编排。门面**不引入新模型**，全部是现有能力的组合查询。

## 二、门面与新读接口（4 枚，全部注册进 `/mcp`）

> 命名沿用 MA 现有 snake_case「动词_对象」风格，与 `get_behavior_prediction`／`list_candidate_rules` 一致。
> 2.1／2.2 只读；2.3 写向（出资人 2026-11-17 场景③定为**本版本一等件**，见 Q2 修订）；2.4 为**新读接口**（现无对外工具，需 DCD 一并裁，见 Q4）。

### 2.1 `get_automation_context`（读）— 场景 ①②

一次取齐「现在是什么状态、谁在不在、接下来会怎样、用户想干什么」。

| 项 | 内容 |
|---|---|
| 输入 | `room?`（房间名）、`member_id?`、`window_minutes=30`（回顾窗口） |
| 输出 | `as_of`、`behavior_state{state, confidence, since}`、`presence{in_home[], last_change}`、`prediction{next_arrival, upcoming_device_hints[]}`、`intent{name, confidence, factors[]}`、`data_quality{coverage, sufficient: bool}` |
| 数据来源（现有） | 行为状态机 `GET /api/behaviors`｜在场 `ma/presence` 缓存｜预测 `get_behavior_prediction`｜意图 `infer_behavior_intent`｜数据覆盖 `get_data_coverage` |
| 错误语义 | `DATA_INSUFFICIENT`：`data_quality.sufficient=false` 时返回 200 + 该码（⚠ 不抛 5xx，AF 要能拿到"数据不够"这个事实去做降级）；`UPSTREAM_TIMEOUT` 沿用 AF 侧既有 `ADM_ERR_UPSTREAM_TIMEOUT` |
| 超时预算 | ≤ 8s（内部四源并发取数） |

**AF 用法**：晚间熄灯检查＝`behavior_state=已入睡` ＋ `presence.in_home` 含成员；离家检查＝`presence.last_change` 是末人离场边沿。草稿可带上 `prediction`/`intent` 作为**依据**（用户审批时看得懂"为什么现在做这件事"）。

### 2.2 `get_automation_opportunities`（读）— 场景 ③

一次取齐「MA 说缺什么自动化、数据够不够、有哪些现成候选」。

| 项 | 内容 |
|---|---|
| 输入 | `room?`、`top_k=10`、`min_samples=5` |
| 输出 | `as_of`、`gaps[{kind, description, evidence[], sample_count, suggested_trigger}]`、`candidates[{rule_id, description, confidence, evidence[], confirm_state}]`、`data_gate{coverage, blocked_reasons[]}` |
| 数据来源（现有） | 召回缺口 `audit_rule_recall`／`refresh_rule_recall_gaps`｜候选规则 `list_candidate_rules`｜数据覆盖 `get_data_coverage` |
| 硬语义 | `candidates[].confirm_state=needs_confirm` 的条目 **⛔ 视为生效**；AF 只能拿去起草 IR，⛔ 直接落库 |

**AF 用法**：AF 不再"凭空编规则"，而是从"MA 说这里缺一条、样本 N 条、数据覆盖够"出发 → `af_draft` 起 IR → 用户 WebUI 审批。

### 2.3 `report_automation_outcome`（写）— 场景 ③：MA 作为自动化的**最终结果**

| 项 | 内容 |
|---|---|
| 输入 | `rule_ref`、`outcome`（`asked`／`executed`／`skipped`／`failed`／`false_positive`）、`at`、`automation_decision`（AF 这次做了什么：开/关/询问）、`user_response?`{`choice`：`accepted`／`declined`／`modified`／`no_response`、`value?`、`at`、`via`：`voice`／`bark`／`webui`}、`context_ref?`（源自哪一次 `get_automation_context` 的 `as_of`/`event_id`）、`evidence{}`、`note?` |
| 输出 | `memory_id`、`staging: true` |
| 语义 | 写 MA 的 **staging** 记忆面（`add_semantic_memory`＋`feedback_memory` 封装）；⛔ 直接晋升；晋升按 MA 现有条件走。**必须能记录「用户的选择」**（出资人场景③原文：「最终调用 ma 记录下用户的选择」），`user_response` 是核心字段，不是可选备注。 |
| 权限 | 属写工具：须进 `mcp_scopes.py:94` `WRITE_TOOLS`；漏登记由 `assert_write_tools_complete()` 启动期记 error |

**AF 用法**：AF 执行后把「决定了什么＋用户怎么回的」回流，MA 下次生成草稿时能检索到"这条自动化上次效果如何 / 用户当时接受了吗"。

### 2.4 `get_member_habits`（读·新接口）— 场景 ④：历史依据

> 现状：跨周/周期性习惯目前只有内部 `activity.infer_habits`（日任务），**无对外工具**（能力面清单 §3.5＝△）。出资人场景④「你这周这个时候都开空调了」正是这类查询 ⇒ 不补此枚，④层缺件。

| 项 | 内容 |
|---|---|
| 输入 | `member_id?`、`room?`、`entity?`、`granularity=week`、`weeks=4` |
| 输出 | `as_of`、`habits[{pattern, entity/room, typical_time_window, frequency, stability(0-1), sample_weeks, evidence_refs[]}]` |
| 数据来源 | 现有 `activity.infer_habits` 结果（跨周习惯）＋ 事件检索补样本计数 |
| 错误语义 | `DATA_INSUFFICIENT` 同 2.1；`stability` 低时 AF 应降级为"参考"而非"依据" |
| 说明 | 只读、无新模型；是把内部能力**暴露成对外工具**，不是新增算法 |

### 2.5 条件面的新鲜度约定（横向规则，适用所有读工具）

出资人场景 ①② 把 MA 查询当 AF DSL 的**条件**用，最硬的设计点是**新鲜度**：条件若基于陈旧数据，会在"事实已经变了"之后误触发。契约约定：

- 每个读返回**必带 `as_of`**（本条数据的采集/计算时刻）与 `stale_after_s`（该数据该类查询的建议最大陈旧秒数）。
- 契约给建议阈值：实时条件（在场/状态）≤ 120s；预测/意图 ≤ 900s；习惯/机会类 ≤ 3600s。AF 侧超阈值即**不采信该条件**（走降级或重新取数），⛔ 带病触发。
- 阈值最终值由 AF 依 DSL 条件预算定，本契约给的是**默认取值＋回退口径**，AF 可收紧不可放宽。

## 三、事件族（MA → AF，MQTT）

**现网已有三条**（连字符风格）：`ma/presence`、`ma/device-health`、`ma/insights`。

**建议新增两条**：

| 主题 | 触发 | 载荷要点 | 频率 |
|---|---|---|---|
| `ma/behavior-state` | 行为状态机 `state` **变更边沿**（不是周期心跳） | `as_of`、`state`、`confidence`、`member?`、`room?` | 低频、边沿 |
| `ma/prediction` | 预测值跨阈值才发（如 `next_arrival` 漂移 > 15min） | `next_arrival`、`upcoming_device_hints[]`、`as_of` | 建议 15–30 分钟一轮，或跨阈值 |

可选二期：`ma/anomaly`（漂移/异常）。理由：场景 ①②③ 全靠 `behavior-state`＋`prediction`，异常族不是首版阻塞。

**公共信封字段**（所有事件族统一，含现网三条的下一版本）：

```
{ "type": "...", "source": "ma", "payload_version": "1.0",
  "event_id": "...", "trace_id": "...",
  "ts": "<家庭墙钟带偏移>", "emitted_at": "<UTC 采集时刻>" }
```

**兼容规则**：加字段＝minor（AF 忽略未知键）；删字段/改语义＝major，须新旧主题双发期（≥ N 天，N 由链主定）后再下线。

> **Q1（链主 2026-11-17 评审订正后口径＝统一连字符，三问已投 DCD）**：现网三条 `ma/presence`／`ma/device-health`／`ma/insights` 全为连字符，homesdk 契约表 §1.2 即此真源；`/` 是 MQTT 层级分隔，同层用 `-` 连词是现网既有风格，点号＝在同层混插第二种风格，还须动现网三条改名＋三仓订阅/白名单，零收益。
> 订正（测量方核）：AF 桥为**精确字面匹配**（`LINKAGE_KIND_BY_TOPIC` 字典逐字 → `ingest_linkage`），⛔ 不存在"分词解析分支"问题；命名单一的真实价值在**风格一致与跨仓 grep/白名单/契约单一口径**，不在运行时。结论不变。

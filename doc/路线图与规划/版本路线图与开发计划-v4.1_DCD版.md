## 〇、与 v4.0 的关键差异

1. **隐私修正**：召回 API 的 member_id 过滤是 **fail-open**（空 member_id 返回全部成员），必须改 fail-closed——这是接入下游前的硬前置（裁定 1）。
2. **新增 vMA-1.1.1 工程卫生版**：308 个 tmp_* 文件、git ahead 12 未推送、mem0 探索已放弃需正式收口（裁定 6）。
3. **vMA-1.2.0 场景图三处瘦身**：不建新表、场景图输出设开关+采样、意图推断降级到 1.2.1（裁定 3）。
4. **屎山策略转向**：放弃"全部迁移"幻想，改"入口切换 + 冻结"（裁定 5）。
5. **SQLite 启动诊断修正**：不是 WAL/预热问题，是 init_schema 同步 DDL，改版本门控迁移（裁定 4）。
6. **vMA-2.0 知识图谱默认不做**，须先交 badcase 集（裁定 8）。
7. 每版挂决策门。

## 三、跨项目前置（给 DB 的通知）

DB 路线图 v2.6 的"记忆召回自建走 MA 召回 API"依赖两个前置：

1. **MA vMA-1.2.2 必须先行**（member_id fail-closed + schema 版本 + 召回基线）——否则 DB 接的是 fail-open 的召回，读得到全家记忆；

建议两仓对齐节奏：DB v2.4.x 期间，MA 先做 vMA-1.1.1 + 1.2.2（2-3 天），DB 到 v2.6 时 MA 召回已加固完成。

## 四、贯穿纪律（沿用 v4.0 + DCD 增补）

1. **文档数字必须为真**：MCP 工具数（49 非 65+）、屎山规模（84 方法非 27）这类数字先核实再写，数字失真会误导下游（裁定 2）；
2. **诊断要先于处方**：TD-3"评估 WAL + 预热脚本"是未核实代码就给的建议，实际 WAL 已开、预热已后台化。今后所有性能/架构判断必须先 file:line 核实再给方案（裁定 4 的教训）；
3. **fail-open 的安全面 = 缺陷**：凡涉及成员/数据的过滤默认 fail-closed（裁定 1）；
4. **弃用项要正式收口**：mem0 放弃必须写进 CHANGELOG，不能靠"没提交"暗示（裁定 6）；
5. **决策门过不过都是成果**：vMA-2.0 默认不做是合法裁定，不是失败。

## 五、一页总结

- **v4.0 质量最高，DCD 不推翻主线**：场景图方向经核实可行，只是瘦身三处。
- **最高优先不是场景图，是隐私修复**：召回 API fail-open 是隐私缺口，且 DB v2.6 就要接入它——vMA-1.2.2 召回加固是两仓的前置。
- **先做 1.1.1 工程卫生**：git 收口 + 308 个 tmp 清理 + mem0 正式收口，1-1.5 天。
- **五处自述修正**：工具数、屎山规模、SQLite 诊断、报告文件位置、WAL 建议，全有源码证据。
- **两个"远期"被挂了硬门**：1.3 过 PoC、1.4 过灰度；2.0 默认不做，先交 badcase 集。

## 七、ADM 联动篇（DCD 2026-09-29 增补）

> 依据：`decisions/20260929-ADM三仓联动七问-裁定.md` + `20260929-ADM协议选型MCP与ACP-裁定.md`
> MA 角色：**记忆中枢（数据权威）**——全生态的记忆、成员、行为事实唯一真源。最成熟的一仓，是当前联动的可靠锚点。

### 7.1 MA 的联动现状（实测）

- DB→MA：最密集通道（MCP + vision REST + butler 窄接口 + app_token 四路）；
- MA→DB：MQTT 单向推 `ma/presence`、`ma/device-health`，另有**越权直推 `butler/trigger/gu_anheng_alert`**（违规，见下）；
- MA→AF：`acp_client.py` 委派给 autoflow（自研 ACP，非业界标准）；
- MA 对外 MCP server：49 工具，生产级。

### 7.2 MA 的联动档位

| 档 | 联动功能 | 就绪门槛 | 说明 |
|----|---------|---------|------|
| 一（加固） | **token 合并设计**：配合 DB→MA 四路收敛，合并 butler_token/app_token，MA 侧鉴权面收口 | MA vMA-1.2.2（召回加固内） | 与 DB v2.6 同步 |
| 一（加固） | **越权清理**：`butler/trigger/*` 直推改为规范主题（各仓只推自己域名） | MA vMA-1.2.2 | 违规定裁：`ma/*` 归 MA |
| 一（加固） | MCP 查询工具面补全（供 DB 查"空调时长""净水器出水量"等业务洞察） | MA vMA-1.2.2 后 | 复用既有模板引擎 |
| 二（价值） | **MA 行为洞察 → AF 联动自动化**（例：净水器出水少 → 生成"提醒喝水"自动化提案） | AF v2.3.0 + MA vMA-1.2.2 | MA 侧只需出洞察（现成），AF 侧消费 |
| 三（挂门） | 语义委派 ACP（建议/叙事类，四条件+四禁止） | 联动稳定后 | 现状 MA→autoflow 委派按规范自查 |

### 7.3 越权修正 + 收件箱（联动前置，DCD 2026-09-29 修订）

MA 直推 `butler/trigger/gu_anheng_alert` 违反"各仓只推自己域名主题"。修订：改为投递 DB 的**公共收件箱** `butler/inbox/notify`（DB 显式开放、ACL+schema+限流兜底），或发布 MA 自己的 `ma/insights` 事件（不 retained，DB 订阅）。**基础能力（TTS/通知/TV 上屏）下放 MQTT，走收件箱模式**；行为洞察模板留 MCP（查询语义），模板产出走 MQTT 事件。

### 7.4 记忆召回 fail-closed（联动安全前提）

MA 的 `retrieve_agent_memories` / `list_agent_memories` 是 fail-closed（member_id 缺失拒查）。联动时 DB 调用必须显式传 member_id，不得依赖"MA 天然可读"——这是 MA 隐私红线，联动接入时保持。

## 三、arena 分析闭环设计（任务 1，已交付）

### 3.1 数据基础

`arena_results` 表（AutoFlow 竞技场对接已建）已逐条记录：
`insight_id, arena_id, agent_id, task_title, task_description, flow_dsl, success(0/1), token_used(int), used_memory_tools(JSON 列表), created_at`。

`used_memory_tools` 即「该 Agent 提交时是否调用了 MA 记忆 / 洞察工具」——天然分 cohort 的依据。

### 3.2 聚合语义

`store.get_arena_analytics(arena_id=None, limit_recent=20)`：
- `with_memory` / `without_memory`：按 `len(used_memory_tools) > 0` 二分；各给 `count / success_count / success_rate / avg_token / total_token`。
- `by_arena` / `by_agent`：分组统计（各组再分 with/without memory 的成功率与 token）。
- `recent`：最近 N 条明细（insight_id / arena / agent / 任务 / 是否用洞察 / token / 成功）。

`GET /api/arena/analytics`（arena_routes.get_analytics）：仅管理员 JWT 可访问（**不在** `ARENA_ENDPOINTS` 白名单，故 `arena_` 令牌访问会被 403 拦截，与生产 / butler 令牌隔离）。

WebUI：定向洞察页新增「竞技场闭环分析」卡片（双卡 cohort 对比 + 最近提交表），`api.arenaAnalytics()` 拉取。

### 3.3 验收门

- 单测 `tests/test_arena_analytics.py`：cohort 划分 / 成功率与平均 token / by_arena·by_agent 分组 / arena_id 过滤，全过。
- 容器内端到端：注入 with/without memory 两条结果 → `GET /api/arena/analytics` 返回正确 cohort 对比；未登录 401、arena 令牌 403。

## 四、HA Assist 集成（任务 2，✅ 已交付 MA 侧）

**实现**：MA 暴露 OpenAI 兼容的 `POST /v1/chat/completions` + `GET /v1/models`
（`api/ha_assist_routes.py` + `ha_assist.py`）。回答时用 `agent_memories.retrieve`
取相关记忆拼进 system prompt，再交 LLM 回答（`ha_assist_memory_top_k` 控制条数）。
鉴权用独立 `ha_assist_token`（app.py `HA_ENDPOINTS` 放行 `/v1/*`，路由层自校验；
未配置则 401）。支持 `stream=true` 的 SSE 分块。

**取舍**：MA 仅做「记忆增强问答」，不做 HA 设备控制（tool calling）；MA 不做实时 HA
查询（见路线图 §五 数据流决策）；身份 / 实时反应仍归管家与 HA。

**HA 侧配置**：HACS `extended_openai_conversation`，`base_url` 指向
`http://192.168.2.200:8086/v1`，`api_key` = `ha_assist_token`，`model` = `ma-family`。
详见 `docs/HA_Assist接入.md`。

**验收**：容器内 HTTP —— 缺/错令牌 401、`/v1/models` 200、`POST /v1/chat/completions`
200（返回带家庭记忆的回答）、`stream=true` SSE 200；单测 `tests/test_ha_assist.py` 4 项通过。

> 附带修复：线上 `new-api` LLM 后端密钥失效（401 Invalid token），已更新为有效
> memory-agent 令牌（config 备份 `data/config.json.bak.llmkey`）。

## 五、活动推断基准评估（任务 3，🟡 进行中）

### 5.1 思路

用 OpenSHS 公开标注数据集（宽表：29 个 0/1 传感器列 + `Activity` 标签 + 每秒时间戳）给
`infer_activities` 一个**可量化基线**：把标注事件流喂进 MA 的活动推断，再与 OpenSHS 标签对比，
按「天 × 活动」做二分类，输出 precision / recall / F1。

### 5.2 已交付（2026-09-16，本机 + 容器内可跑）

- `benchmarks/openshs_schema.py`：29 个 OpenSHS 传感器列 → MA 实体 / 房间 / 标签的映射
  （entity_id 故意带 `_TAG_RULES` 识别的子串，故**空 name_map 也能正确打标**）；
  OpenSHS 活动标签 → MA 活动名的映射（sleep→sleeping、cook→cooking、watchTV→watching_tv、
  work→working、bathe/useToilet→bathing、leaveHouse→away）。
- `benchmarks/openshs_convert.py`：**边沿触发**宽表→长表转换（只在该传感器 0/1 变化时产事件，
  吻合 HA 状态变化日志语义，避免海量重复事件破坏「静默间隔」检测）+ 真值（ground truth）抽取。
- `benchmarks/gen_sample.py`：生成一份自包含的多活动样本（宽表 CSV），让基准可离线、可复现运行，
  不依赖外网下载。
- `benchmarks/openshs_bench.py`：加载 CSV → 内存 `Store` → `infer_activities` → 与真值对比打分，
  输出基线报告（`python -m benchmarks.openshs_bench`）。
- `tests/test_openshs_bench.py`：转换器 / 映射 / 端到端单测，5 项全过。

### 5.3 关键发现

- MA 的 `infer_activities` 纯事件逻辑、不依赖 chroma/LLM，可在本机直接跑（FTS5 在本地 sqlite 可用）。
- MA **睡眠检测基于「无家电/门/电脑操作的静默间隔」**，且静默括号两端都必须是 active(on) 跳变；
  若 OpenSHS 睡眠段只有 presence/light 信号、缺少「醒时开门/开灯」这类 on 锚点，则睡眠召回会偏低。
  这是真实的基线局限，需在拿到真实多日数据集后量化，并可作为后续改进项（如引入「关灯=入睡」软锚）。

### 5.4 待办

- 在 NAS（可外网）下载完整 OpenSHS 数据集（多日、含更多活动），放到任意路径后
  `python -m benchmarks.openshs_bench --csv <path>` 替换样本，跑出真实多日基线。
- 把基线报告沉淀进 `docs/` 作为 v1.0 活动识别能力的量化证明。

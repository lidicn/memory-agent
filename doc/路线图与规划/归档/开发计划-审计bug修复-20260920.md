**风险**：中（加索引需迁移，审计异步改架构）

- `store.py:2019`、`:2076`：在场热查询只有 `idx_be_day_room`，缺 `(server_ts)` 和 `(room, server_ts)` 索引
- `mcp_server.py:662-677`、`:896-898`：每个工具调用后 `INSERT audit` + `commit` 直接在事件循环上

   - 工具调用后只 enqueue，不等待 commit
4. 进程退出时 flush 队列（graceful shutdown）

**涉及文件**：
- `src/memory_agent/store.py`（索引迁移）
- `src/memory_agent/mcp_server.py`（审计异步化）

- 进程退出时审计记录不丢（graceful flush）

**验收标准**：

## 二、投产后架构性优化（2 项 P1）

### 10. P1-3：_lock 只保护连接创建，不保护 execute/commit

**日期**：09-30 ~ 10-01（2.5 天）
**预估**：2.5 天
**风险**：高（全局改 store 锁策略，影响所有数据操作）

**问题**：
- `store.py:9` docstring 声称「单连接 + RLock」，但 15+ 方法违反
- `_lock` 只保护连接创建，不保护 execute/commit
- 共享连接 `check_same_thread=False` → 并发 execute 抛异常/事务互踩
- 幂等键 check-then-write 无锁 → 竞态 → 重复写入

**修复方案**（二选一，评估后决定）：
- **方案 A**：每线程一连接（`threading.local`）+ WAL + `busy_timeout`
  - 优点：并发性能好，不需要全局锁
  - 缺点：连接管理复杂，事务语义需仔细处理
- **方案 B**：把 `_lock` 包到所有 execute/commit（全局锁）
  - 优点：简单，正确性容易保证
  - 缺点：并发性能差（写操作串行化）
- 幂等改 `INSERT ... ON CONFLICT DO NOTHING` 由 DB 保证
- docstring 与实现对齐

**涉及文件**：
- `src/memory_agent/store.py`（全局）

**测试计划**：
- 并发写入不抛异常
- 幂等键不重复写入
- 事务不互踩
- 性能基准：并发读/写延迟

**验收标准**：
- 所有 execute/commit 在锁保护下（或每线程独立连接）
- 并发测试通过，无异常/无重复
- docstring 与实现一致

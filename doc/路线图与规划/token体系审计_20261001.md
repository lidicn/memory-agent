# MA 侧 token 体系审计表（路线图 3.3.1，2026-10-01）

> 范围：memory-agent（MA）服务内五套 token/鉴权体系的签发点、校验点、承载端点、
> scope/权限模型、过期机制与调用方。本表只做审计与改动面盘点，**不含任何实现**；
> 「butler + app → service_token 合并」在末尾单列，等 DCD 裁决。
>
> 行号基于 worktree 审计当日的代码（与主线可能有数行漂移，锚点以函数名为准）。

## 六、审计发现（现状问题清单）

1. **F-1 双实现漂移**：butler 走「config 明文 + 全局中间件比对」，app 走「哈希多令牌 store + 全局中间件比对」，同属"外部服务窄白名单令牌"却是两套代码（`app.py:264-284`）。
2. **F-2 app 白名单不分方法**：`_app_allowed` 仅查路径（`app.py:259-261`），butler 有 GET/POST/PATCH 方法级细分（审计 P0-3 未覆盖 app）。
3. **F-3 无过期/轮换机制**：butler/app/mcp/acp/arena 均无 TTL；仅靠人工吊销。butler 连吊销 API 都没有。
4. **F-4 审计粒度不均**：mcp 有逐调用审计（`log_mcp_audit`），butler/app/arena 只有 `last_used_at/use_count`（butler 连这个都没有）。
5. **F-5 arena 签发缺口**：kind=arena 只能手工编辑 config.json 产生，无 WebUI/接口通道（无审计、易出错）。
6. **F-6 令牌共享存储**：mcp/acp/arena/debug 同表 `agent_tokens`，靠 `kind` 字段做身份隔离——隔离在代码约定而非数据结构，kind 写错即跨面（如 `mcp_auth.py:101-106`、`acp_auth.py:52`、`app.py:309-317` 三处各自判定）。
7. **F-7 校验顺序**：`_authenticate` 中 Bearer 依次尝试 butler→app→JWT→arena→debug；明文静态密钥（butler）优先级最高，JWT 用户若恰好持同名串（不可能——butler 比对的是全局 config），实际风险为「一把静态密钥泄露 = 管家面全开」且无法按实例吊销。

### 7.5 合并前必须先裁决的点
1. 白名单粒度：**令牌级携带路径/方法清单**（灵活，F-2 根治） vs 维持代码常量按 name 映射（改动最小）。
2. butler 单密钥 → 多实例：是否需要「一把令牌对应多个管家实例」的过渡兼容（建议直接一实例一令牌，配合 env 迁移自动生成首个）。
3. 过期/轮换是否纳入本次合并（F-3）：若纳入，需在 `verify` 增加 `expires_at` 判定并影响全部 7.1-7.3 位置。
4. `source` 派生（记忆来源防伪）语义是否在 service_token 下原样保留（7.3 第 2 行，建议保留）。

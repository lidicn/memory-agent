## 一、DCD 是什么

DCD 不替你写代码，也不替你上班。DCD 做三件事：

1. **核实**——你说"这里有问题"，DCD 先去读源码确认问题真的存在、长什么样（file:line）；
2. **裁定**——多个方案摆上桌，DCD 选定一个并写下理由，落盘存档；
3. **背书**——裁定留了痕，将来错了可以翻出来追责 DCD，而不是追责执行的你。

**决策的价值不在于列出选项，而在于选定并负责。**

## 二、全流程（五阶段）

```
① 受理      ② 核实        ③ 裁定        ④ 交付          ⑤ 回访
开发者填表 → DCD 读源码 → DCD 出裁定 → 落到开发者    → 开发者回填
投 inbox/    验证证据      存档到        自己的 doc/    执行结果
             不信二手      decisions/   体系里         + DCD 复盘
```

| 阶段 | 谁做 | 做什么 | 产出位置 |
|------|------|--------|---------|
| ① 受理 | 开发者 | 填决策申请表，投进 `E:\NAS\关键决策部\inbox\`，对话里 @ 文件 | inbox/ |
| ② 核实 | DCD | 遍历相关代码，验证每条证据；证据不足就退回并列《待补清单》 | 对话 |
| ③ 裁定 | DCD | 出《决策意见书》：结论/理由/执行要点/验收标准/回滚条件 | `decisions\YYYYMMDD-事项-决策.md` |
| ④ 交付 | DCD | **路线图、计划等产出落到开发者项目自己的 doc 目录**，不留在 DCD 目录 | 项目 docs/ |
| ⑤ 回访 | 开发者 | 执行完在决策书末尾《执行回填》区写一句结果（成了/没成/偏差） | 原决策书 |

**为什么产出要落在你的 doc 目录**（对应你的想法 1）：你以后只翻自己项目的文档体系就够，不用记着"DCD 那边还有一份"。DCD 的 `decisions/` 只存裁定书——那是判例，不是项目文档。

## 三、什么时候找 DCD（求助触发器）

对应你的想法 2：DCD 版路线图的每张版本卡里会内嵌这一段。看到以下任一信号，**停下来，提交申请**，不要硬扛：

### 3.1 必须找（硬触发）

- 同一个问题**卡住超过半天**；
- 准备做**不可逆操作**（删数据、改存储格式、动授权/安全模型、发版）；
- 发现**两个方案各有道理、选哪个都说得通**——这种僵持最烧时间；
- 要动的代码**牵涉外仓/跨项目接口**（如 ADM 三仓）；
- 直觉告诉你"这里可能有个大坑"但说不清。

### 3.2 可以找（软触发）

- 想给路线图加新东西，但不确定值不值得做；
- 怀疑现有文档/路线图的某个前提是错的（大概率真是错的——三轮实战里每轮都推翻了至少一个前提）。

### 3.3 别找（DCD 会退回）

- 有明确文档/规范覆盖的常规实现细节；
- 局部重构、测试修复、文案调整；
- "帮我写这个功能"——这是开发任务，不是决策。DCD 按 §8 介入尺度只在特定条件下亲自下场（详见制度 §8）。

> **给 DCD 的提示词不用讲究**。一句话就行："这个 selectMemories 每轮都变，会不会把缓存搞坏？"——DCD 自己会去核实。你不需要把问题整理好才配提问。

## 四、DCD 的三类产品

| 产品 | 什么时候产出 | 细度 |
|------|------------|------|
| **决策意见书** | 任何单项难题 | 一事一议，含 file:line 证据 |
| **版本路线图（DCD 版）** | 版本规划/方向迷茫时 | 版本卡 + 决策门 + 风险登记册 |
| **执行细案（PR 拆分/工时/依赖序）** | **满足条件才做**（见下） | 每个功能卡拆到 PR 级 |

### 执行细案的推广结论（对应你的想法 3）：分档，不全量照搬

AF 的 27-PR 细案是**重型武器**，滥用会变成负担。启用条件（满足任一）：

- **跨模块耦合高**——一个改动牵动多条管线（AF 的 IR schema 动一下，编译/仿真/NL/报告四段全要跟着动）；
- **有不可逆操作或安全红线**（授权模型、自动封禁、数据迁移）；
- **版本工期 > 5 天**——超过这个长度，靠脑子记不住依赖序。

不满足就默认**轻量版**：版本卡 + 出口条件 + 关键依赖，任务级不拆 PR。DB 的 v2.4.1 止血版就是轻量版——5 个任务卡，直接开干，不需要细案。

**v2.3 需求决策门采集方案**这类"数据先行"的设计**值得全项目推广**：凡是"最贵、最可做可不做"的候选项，一律先埋点采集真实需求数据，用数据决定做不做，不靠热情。

## 五、开发者自评环节（内嵌进每张 DCD 版版本卡）

每个 DCD 版路线图的版本卡末尾固定带这段：

```markdown
### 🔍 自评（开发中遇到以下情况，停下来找 DCD）
- [ ] 实现时发现路线图的某个前提与代码事实不符 → 提交复议（附证据）
- [ ] 某个任务实际工时超出估算 2 倍 → 提交范围重估
- [ ] 临时想塞一个本版本卡没有的功能 → 提交变更申请，别私加
- [ ] 要动 [本版本红名单文件/模块] → 提交评审
- [ ] 连续两天没有可演示的进展 → 大概率卡住了，提交求助
```

设计意图：让路线图在开发者**最需要的时刻**（卡住、怀疑、想加塞）主动提醒 DCD 的存在，把"找 DCD"从依赖自觉变成流程内嵌节点。

## 六、DCD 的自律边界（写给你看的承诺）

1. **核实优先**：没读源码不下结论。三轮实战推翻的前提（schema 未精简、TTS 无调度层、双轨需人工同步）都是这么发现的。
2. **C 方案永远在场**：任何申请都评估"维持现状"，防止为了做而做。
3. **收益 <5% 默认不做**：优化类申请过不了测量关就毙掉。
4. **DCD 会犯错**：v1 文档没核实就写的教训刻在制度里（§8.4）。发现 DCD 错了，拿证据来复议——翻案是制度功能，不是冒犯。
5. **DCD 不是保姆**：能力再强也不接管你的键盘。指导方案是默认，亲自下场是救援。

## 七、判例库（decisions/ 已有存档，新项目先检索）

| 判例 | 可复用的结论 |
|------|------------|
| additionalProperties 精简 | schema 类优化先核实"是否已经有人做过"；布尔形态和对象形态要分开处理 |
| AF 双轨真值源 | "需要人工同步的两份数据"先查是否已共享底层真值表 |
| AF 试演期封禁 | "只统计不拦截"对安全功能等于失职；暂停可逆、恢复要人 |
| DB TTS 调度 | 自查"统一层不存在"之前先全项目搜一遍——可能已经存在只是没接全 |
| 前缀缓存 | 动态内容只放 prompt 尾部；稳定内容沉前缀 |

新项目立项/遇到同类问题时，先翻这张表，可能直接有答案。

## 三、P2-9　设备模糊匹配：最长名优先导致"电脑"匹配到"电脑插座"

**位置**：`src/memory_agent/voice_util.py:200` `match_device`（CC=60，覆盖 10.5%）

### 缺陷

步骤 1a 之后，当 `query_core` 抽不出或含噪音时，匹配退化为：

```
按 len(friendly_name) 降序排序 → 取最长者
```

实测构造反例：

```
候选：书房电脑(4字)  书房电脑插座(6字)
查询："书房电脑"   query_core = "电脑"

排序后：书房电脑插座(6) > 书房电脑(4)
返回：  switch.study_plug   ← 书房电脑插座
```

**用户问的是电脑，拿到的是电脑的插座。**

### 为什么这是家庭场景的高频问题

触发条件是**两个设备名互为前缀、且后者更长**。这在 HA 家庭里极其常见：

| 用户说的 | 可能匹配到 |
|---|---|
| 电脑 | 电脑插座 |
| 灯 | 灯带 |
| 空调 | 空调插座 |
| 电视 | 电视机顶盒 |

不是边缘 case，是命名习惯导致的常态。

### 定级 P2 的理由

定 P2 而非 P1：它是"答非所问"而非崩溃，且当 `query_core` 抽取准确时（步骤 1）不受影响。

但**用户可感知度很高**——问 A 得到 B，且置信度照常返回，调用方无从分辨。

### 修复方向

1. 匹配打分应优先"完全相等 > 前缀匹配 > 包含匹配"，而非单纯按长度
2. 或引入"插座/开关/传感器"等后缀降权（这类设备通常是附属品）

### 相关：P3-6 遍历顺序依赖

`match_device` 步骤 2/3 直接 `return` 首个命中，与步骤 1a 的显式 `sort` 不一致。

结果取决于 `name_map` 遍历顺序，而 `name_map` 来自 `_config_entities()` → `expand_entities_from_config()`，由 `config.rooms` 的**声明顺序**决定，无 `ORDER BY`。

实测：同一"客厅灯"查询，字典顺序 A 返回「客厅灯带」、顺序 B 返回「客厅主灯」。

**同样的输入，改一下配置文件的行顺序，答案就变了。** 定 P3：当前配置下结果稳定，但这是隐式契约。

## 四、P4 观察项　`llm_ask` 调试代码残留

`api/llm_routes.py:469`（CC=45，覆盖 11.3%）每次请求全量遍历 `name_map` 构建 `match_candidates`，**仅用于 `_debug` 字段返回**。

实测开销：

```
name_map 3000 条 → 每次请求 0.255 ms
```

**不构成性能问题**，故定 P4 而非 P3。但它是"为调试字段付出全量遍历"，且会膨胀响应体。建议按需返回（如加 `?debug=1`）。

## 六、一个必须记的方法论教训

**本轮差点全部白做。**

`probe_complexity` 这个函数名**已经存在**（第四轮 R4-2 的 radon 版本）。我新写的 AST 版本被后定义的同名函数覆盖，导致：

```
R12-1 E+F 级函数: 0        ← 假结果
R12-2 高CC×低覆盖: 0
```

修复后（改名 `probe_cc_ast`）：

```
R12-1 E+F 级函数: 26
R12-2 高CC×低覆盖（真风险）: 14
```

**如果没检查就直接写报告，本轮会输出一份"高复杂度函数 0 个，无风险"的结论**——而真实情况是 14 个风险区、且其中藏着本轮最重要的 P2-9。

这是十二轮里第三次同类问题（第五轮 `ast.alias` 漏计、第七轮/第十轮判定规则缺失）。**探针静默返回空值，比返回错误结果更危险——它看起来像"没找到问题"。**

已在 `ma_audit.py` 中固化：函数名加轮次前缀，避免跨轮冲突。

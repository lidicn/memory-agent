## 三、修正第一轮的一个定性错误

**第一轮报告**（图谱分析）写的是：

> `insights_legacy` 仍被 `insights` 调用 17 个目标、自身内部 15 个，**两条实现并存且互相调用**。这是**结构性不一致风险**。

本轮查证后这个定性不准确。实际情况：

```
外部调用方  ──►  insights 新包（InsightService，55 个方法）
                     │
                     ├─ 自己实现：39 个
                     └─ 委托 self.legacy.*：16 个方法
                              │
                              └─► insights_legacy（InsightService）
```

**证据**：
- `runtime.py:72` 只有 `self.insights = InsightService(...)`（新包），**无 legacy 实例**
- 全项目仅 `insights/api.py` 三处 import legacy（121、189、348 行），**无外部直接调用**
- `insights/api.py` 内部 16 处 `self.legacy.*` 委托

所以它是**单向的门面-委托分层**，不是双向并行。第一轮看到的"17 个目标被 insights 调用"正是这 16 个委托。

**这个修正很重要**：如果是双向并行，同一查询走不同轨会返回不同结果，是 P1 级风险；如果是单向委托，调用方只经过门面，口径由门面统一，风险等级完全不同。

## 四、18 个签名差异 / 1 个返回键差异：逐项证伪

### 返回键差异（唯一一处，重点核查）

`get_last_event`：

| 轨 | 返回结构 |
|---|---|
| 新 `insights/api.py:329` | `{"event": {...}, "total": 1, "offset": 0, "limit": 1, "has_more": False}` — 分页信封 |
| `insights_legacy:3228` | `{"ok": True, "entity_id": ..., "friendly_name": ..., "ts": ..., "old_state": ..., "new_state": ..., "transition": ...}` — 扁平业务字段 |

**判定：非缺陷。**

理由：新包的 `get_last_event` **不委托 legacy**——它走 `self.core.load_events()` + `sort()` + `events[-1]` 自己实现，返回分页信封。而 legacy 版本**只被新包内部委托的 16 个方法之外的路径使用**。

外部调用方（`mcp_server.py:2017`、`tool_schema.py:909`）统一走 `rt.insights.get_last_event`，**只会拿到新轨的分页信封**。不存在"同一调用有时拿 A 形状有时拿 B 形状"的情况。

legacy 的扁平版是 [FROZEN-LEGACY] 标记的历史形状，保留给内部兼容用。

### 18 个签名差异

集中于 `_count_by_filter`、`_iter_all_events`、`_rhythm`、`_tags_of`、`_usage_by_attr`、`_usage_one`、`anomaly_report`、`behavior_insights`、`data_quality_issues`、`define_activity` 等。

**判定：非缺陷。** 两类原因：
1. 新包方法带 `self` 之外的额外参数（如注入的 `repository`/`resolver`），是重构引入的依赖注入，非接口变更
2. 私有方法（`_` 开头）本就不是对外契约，签名不同属正常重构

`__init__` 的差异是因为比对把 `ActivityEngine.__init__`、`AnomalyDetector.__init__` 与 `InsightService.__init__` 归到了同一名字下——**探针自身的归类噪音**，已识别。

## 五、双轨的残留风险（如实记录，但不定级）

虽然证伪了"双向并行"，仍有两点值得记录：

1. **`insights/api.py` 有 16 个方法直接 `return self.legacy.*(...)` 或 `out = self.legacy.*(...)`**
   若门面未对返回值做规范化，这些方法返回的就是 legacy 的扁平形状，与同文件自己实现的方法（分页信封）**混在同一门面下**。
   本轮抽查 `device_usage`（350 行）确认它有"补 Page 键"的处理，说明作者意识到了这一点。但 16 个委托方法**未逐一验证是否都做了规范化**。

2. **legacy 是 "FROZEN" 状态但仍在承担 16 个方法的实际计算**
   重构未完成度：新包 55 个方法中 39 个自实现、16 个委托——**约 29% 仍走旧实现**。

这两点列为规划第九轮收口项，本轮不定级。

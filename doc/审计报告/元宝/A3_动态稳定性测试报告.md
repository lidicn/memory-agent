## 四、事件循环阻塞监测（全新维度，此前为 0）

**方法**：在真实事件循环中运行 monitor 协程采样 `loop lag`，对比三种负载。

| 场景 | P50 | P99 | max |
|---|---|---|---|
| ① 基线（几乎空闲） | 0.99ms | **1.02ms** | 1.02ms |
| ② `to_thread` 卸载（正确做法） | 0.98ms | **25.52ms** | 25.52ms |
| ③ 协程内直接同步扫描 | 1.00ms | **74.42ms** | 74.42ms |

**结论**：

- ③（未卸载）的 P99 是 ② 的 **2.9 倍**、是基线的 **73 倍**
- **未卸载的同步 DB 调用确实显著阻塞事件循环** → 为第一轮 P2-2（6 处 async 未卸载 I/O）提供了动态数据支撑

**值得注意**：即便用了 `to_thread`，P99 仍达 25.5ms（GIL 竞争 + 线程切换开销）。说明**卸载能大幅缓解但不能完全消除**阻塞。这对"高并发下响应变慢"有解释力。

## 五、长跑 + 资源采样

**规模**：真实 ASGI 服务，**213,500 次真实 HTTP 请求 / 100 秒**（QPS ≈ 2135）

| 指标 | 起始 | 结束 | 判定 |
|---|---|---|---|
| RSS | 58.3MB | 60.4MB（+2.1MB） | 后段平稳 |
| 文件描述符 | 13 | **13** | **无泄漏** |
| 线程数 | 1 | **1** | **无泄漏** |

### 关于"RSS 斜率 +22.45 MB/小时"的正确解读

线性拟合给出 +22.45 MB/小时，看似有泄漏。**但实际数据显示不是**：

```
t=99s:  RSS=60.4MB  req=213,450
t=100s: RSS=60.4MB  req=213,500
```

**最后 1 秒内 2135 次请求，RSS 完全不变。** +2.1MB 全部集中在前段（连接池、缓存、SQLite 页缓存初始化），后段斜率为 0。

**方法论教训**：线性拟合斜率对"初期阶跃 + 后期平稳"的曲线会产生严重误导。判断泄漏应看**后段是否持续爬升**，而非整体拟合斜率。这类曲线用分段斜率才可靠。

**结论：无内存/句柄/线程泄漏迹象。**

## 六、诚实声明（本阶段的限制）

| 限制 | 说明 |
|---|---|
| **长跑仅 100s** | 远低于计划的 4-8h。**缓慢泄漏（如每小时几 MB）在此时长内测不出**。要真正确认需 72h 级长跑 |
| **压测未覆盖重端点** | 只压了免鉴权轻量端点。`llm_ask`（CC=45）、insight 系列未压 |
| **无真实 HA/LLM** | 依赖外部服务的路径未纳入 |
| **沙箱环境反复重置** | 执行期间 `starlette`/`mcp`/`pymysql`/`bcrypt` 多次丢失，需反复重装。**这本身是重要发现**：环境非持久，任何"跑通了"的结论都需复核环境指纹 |
| **QPS 不代表生产** | 2135 QPS 是免鉴权轻量端点的极限，生产含 LLM 调用的真实 QPS 会低得多 |

## 七、关于沙箱环境不稳定（需单列的发现）

执行过程中观察到：**pip 安装的依赖会在一段时间后消失**。

```
21:30 装 starlette/mcp/pymysql/bcrypt → 验证 OK
21:40 再跑 → ModuleNotFoundError: starlette
21:45 重装 → OK
```

**影响**：此前任何"测试跑通/验证通过"的结论，若未记录当时的环境指纹，都可能与当前环境脱节。

**应对（已固化）**：在**同一次 bash 调用内**完成"装依赖 → 跑测试"，避免跨调用失效。并在报告中记录环境指纹。

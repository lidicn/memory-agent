## T1/T2 · phrase 与 OR 实测

实测（memory 文本「客厅的灯昨天开了三个小时」，问句「客厅的灯昨天开了多久」）：

    trigram:   phrase->0   OR(chars)->0
    unicode61: phrase->0   OR(chars)->0

- T1：phrase 包裹确实 0 命中，R5-1 成立。
- T2：**R5-1 建议的「改 OR 分词」同样 0 命中，该建议无效**。原因见 T3/T4：OR 拆出的单字低于 trigram 3 字符下限，在 unicode61 下又无法匹配整句 token。

修正建议：方向不是 phrase->OR，而是换真正能处理中文的分词器（jieba 预分词，或 CJK 自定义 tokenizer）。

## T3 · unicode61 对中文检索完全失效（严重性上调）

实测（fts5vocab 看实际 token）：

    unicode61 tokens = ['客厅的灯昨天开了三个小时']   <- 整句切成 1 个 token
      MATCH '灯'     -> 0
      MATCH '客厅'   -> 0
      MATCH '客厅的灯' -> 0

unicode61 按 Unicode 类别切词，中文无空格 -> 整段中文成为一个 token，任何子串查询都无法匹配。

放大 R4-3：R4-3 是推断，R7 实测证实它等于「中文检索彻底关闭」。MA 的降级链 trigram -> unicode61，一旦 trigram 不可用，中文 FTS 检索从「弱」直接变「无」，且静默。

## T4 · trigram 有 3 字符下限（新发现）

实测：

    trigram tokens = ['三个小','个小时','了三个','厅的灯','天开了','客厅的','开了三','昨天开','灯昨天','的灯昨']
      MATCH '灯'(1字)     -> 0
      MATCH '客厅'(2字)   -> 0
      MATCH '客厅的'(3字) -> 1
      MATCH '客厅的灯'(4字)-> 1

trigram 按 3 字符滑窗建索引，查询词 < 3 字符恒 0 命中。对中文致命：单字设备名（灯/门/锁）和双字房间名（客厅/卧室）都查不到——恰是 MA 注释声称 FTS 路要覆盖的「专名/设备名/房间名」。

讽刺点：MA 选 trigram 的理由是「中文子串友好」，实测它恰好查不了 MA 最想查的短实体名。

### T5 · R5-3 证实：FTS 结果层过滤在 LIMIT 之后，召回丢失

**实测**（trigram 表，11 条记忆其中前 10 条 member=B、第 11 条 member=A；k=5）：

    总匹配(不过滤): 11
    --- MA 做法: LIMIT 5 先截断, 再过滤 member=A ---
      LIMIT结果: [('m1','B'),('m2','B'),('m3','B'),('m4','B'),('m5','B')]
      过滤后: []   <-- 空=召回丢失
    --- 下推 member=A 后 LIMIT 5 ---
       [('mA',)]   <-- 有值=修复有效

**结论**：R5-3 **由推断升级为实测证实**。SQL 先 `LIMIT 5` 取回前 5 条（全是 member=B），Python 侧再按 member=A 过滤后**归零**；而把 `member_id` 下推到 SQL `WHERE` 后 `LIMIT 5` 能正确取回 mA。

**注**：本次能测出，是因为改用 trigram 表让中文 3 字查询（「客厅灯」）真正命中；上一版用默认 tokenizer 导致两边都返 0、无法区分。**这同时说明：R5-3 的危害只在 FTS 路真能命中时显现**——而 R7 已证明 FTS 路对中文长问句基本不命中，故两者叠加下 FTS 路整体近乎失效。

（更正：R7 报告正文原写「R5-3 本次未测出」，现更正为**已证实**。）

### T6 · R4-2 证实：迁移非重复列错误留下部分迁移态

**实测**（模拟 MA 的「逐条 ALTER + 只捕 duplicate column + 他错 print 续行」）：

    MA 做法(逐条 try, 他错 print 续行)结果:
       ('OK', 'b')
       ('ERR', 'no such table: nonext')
       ('OK', 'd')
      最终 t 的列: ['a', 'b', 'd']
      -> b 和 d 都加上了, 中间的失败没有中断后续; 库停在部分迁移态

    对比: 迁移段包事务
       事务回滚, 错误: no such table: nonext
       最终 t 的列: ['a']  -> 干净, 无中间态

**结论**：R4-2 **由推断升级为实测证实**。当 ALTER 因非「duplicate column」原因失败（如表不存在/磁盘满/锁库）时，MA 的写法**不中断、不回滚、继续跑后续迁移**，库停在「部分列已加」的中间态。而把迁移段包进事务后，失败可干净回滚——实测确认 SQLite 的 ALTER TABLE 在事务内可回滚。

**建议**：`init_schema` 的迁移段整体包事务，失败则 rollback + 明确报错。

## 补充实测（T7）· WAL 崩溃恢复：synchronous=FULL vs NORMAL

**方法**：子进程用 MA 的 `connect()` 同款配置（WAL + 指定 synchronous + timeout=30）写入 1000 行并 `commit()`，随后 `os._exit(1)` **硬退出**（不 close、不 checkpoint，模拟崩溃）。父进程重开库做 `integrity_check` + 计数。

**实测输出**：

    [synchronous=FULL]   子进程崩溃退出码=1
       重开后 integrity_check=ok  已提交行数=1000  残留wal=False  数据完整: True
    [synchronous=NORMAL] 子进程崩溃退出码=1
       重开后 integrity_check=ok  已提交行数=1000  残留wal=False  数据完整: True

**结论（务必如实）**：
- 两者**都**保住了已提交数据、integrity 均 ok。**本环境无法区分 FULL 与 NORMAL 的差异**。
- 原因：`os._exit` 是**进程级**崩溃，OS 仍在运行，WAL 页通常还在 OS 页缓存中，重开可正常恢复。FULL 与 NORMAL 的差异（提交时是否 fsync WAL）只在**断电 / OS 崩溃 / 虚拟机强杀**时显现——本沙箱**无法模拟真正的掉电**。
- 因此：**commit e85febd 选择 FULL 的正确性，本轮无法实证**，只能依据 SQLite 文档语义（NORMAL 下 WAL 提交不 fsync，掉电可能丢最近事务/损 WAL 帧）支持其合理性。

**这条实测的价值在于划清边界**：不是所有结论都能在本沙箱内验证。FULL vs NORMAL 属「必须真掉电才能验」的一类。

## 补充实测（T8）· 多线程写并发：RLock 的必要性

**方法**：8 线程 × 500 次 INSERT+commit（共 4000 行），对比两种配置。

**实测输出**：

    [A] 单连接+RLock (MA 模式):
        异常数: 0  总行数: 4000 /4000  完整: True
    [B] 单连接无锁 (错误示范):
        异常数: 7  总行数: 516 /4000
        样例: [(5,'InterfaceError','not an error'),
               (4,'InterfaceError','not an error'),
               (3,'InterfaceError','bad parameter or other API misuse')]

**结论**：
- **[A] 验证了 MA 的 `单连接 + RLock` 设计在多线程写下是正确且有效的**：4000 行全部落库、零异常。
- **[B] 反证锁的必要性**：去掉 RLock 后，8 线程共享一个 sqlite3 连接立即出现 `InterfaceError`（连接被并发使用），**只写了 516/4000 行就崩**——数据大量丢失。
- 这解释了 `store.py:9` 注释「单连接 + RLock，check_same_thread=False 以适配线程池」的**工程必要性**：不是保守，是必须。

**对 R3 的呼应**：R3（数据库专项）曾指出「单连接 RLock 是写并发瓶颈」。T8 实测确认它是**有意的正确性换吞吐**——去掉它直接崩，故不能为性能轻率移除；若要提升并发，正确方向是**读写分离连接**（多读连接 + 单写连接），而非去掉锁。

## 补充实测（T10）· 数据库损坏检测与备份恢复（check_and_recover）

**背景**：数据库反复损坏是项目头号历史问题。R3 曾静态读过 `check_and_recover`，但从未实测它「真能恢复」。本轮完整复刻其逻辑。

**方法**：
1. 建一个健康备份快照 `backup/ma-20261010.db`（模拟 `BackupManager` 的 `VACUUM INTO` 产物，500 行）；
2. 建主库并写 500 行，然后**把文件头 16 字节清零**（真损坏）；
3. 复刻 MA 的恢复流程：integrity_check 判红 → 扫 `backup/ma-*.db` 与 `<db>.bak*` → 取最新且**自身 integrity_check 通过**的备份 → 覆盖 → 清 `-wal`/`-shm` → 复查。

**实测输出**：

    备份快照建好: ma-20261010.db 16384 bytes
    主库已破坏(文件头清零)
    --- 检测阶段 ---
    损坏主库 integrity_check: open-error: file is not a database
    判红: True
    --- 恢复阶段(复刻 MA 逻辑) ---
    候选备份: ['ma-20261010.db']  选中: ma-20261010.db
    已从备份恢复 + 清理 -wal/-shm
    --- 恢复后验证 ---
    恢复后 integrity_check: ok
    恢复后行数: 500 /500  完整: True

**结论**：
- MA 的 `check_and_recover` 机制**逻辑自洽且有效**：损坏检测（integrity 判红）→ 备份候选筛选（**逐个自校验、只取校验通过的**，避免用坏备份覆盖）→ 覆盖 + 清残留 wal/shm → 复查，全链路走通，**从真损坏恢复到 ok、数据完整**。
- 特别是「**只选自身 integrity_check 通过的备份**」这一步是正确防御——否则可能用另一个坏文件覆盖，造成二次损坏。
- 这解释了代码注释里「备份来源两处 `<db>.bak*` 与 `backup_dir/ma-*.db`，按 mtime 取最新」的修复（早期两处永不相交、恢复永远空跑）**是必要且正确的**。

**注意（边界）**：本轮是「文件头清零」这种**可检测**的损坏；真实生产里的损坏（WAL 帧不完整、页级损坏）是否都能被 `quick_check` 判红，不在本沙箱可验范围。

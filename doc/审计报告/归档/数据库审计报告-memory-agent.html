二、发现明细按严重程度从高到低

严重（1 条）

严重稳定性功能性 · 数据完整性

D01「自动恢复」的候选集包含手工文件拷贝（缺 -wal 的不一致快照），而产生这类拷贝的脚本正是排障时最先被执行的

位置
store.py:765-771（恢复候选 = db_path + ".bak*" 与 backup_dir/ma-*.db 合并后按 mtime 降序取最新）
store.py:784（shutil.copy2(候选, db_path) 覆盖主库）
store.py:787-793（覆盖后删 -wal / -shm）
scripts/db_integrity_check.py:6,11（BAK = f"/data/memory_agent.db.bak.{int(time.time())}" 后 shutil.copy2(DB, BAK)）
触发条件
① 运行 python scripts/db_integrity_check.py——它会无条件先把主库文件原样复制成 /data/memory_agent.db.bak.<epoch>（本意是"动手前留个退路"）；② 此后任意一次启动时 quick_check 判红，check_and_recover 就会进入恢复分支。
影响
WAL 模式下「主库文件 + -wal」才构成一个完整数据库。文件级 copy2 只拿到主库那一部分，最近提交（默认自动 checkpoint 阈值 1000 页，约 4MB）全部不在里面。若这份手工拷贝的 mtime 比最近一次 VACUUM INTO 快照更新——排障当天必然如此——恢复动作就是用一份缺最近提交的库覆盖主库，随后删掉 -wal 与 -shm，把"丢的那一段"永久抹掉。整个过程会打印一行"已从备份恢复"，没有任何一致性校验拦住它。
为什么算严重
它破坏的是安全网本身：伤害不可逆，且触发者恰好是最需要它可靠的那个人。
最小修复
① 恢复候选只认 backup_dir 下由 VACUUM INTO 产出的 ma-*.db，把 db_path + ".bak*" 从候选里去掉（或仅作最后兜底）；② 覆盖主库前对每个候选跑 PRAGMA integrity_check，非 ok 就换下一个并记 warning；③ 把 db_integrity_check.py 的 copy2 改成 VACUUM INTO（backup.py:56-76 已有正确写法可抄），并把备份文件挪出主库所在目录；④ 给历史遗留的 *.db.bak* 加轮转（现在 backup.py 的 _rotate 只管 ma-* 与 chroma-*，这类文件永不清理）。

D03每小时 TRUNCATE checkpoint 的返回值从未被检查，被 busy 挡下仍报成功 —— 「静默失效」这一层没有修完

位置
store.py:660-668（checkpoint()：self._conn.execute("PRAGMA wal_checkpoint(TRUNCATE)")，不取返回行；self._conn is None 时直接静默 return）
store.py:1990（close() 里同样只捕异常、不看返回行）
runtime.py:399-417（周期任务把 store.checkpoint 丢进 to_thread，只 except Exception）
触发条件
有其他连接/进程持读锁时（每日备份的 VACUUM INTO、维护脚本的 SELECT/integrity_check、第二条连接），wal_checkpoint(TRUNCATE) 不抛异常，而是返回一行 (busy, log, checkpointed)。
影响
本轮 checkpoint 什么都没做，任务与日志却显示成功：WAL 不截断、文件不收缩，"每小时把 WAL 合并回主库、把重启恢复窗口压到最小"的运维保证实际上无法被验证。第一轮修的是"绕开锁"，这一层是"绕过失败"。
诚实边界
代码里没有改动 wal_autocheckpoint，SQLite 默认的 1000 页自动 checkpoint 仍然生效，所以 WAL 不会无限增长；受影响的是"文件不收缩 / 大 WAL 不合并 / 失败不可观测"，不是"WAL 撑爆磁盘"。
最小修复
取返回行 busy, log, ckpt = cur.fetchone()，busy != 0 或 ckpt < log 时记 warning 并计数（可暴露到健康端点）；self._conn is None 时也留一条可观测信号，而不是静默返回。同一段逻辑可复用到 close() 里的那条 PRAGMA。

D07服务进程与维护脚本/备份/部署脚本对同一个 SQLite 文件的多进程并发没有任何协调，也没有应用层重试退避

位置
维护脚本直连生产库：scripts/db_health_check.py:6、db_stats.py:5、reindex_and_cleanup.py:5、fix_empty_memory_id.py:7、delete_empty_memory_id.py:5、db_integrity_check.py:16（都是 sqlite3.connect("/data/memory_agent.db")，默认 timeout=5s，且不设置 journal_mode / synchronous / foreign_keys）

触发条件
在容器里执行维护脚本、每日备份窗口、部署脚本的 DB 快照与在线服务重叠。

最小修复

中稳定性并发 · 潜在

D08check_and_recover 的恢复段完全在锁外，会直接关闭共享连接并覆盖主库文件

位置
store.py:765-810，其中 :780 conn = self.connect()、:781 conn.close()、:782 self._conn = None、:784 shutil.copy2(latest_bak, self.db_path)、:787-793 删 -wal/-shm、:796-798 新连接复核——全部不在 with self._lock 内（该函数里的锁只出现在内层 _run() 的 self._db()，见 store.py:737）。
触发条件
运行期任何一次对 check_and_recover 的调用。当前唯一的生产调用点是 runtime.py:173 的启动期调用（那时确实还没有并发），另有 7 处测试调用（tests/test_db_integrity_check_mode.py）。
影响
这是"当前不可达、但一旦被挪进健康巡检/定时任务就会立刻出事"的地雷：它会在别的线程正持有连接时把连接关掉、把库文件覆盖掉、把 -wal/-shm 删掉。另外 close() 之后 _conn=None，别的线程下一次 self.connect() 会把刚被替换的库重新打开并重建 -wal/-shm，恢复动作的原子性无从谈起。Windows 上还有额外风险：shutil.copy2 与 os.remove 在目标被其他进程/句柄占用时会直接失败（Docker Desktop、杀毒扫描、编辑器索引都可能占用）。
最小修复
把 765-810 整段包进 with self._lock:；在 docstring 与调用点显式声明"仅允许启动期单线程调用"，并在函数开头加一个 self._started 类的一次性守卫，防止它被误接进运行期健康检查。
中功能性 · 迁移稳定性

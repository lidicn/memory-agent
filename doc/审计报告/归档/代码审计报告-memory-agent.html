F1　WAL checkpoint 周期任务无锁操作共享连接高

src/memory_agent/runtime.py:406-414对照：src/memory_agent/store.py:640-657, 665-687
代码事实
新增的常驻任务 _periodic_wal_checkpoint() 通过 self.store.connect() 取得连接后直接执行 PRAGMA wal_checkpoint(TRUNCATE)，整个 _ckpt() 函数体没有获取 store._lock。而 Store.connect() 返回的是进程级单例连接（store.py:641-645），存储层所有读写都靠 with self._lock（如 store.py:665-687 的 transaction()）串行化同一连接。
触发条件
服务运行满 1 小时后（首次延时 30s + 每 3600s 一轮），若此刻恰好有采集/对账/配置写入正在该连接上执行或提交，checkpoint 就会与业务语句在同一连接上并发执行。
为什么影响稳定性
sqlite3 连接仅在 check_same_thread=False 下允许跨线程，但并发使用同一连接需要调用方自行加锁；此处锁被绕开。后果有两类：(1) 两个线程在同一连接上交错执行语句，出现 OperationalError: cannot commit - no transaction is active / database is locked 一类非预期异常；(2) TRUNCATE checkpoint 需要独占，若撞上未提交的读/写事务会返回 SQLITE_BUSY，checkpoint 静默不生效——恰好让“避免 WAL 无限增长”这个修复目标落空，而异常只被打成一行 print（runtime.py:412-413），运维无从察觉。
验证状态
“未加锁”为确定性事实（runtime.py:408-411 无 lock，store.py:641-645 为单例连接）；具体异常种类属推断，需运行时复现确认。
最小修复建议
让 checkpoint 走存储层的锁，例如在 Store 上新增 def checkpoint(self): with self._lock: self.connect().execute("PRAGMA wal_checkpoint(TRUNCATE)")，_ckpt() 改为调用 self.store.checkpoint()；同时不要把失败仅 print，改用 logger.warning 并让返回码可见。

F2　CI 使用未安装的 pytest 插件参数，流水线仍会红高

.github/workflows/ci.yml:26-43对照：pyproject.toml:6-30, pytest.ini
代码事实
CI 的测试步骤是 python -m pytest tests/ -q --ignore=... -x --timeout=60（第 38-43 行），但安装步骤只装了 pytest pytest-asyncio 加 pip install -e .（第 29-30 行）。全仓 grep pytest-timeout / --timeout：只在 ci.yml:43 出现一次，pyproject.toml 的 dependencies 与 optional-dependencies 均未声明，pytest.ini 也没有 addopts。配套提交 40f174c ci: 修复 GitHub Actions CI 失败 目的在于让流水线变绿。
触发条件
每次 push / PR 到 main，运行到 “Run unit tests” 步骤时。
为什么影响功能性
--timeout 是 pytest-timeout 插件提供的参数；插件缺席时 pytest 会在收集阶段以 error: unrecognized arguments: --timeout=60 退出（exit code 4），测试一条都不会执行。“修复 CI”的提交因此可能仍是红的，而开发者看到的是“参数错误”而非“用例失败”，容易再次误判。仓库当前也没有任何 @pytest.mark.timeout 使用点，说明该参数无历史依赖。
验证状态
“未声明、未安装”为确定性事实；若 GitHub runner 镜像恰好预装了 pytest-timeout 则可侥幸通过——但按仓库自身声明口径这是一个未被固定的隐式依赖。
最小修复建议
二选一：① 在 pyproject.toml 增加 [project.optional-dependencies] test = ["pytest","pytest-asyncio","pytest-timeout"]，CI 改为 pip install -e ".[test]"；② 直接删掉 --timeout=60，把超时保护下沉到 gates.yml 的 job 级 timeout-minutes。

F3　store.close() 吞掉提交与 checkpoint 异常，且异常路径不关闭连接中

src/memory_agent/store.py:1969-1983调用点：runtime.py:908
代码事实
close() 的结构是：try: → self._conn.commit() → 内层 try/except Exception: pass 包住 PRAGMA wal_checkpoint(TRUNCATE) → self._conn.close()；外层再有一个 except Exception: pass，随后无条件 self._conn = None。
触发条件
关停时若 commit() 抛异常（磁盘满、WAL/SHM 不可写、连接已被上一轮的 checkpoint 线程搞到可疑状态），或 close() 本身抛错。
为什么影响数据正确性
(1) 外层裸 except Exception: pass 把“提交失败”这一最需要被看见的失败吞成静默：进程照样退出、日志无痕，最后一个事务的写入去向无人知晓，而提交失败往往正意味着数据没落盘。(2) 异常发生在外层时 self._conn.close() 不会执行，但下一行仍把 self._conn 置为 None，句柄被丢弃且不可达——连接泄漏，同时使“关闭前强制 checkpoint”这一验收目标在异常路径上完全不成立（内层 except Exception: pass 同样吞掉 checkpoint 失败）。
验证状态
异常分支是否被真实触发需运行时确认；但“异常被吞 + 句柄丢弃”的代码路径本身确定。
最小修复建议
改为：close() 内各自 try/except 记录 logger.error（不得 pass）；把 self._conn.close() 放进 finally；commit/checkpoint 失败时保留 self._conn 或至少把失败状态返回给 runtime.shutdown() 打印。

F4　密钥/用户名“防意外清空”保护把合法清空也静默忽略，接口仍报成功中

src/memory_agent/api/config_routes.py:62-84, 245-292
代码事实
EMPTY_PRESERVE_FIELDS = SECRET_FIELDS + ("nr_user","ha_db_user","go2rtc_user","tv_mqtt_user")（第 72-74 行）。update_config_api 对这批字段的处理是：空字符串或掩码 → continue（保持原值，第 255-259 行），只有 "__CLEAR__" 才真正清空。循环结束后返回 ok({"message":"配置已更新","changed":changed})（第 292 行）。
触发条件

为什么影响功能性
该字段既不在 changed 里、也不报错，HTTP 返回的是“配置已更新”的成功响应。调用方会认为清空成功，实际值原样保留：问题在下一次取帧/连接失败时才以 401、认证失败等形式暴露，排查成本被转移到很远的地方。__CLEAR__ 这个约定只存在于本文件注释里，仓库内没有随附的接口文档或前端契约校验，属于“行为与契约不符 + 静默失败”。
验证状态
语义确定（读代码即可复现判断）；是否已有前端正确实现 __CLEAR__ 未核实（src/memory_agent/static/ 未纳入本次阅读范围）。
最小修复建议
把“被忽略”显式化：命中保留分支时把字段名收集到 preserved 列表并随响应返回（如 {"changed":[...], "preserved":["go2rtc_user"]}），或在文档/OpenAPI 里写明清空必须用 __CLEAR__；对用户名这类非密钥字段可考虑直接允许空串（只对 SECRET_FIELDS 保留防清空）。

F5　断路器“半开放行一次”实际不成立低

src/memory_agent/circuit_breaker.py:30-38测试注释：tests/test_circuit_breaker.py:27
代码事实
allow()：失败数达标后，只要 time.monotonic() - self._opened_at >= cooldown_seconds 就 self._half_open = True; return True——_opened_at 在这一支里不被更新，因此冷却期满后每一次调用都会放行，没有“只放行一次探测”的闸门。_half_open 也只影响 state() 的展示。
触发条件
冷却期刚过、上游仍不可用时，同一时刻有多个并发调用（多路 LLM/embedding 调用）。
影响
模块 docstring 写“半开（放行一次探测），成功则复位”，测试注释也写“冷却到 → half_open 放行一次”，实现与这两处说法不符：熔断退化为“冷却后全放行”，探测流量不再受限，降级保护变弱。属行为与文档不一致，不造成崩溃。
验证状态
逻辑确定（单次调用路径已被现有测试覆盖，测试只断言一次调用，掩盖了该差异）。
最小修复建议
半开时用一次性令牌：allow() 中改为 if self._half_open and self._probe_taken: return False，探测放行后置位 _probe_taken，由 record_success/record_failure 复位；或明确把 docstring 改成“冷却后放行”。

F8　采集服务 stop() 吞掉 CancelledError，破坏取消传播低

src/memory_agent/poller.py:95-105
代码事实
stop() 中对每个任务执行 task.cancel() 后 await task，异常处理写成 except (asyncio.CancelledError, Exception): pass，把 CancelledError 与普通异常一起吞掉。
触发条件
stop() 自身所在的任务被取消时（例如 runtime.shutdown() 因上层超时被杀），await task 抛出的取消信号会被该 except 吃掉。
影响
取消传播被中断：关停流程可能继续执行后续步骤而不是尽快退出，在容器 kill 时表现为关停被拖长；且真正的取消原因被静默。同类写法应只吞预期异常。
验证状态
代码路径确定；实际是否被触发取决于关停时序，需运行时确认。
最小修复建议
拆成两段：except asyncio.CancelledError: pass 只在确认是“被取消的就是该任务本身”时才吞；更稳妥的写法是 await asyncio.gather(task, return_exceptions=True)，不再手写异常分支。

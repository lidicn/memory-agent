## 一、M16【中·已修复验证】出站端点无目标地址校验

### 缺陷

`api/acp_routes.py:181 acp_test_outbound`：

```
url ← body.get("url")        ← 请求体，注释写着"先填后测"
endpoint = url + "/acp"
→ httpx.AsyncClient(timeout=10).stream("POST", endpoint, ...)
```

**全程无 scheme / 内网地址 / 端口校验。** 有 `require_user` 鉴权，
但鉴的是"谁在请求"，不管"请求发到哪"。

### 实测（本地靶子）

```
靶子收到的请求: 2 次   path=/acp   （192.168 / 127.0.0.1 均原样发出）
169.254.169.254       → 请求已发出（沙箱返回 403，真实环境会通）
回显实测：解析出 tools = ['delegate_to_autoflow']
```

⇒ 请求原样发出 + 响应内容回显 = **可对内网服务做指纹识别**。

全项目搜索：`allowlist` / `whitelist` / `validate_url` / `SSRF` **零命中** ——
这个端点**压根没有护栏**。

### 与 D17 / F15 的形态差异（重要）

| 项目 | 缺陷 | 形态 |
|---|---|---|
| doubao-butler D17 | SSRF | 护栏**装了**，装在没人走的保存路径上 |
| AutoForge F15 | 出站旁路 | 护栏**装了**，4 处直连 `urlopen` 绕过 |
| **memory-agent M16** | SSRF | **压根没有护栏** |

⇒ 三处同族但形态不同，修复方式也不同：前两处要"把护栏接到正确路径上"，
这里要"从零建护栏"。

### ⚠ 补丁第一版我自己写错了，差点引入业务中断

第一版我写成"拒绝私有网段"。**这是错的**——
memory-agent 就是读 HomeAssistant 的，而 HA / go2rtc 通常就在 `192.168.x.x`。
一律拒绝私有网段会**打断主业务**。

已改为：**放行私有网段，只拒绝环回 / 链路本地 / 非 http(s)**。

对照实测：

| URL | 原版 | 补丁版 |
|---|---|---|
| `http://192.168.1.50:8123/api`（真实 HA） | 放行 | **放行**（业务不受影响） |
| `http://169.254.169.254/latest`（云元数据） | 放行 | 拒绝 |
| `http://127.0.0.1:8080/acp` | 放行 | 拒绝 |
| `http://localhost/acp` | 放行 | 拒绝 |
| `file:///etc/passwd` | 放行 | 拒绝 |
| `https://acp.example.com/acp` | 放行 | 放行 |

## 二、W108：379 条 AFS-07 几乎没有真 IO

### 分层结果

| 类别 | 数量 | 判定 |
|---|---|---|
| SQLite 连接上的操作 | **239** | 单连接架构的必然结果 |
| `dict.get` | **58** | 假阳性（同名方法，**第三次遇到**） |
| `json.dumps` | **25** | 内存序列化，不是 IO |
| `connect` | 14 | 幂等获取，已判安全 |
| **真 IO** | **16** | 保留 medium |

### 为什么 SQLite 在锁内不是缺陷

`store.py` 第 9 行注释明确写着：

> 单连接 + `RLock` 保护，`check_same_thread=False` 以适配线程池

**单连接必须串行化，所有 DB 操作在锁内是架构必然**，不是 239 个独立缺陷。
修复方式是架构级（换连接池 / 拆分锁），不是逐条改。

⇒ **聚合报 1 条 / 文件**（共 5 条 low），而不是 239 条。

### 过程中的两次自我纠错

1. **W108b**：聚合字典写成模块级 ⇒ 跨文件累积 ⇒ 输出 **232 条重复**。
   改函数内局部变量后变成 5 条。
2. **W108c**：`httpx.get` 的 attr 也是 `get`，第一版把它误判成 `dict.get` 吞掉
   ⇒ **会把真 SSRF 判成内存操作**。负向测试救的场。

## 六、本轮最该记住的一条

**我在给 M16 打补丁时，差点亲手引入一个业务中断缺陷。**

第一版我照着 doubao-butler D17 的思路写"拒绝私有网段"——
在那个项目里是对的（它的外部 API 都在公网），
但 memory-agent 是**读 HomeAssistant 的**，HA 就在 `192.168.x.x`。
照搬过来会把主业务挡在门外。

**这说明"同族缺陷"不等于"同一个修法"。**
D17 和 M16 都叫 SSRF、都由 OUTB-01 报出、都缺目标地址校验——
但一个是"护栏装错路径"，一个是"没有护栏"；
一个的外部目标是公网，一个的业务目标**就在内网**。

我差点犯的错，本质上是**把上一个项目的答案直接当成这个项目的答案**。

对照实测表救了这个场——如果我只跑"补丁版能否拦截 169.254"，
我会看到"拦截成功"就收工，不会发现 HA 地址也被拦了。
**所以对照测试里必须放一条"正常业务地址必须放行"的用例**，
这条用例的价值不在于验证补丁，而在于防止补丁做过头。

推而广之：**任何"加拦截"的修复，都要有一条"不该被拦的必须通"的反向用例。**
安全补丁最常见的失败不是拦不住，而是拦太宽。

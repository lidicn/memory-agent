## 二、分诊：medium 549 → 389

### W129：MIXED-RETURN 中 Optional 标注是契约合规

116 条 medium 里：

| 标注 | 条数 |
|---|---|
| `dict \| None` | 30 |
| `Optional[dict]` | 6 |
| `str \| None` | 12 |
| `Optional[datetime]` | 8 |

这些函数**明确声明了可能返回 None，也确实返回了 None**——契约没有被违背。

W68（doubao-butler 第九轮）只处理了"标注非 Optional 却返回 None"那一半，**Optional 这一半一直没管**，于是 94 条完全合规的函数被报成 medium。

> 这是"修复只做一半"的又一次——与 W77（只认 `self.path`）、W79e（语义反转）、W126（只降 explicit-null）同源。

**结果：116 → 23 medium。** 负向测试三条全过（Optional→low / 非 Optional→high / 无标注→medium 对照不变）。

### W130/W130e：div-zero 三形态保护识别

93 条 medium 拆开后：

- **23 条字面常量分母**（`stats['total_volume_ml'] / 1000`）⇒ 单位换算，不是除零风险 ⇒ `NUM-01-unit-conversion`(low)
- **25 条 `len()` 分母** ⇒ 独立成 `NUM-01-div-zero-len`

核验 25 条 `len()` 分母时，**我的核验脚本错了两版**：

| 版本 | 漏什么 | 误判 |
|---|---|---|
| 正则版 | 只认 `if not X` / `max(1,..)` | 漏 `if stranger_signals:` 真值早退 ⇒ 误判 23 条无保护 |
| AST 版 | 只认 `If` 包裹 | 漏三元条件表达式 ⇒ 误判 21 条无保护 |
| **v3** | 三形态全认（if-guard / ternary / max1） | **25 条全部有保护，0 真缺陷** |

**结果：93 → 26 medium + 23 low。**

## 三、M21【高危·新确证】

### 现象

`verify_token`（`auth.py:261`）：

```python
users = self._load_users()
if username not in users:
    return None          # ← 损坏时 _load_users() 返回 {}
```

`_load_users()` 读失败返回 `{}` ⇒ `username not in users` ⇒ **所有已签发 token 立即失效**。

`login` 同理取不到 `password_hash` ⇒ **管理员也无法重新登录**。

### 对照实测

| | 损坏前 | 损坏后 |
|---|---|---|
| `verify_token(已有 token)` | 有效 | **None（失效）** |
| `login(admin)` | ok | **"用户名或密码错误"** |

**补丁副本表现完全相同**——M6 的补丁只防"写盘覆盖"，没防"读失败后登录链静默拒绝"。

### 为什么单列

M6 修的是**数据丢失**，M21 是**可用性**，补丁未覆盖后者。

后果链：users.json 损坏 ⇒ 所有人登出 ⇒ 无人能登录 ⇒ **而修复路径（UI）本身需要登录** ⇒ 无法自助恢复。

users.json 损坏不是假设——与"数据库频繁损坏"同源（磁盘满、异常停机）。

## 六、本轮最该记住的一条

**我的核验脚本错了两版，两版都把"有保护"判成"无保护"。**

第一版漏真值早退，第二版漏三元条件。如果我在第二版就停，会报出 21 条"无保护的除零"——**凭空造出 21 条缺陷**。

这和被测代码里的"修复只做一半"是同一个病，只是发生在**我自己写的核验工具**上。而且更危险：被测代码的漏判会被 PoC 抓到（第十七轮 M6 就是这样被专用适配器抓出来的），**核验脚本的漏判没有任何东西会抓它**——它就是判据本身。

对策：第三版我做了三形态穷举，并且**对每一条"无保护"结论都回去看了源码**。

## 二、M17【中·已修复验证】

### 缺陷

`store.insert_events` 的 docstring 写着：

> 单次事务 + `executemany`，**500 条一批由调用方控制**。

但实测调用方 `poller.py`：

```python
for entity_id, records in (series or {}).items():
    events = self._events_from_series(room, entity_id, records)
    buffer.extend(events)                      # ← entity 循环内累积

if len(buffer) >= self.FLUSH_SIZE:             # ← 检查点在 **window 循环外**
    await self._flush(buffer)
```

**`FLUSH_SIZE` 只在 window 边界生效，不是真正的 500 一批。**
`_flush` → `add_events` → `insert_events` 三处**都不分批**。

⇒ 一个 window 内 N 个 entity 的 events 全部累积，一次 `executemany`、一个事务。

### 实测（48 万行，单连接 + 全局 RLock）

| | 原版（单事务） | 补丁版（500 分批） |
|---|---|---|
| 读请求被阻塞 **最大值** | **721.1ms** | **175.6ms**（降 76%） |
| 读请求被阻塞 平均 | 721.1ms | 50.8ms |
| 盘上（db + WAL） | 34.9MB | **20.5MB**（减 41%） |
| 写入耗时 | 0.72s | 0.73s（基本不变） |

单条 event ≈ 2.5KB ⇒ 48 万条 ≈ 1.2GB，**远超容器 471MB 内存上限**。
在 J3455 弱机上，721ms 会放大到数秒级冻结。

### ⚠ 这个缺陷**不丢数据**

分批后每批独立 `commit`，实测中断时残留 **0 行**，原子性保持。
所以定 medium 不是 high。

**而且它不能直接解释"数据库频繁损坏"**——长时间持锁 + WAL 暴涨在弱机上会**加剧**风险，但不是根因。这个问题仍然没有答案。

### 修复

① `store.insert_events` 内部分批（`EVENT_BATCH_SIZE = 500`，每批独立事务）
② `poller` 的 flush 检查点**移入 entity 循环内**，才是真正的 500 一批

## 二、M20【中·已修复验证】

### 缺陷

`llm_client.py:520 LLMRouter.chat()` 遍历全部 provider：

```python
for prov in providers:
    try:
        ...
    except Exception as exc:
        errors.append(...)        # ← 只收集
...
br.record_failure(summary)        # ← **循环外，只记 1 次**
```

断路器阈值是 `get_breaker("llm", 3, 60.0)`（失败 3 次、冷却 60s）。

**问题在于粒度**：一次 `chat()` 调用里 4 个后端全挂，也只算「1 次失败」。
要打开断路器必须完成 **3 次完整遍历**——而每次遍历都要把 4 个后端各等满 timeout。

### 对照实测

| | 首次短路 | 累计等待 |
|---|---|---|
| 原版 | **第 4 次**调用 | 0.25s |
| 补丁版 | **第 2 次**调用 | 0.08s |

换算到生产（4 后端 × 25s timeout）：

- 原版：**累计 300 秒**才短路，期间每次调用卡满 100 秒
- 补丁版：累计 100 秒

用户感知是：**LLM 全挂后的 5 分钟内，每次 MCP/LLM 调用都要等 100 秒**。

### 修复

在每个 provider 的 `except` 分支加 `br.record_failure(str(exc))`，
**同时保留循环外那一次**——单后端部署时它是唯一能让断路器打开的路径。

### 不误伤验证

部分故障（1 坏 3 好）实测：6 次调用后 `_f` 峰值 = **0**。
因为随后的成功 `record_success()` 会清零计数。

> 我一开始预判「后端级计数会在部分故障下误伤」，**这个预判被实测推翻了**。
> 真正差异只在全故障场景。

## 六、本轮最该记住的一条

**我预判错了，而实测纠正了我——但这次的方向和第四轮相反。**

第四轮我推断「471MB 库 checkpoint 慢导致冻结」，第五轮被证伪——**那是推断太顺理成章**。

本轮我预判「后端级计数会在部分故障下误伤」，实测推翻——**这是谨慎方向的误判**：
我担心补丁有副作用，于是去测，结果没有。

两次都是**推断 vs 实测**，但性质不同：

- 第四轮：把推断当根因，**没测就用了**
- 本轮：把推断当风险，**测了才发现不存在**

差别在于：**前者让结论变松，后者让结论变紧**。变紧的误判代价小——只是多打了个补丁说明；变松的误判代价大——会把 439 条未验证的降噪当成"已确认没问题"。

推论：**宁可误判「有风险」去测一次，也不要误判「没问题」直接放行。** 这条正是降噪台账存在的理由——447 条降噪里，我一条都没做过"去测一次"这个动作。

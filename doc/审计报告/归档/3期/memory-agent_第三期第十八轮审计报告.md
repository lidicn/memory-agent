## 二、那条误杀：它漏的正是 M6

### 现象

`auth.py:190 AuthManager._load_users`：

```python
except Exception as exc:
    _LOG.warning("读取用户文件失败 %s: %s", self.users_file, exc)
    return {}
```

W109 的判据是"**有日志 ⇒ 有意降级 ⇒ low**"。于是它被降成 low，沉进噪声。

### 但它就是 M6

调用方 `register()`：

```python
users = self._load_users()      # ← 损坏时返回 {}
...
users[username] = {...}
self._save_users(users)         # ← 全量覆盖
```

第十七轮专用 PoC 实测：播种 alice/bob/carol → 损坏 → 注册 dave →
**盘上只剩 dave，原 3 个账号全丢（`data_lost`）**。

### 根因

**日志只保证"你知道自己丢了什么"，不保证"你没丢"。**

可见性和破坏性是两个正交维度——我在 doubao-butler 第十五轮就确证过一次
（M6/M7 日志都在，照样丢数据），**换到这个项目又让判据犯同样的错，是第三次**。

### 修复：W126 + W126b

- **W126**：状态读取器（同类存在写方法）返回空值 ⇒ 交回 medium 以上
- **W126b**：状态读取器**不受"有日志"降权保护**

负向测试两条都过：

| 用例 | 期望 | 实测 |
|---|---|---|
| 状态读取器 + 有日志 + 同类有写方法 | 不降 low | ✅ medium / state-reader |
| 无写方法的普通读取器 + 有日志（对照） | 降 low | ✅ low |

对照组保留——**没有过度收紧**。

## 六、本轮最该记住的一条

**降噪台账建对了——它第一次抓到误杀，而漏的恰是已确证缺陷。**

第十四轮建台账时我写过：

> 每一次"命中变少"都是一次"这些不是缺陷"的判断。只要有一条判据是错的，
> 就会系统性漏掉一类真缺陷，且**只表现为"命中少了"，不会报错**。

这个担心成真了。而且**漏的不是某个我没看过的角落，是 M6——我自己手工确证过、
写进台账、打过补丁的缺陷**。它一直在 low 里躺着，因为判据说"有日志，属有意降级"。

两条推论：

1. **判据的语义错误比判据的漏报更危险**。漏报至少是"没说"，误降是"说了没事"。
2. **误杀要靠独立判据才能发现**。W109 自己永远不会发现它错了——
   它对自己的结论永远自洽。我是用"调用方有没有判空"这个**外部判据**才抓到的。

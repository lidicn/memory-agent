## 一、M3 结论：生产部署下假设不成立（但需你确认一件事）

### 证据链

| 证据 | 来源 | 结论 |
|---|---|---|
| `NAS="lidicn@192.168.2.200"`、`NAS_SRC="/vol1/1000/docker/memory-agent"` | `deploy_nas.sh` | 容器跑在 NAS **主机**上 |
| `docker restart memory-agent` 在 NAS 上执行 | `deploy_nas.sh` | 同上 |
| compose 位于 `/vol1/1000/docker/memory-agent` | `deploy_nas.sh` | `./data` = 该目录下 `data/` |
| "MA 运行在 NAS 上（J3455，SQLite 471MB，112 万条事件）" | `doc/QA-MA-全量MCP测试提示词.md` | 生产实况 |

**`/vol1` 是群晖本地存储池，不是 NFS/SMB 网络挂载** ⇒
**容器与数据同机，SQLite 官方警告的"网络文件系统 advisory lock 不可靠"在生产路径上不适用。**

### 深度研究的核心结论（供参考）

`SQLite数据库损坏根因研究.md` 给出：**NFS/SMB/CIFS 上跑 WAL 是最高风险级，官方明确 WAL 不能用于网络文件系统**。但结论落到本项目要分场景：

- **生产（NAS 主机本地 /vol1）**：不适用，M3 基本排除
- **开发机 `E:\NAS\memory-agent\doc`**：这是**真 SMB 映射**。若有人在开发机上跑 compose，**那就是标准高危场景**

**需要你确认的只剩一件事**：出问题的那台机器，是不是在开发机（E: 盘映射）上跑的？
如果只在 NAS 上跑，M3 可以关闭。

## 二、M9【高危·已修复验证】真正的候选根因

### 代码与注释不符

`runtime.py:398` 注释写着：

> checkpoint 被阻塞时跳过本轮，不影响主流程

而 `store.py:660` 的实现是：

```python
with self._lock:                              # ← Python RLock，无超时
    self._conn.execute("PRAGMA wal_checkpoint(TRUNCATE)")
```

**`with` 会无限等待，"跳过"这个承诺代码从未实现。**

### 对照实测

| | 业务持锁 8s 时 checkpoint | 判定 |
|---|---|---|
| **原版** | 耗时 **7.7s**，仍执行 | ❌ 阻塞等待，未跳过 |
| **补丁版** | 耗时 **5.0s**，返回 `False` | ✅ 跳过，不阻塞业务 |

反向同样成立（实测）：**checkpoint 持锁期间，一个 `SELECT 1` 也等了 2.8s。**

### 为什么这条能解释你的主诉

```
471MB 库 + J3455 低功耗 CPU
      ↓
每小时 checkpoint(TRUNCATE) 耗时可能数十秒
      ↓
持锁期间所有业务读写被阻塞（无超时）
      ↓
服务周期性冻结
      ↓  ← 这一步是关键
被当成"数据库出错"，人工/SIGKILL 重启容器
      ↓
打断 WAL 写入 → 真的损坏
      ↓
下次启动 integrity 判红 → 无备份(M5) 或恢复分支崩(M1) → 起不来
```

**前四轮修的 M1/M2/M5/M6/M7 全在链条尾部（损坏后救不回来）；M9 在链条头部（为什么会损坏）。**

> 链条中"471MB 上 checkpoint 实际耗时"是**推断**，未在真实规模下实测；
> 已实测的是"持锁即阻塞、无超时、不跳过"这个机制本身。

### 修复

`checkpoint(timeout=5.0)`：`acquire(timeout=...)` 拿不到锁就跳过本轮，
**与注释原本的承诺一致**。

## 四、M10【低】启动期全表 UPDATE

`store.py:1454`：

```sql
UPDATE idempotency_keys
   SET expires_at = expires_at || ' 23:59:59'
 WHERE length(expires_at) = 10
```

`length()` **无法走索引** ⇒ 每次启动全表扫描，且无 `schema_version` 判据（每次都跑）。
`init_schema` 共 632 行、61 条 DDL（44 CREATE / 14 ALTER）。

属启动性能风险，非正确性缺陷；未实测耗时。

## 八、本轮最该记住的一条

**M9 是被"注释与代码不符"这条线索钓出来的。**

项目自己的注释承诺了"跳过"，而实现是无限等待。这类缺陷静态规则查不出来
（`with self._lock:` 是完全正常的写法），只能靠**读注释 → 质疑 → 实测**。

这是"缓释标记答非所问"信号在本期的第一次兑现——上一期它帮我们发现了
AutoForge 的 F10 和 doubao-butler 的 D6。三次的共同点是：
**注释描述的是作者的意图，而防护是否生效取决于实际执行路径。**

顺带记一个我自己的失误：M9 补丁第一版我写错了 acquire 逻辑（重复获取锁），
是跑验证时发现的。**补丁必须过实测，不能只过语法检查** —— 这和上一期
D16 那次"参数传了但守卫没插"是同一个教训。

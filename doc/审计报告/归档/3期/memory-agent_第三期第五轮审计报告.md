## 一、R1【证伪】checkpoint 并不慢——第四轮推断不成立

### 第四轮的推断

> 471MB 库 + J3455 低功耗 CPU → 每小时 checkpoint(TRUNCATE) 耗时数十秒
> → 持锁阻塞所有业务 → 服务周期性冻结 → 被误判"数据库出错"重启
> → SIGKILL 打断 WAL → 真的损坏 → 起不来

### 第五轮实测

| 场景 | 结果 |
|---|---|
| 库 109MB / WAL 708KB | checkpoint **1ms** |
| 库 11MB / WAL 0.2MB | **0.4ms** |
| 库 11MB / WAL 5.3MB | **2.9ms** |
| 库 36MB（30 万行） | **1ms** |

**固定库规模只改 WAL（0.2MB → 5MB）耗时从 0.4ms 到 2.9ms；
而库从 11MB 涨到 109MB 耗时没有变化。**

⇒ **checkpoint 耗时由 WAL 脏页量决定，与库大小无关，且是毫秒级。**

### 结论

推断的**核心环节（checkpoint 慢）不成立**。
机制部分（RLock 无超时、注释承诺的"跳过"未实现）**仍然成立**，实测持锁 8s 时 checkpoint 等满 7.7s。

**M9 严重度 high → medium**，补丁保留（让代码符合注释，防御性），但不该再被当成"容器起不来的根因"。

## 二、R2【证伪】purge_old 的 VACUUM 不是性能问题

`store.py:4655` 在**全局锁内**执行 `VACUUM`（阈值：删除 ≥ 5 万行）。
本轮假设"大库 VACUUM 造成长时间冻结"。

### 实测

| 规模 | DELETE 分批 | VACUUM | VACUUM 占比 |
|---|---|---|---|
| 6 万行 / 7MB | 0.08s | **0.00s** | 1% |
| 20 万行 / 24MB | 0.53s | **0.00s** | 0% |
| 40 万行 / 49MB | 1.24s | **0.00s** | 0% |

单独确认：20 万行库 `VACUUM` 耗时 **0.7ms**，`page_count` 从数万降到 3
（**确认真的执行了**，不是 no-op）。

⇒ **VACUUM 不是耗时主体，DELETE 才是。而 DELETE 已经分批（P0-7，每批 5000 行放锁）。**

### 顺带纠正一个测量假象

早先测到"业务查询最大阻塞 1075ms"，我一度以为是锁等待。
**实际是 GIL 调度延迟** —— `purge_old` 在 `to_thread` 里密集占用 CPU，
探针线程抢不到 GIL，测出来的"阻塞"不是锁竞争。

**教训：多线程实测里，`time.time()` 差值包含 GIL 调度，不能直接当成锁等待时间。**

## 四、W97【工作流】长事务 / 锁内重型操作检测

新增 `core/analyzers/long_txn_defects.py`。

**为什么需要它**：M9 的教训是"静态规则查不出 `with self._lock:` 有什么问题"，
必须判断**锁区间里跑了什么**。项目自己就记录过一次真实事故：

> `purge_old` docstring：实测 30 万行一次删完持锁 **143 秒**，
> 期间采集线程、WebUI、MCP 全部排队（一个并发读者实测等了 143151 ms）

检测两类：
1. 锁内的**非 SQL 慢操作**（sleep / 网络请求 / 子进程 / 文件读写）
2. 锁内的**重型 SQL**（无 WHERE 的 DELETE/UPDATE、全表 COUNT/聚合、VACUUM、REINDEX、executemany）

**负向测试已通过**：锁内 `sleep` 必报、锁外 `sleep` 不报。

### 跑本项目结果

```
high = 0        ← 锁内没有 sleep/网络/子进程/文件读写
medium = 21
```

**high=0 是个好消息**：说明锁内确实没有慢操作，项目在这一点上做得扎实。

21 条 medium 主要是全表 COUNT 与 UPDATE（部分为多行 SQL 的误报），
其中 `stats()` 对 112 万行 `events` 做 `SELECT COUNT(*) FROM events`（锁内）
值得留意，但单次百毫秒级，不构成冻结。

## 五、本轮判定的假阳性

**CONC-03（async 函数内 subprocess.Popen 卡死事件循环）** —— `api/system_routes.py:179`

两条理由都成立：
1. **路径不可达**：`apply_update` 前置检查 REPO_DIR 可写性，线上 `src` 是 `:ro` 只读挂载，
   注释明确"在线更新已停用，改由宿主 deploy_nas.sh 承担" ⇒ `Popen` 那行执行不到
2. **Popen 本身非阻塞**：`Popen` 只启动进程并立即返回，不像 `run`/`wait` 会阻塞

⇒ 判假阳性，不立缺陷。

**CONC-08（4 条属性锁覆盖不一致）**：`self.templates` / `self.disabled` 等
**实例属性**（非 SQLite 连接）在 `save()` 持锁写、`_load()` 裸写。
与 W93（SQLite 连接锁覆盖 0 处问题）**不冲突**，是不同对象。
构造期单线程调用，当前不活跃。

- `./data` 实际挂载类型 —— 仍是唯一待你确认的部署事实

**这些都需要生产环境的运行时信息，代码审计给不出答案。**

## 九、本轮最该记住的一条

**我连续两轮的推断都被实测推翻了，而这是好事。**

第四轮我看注释说"checkpoint 被阻塞时跳过"、代码没实现，
就顺着推出"checkpoint 慢 → 冻结 → 误判重启 → 损坏"这条完整链条。
链条逻辑自洽、每一步听起来都合理——**唯独没有一步是实测的**。

第五轮实测：checkpoint 只要 1ms。链条第一段就断了。

**教训不是"别推理"，是"推断必须标注为推断，并且尽快实测"。**
第四轮报告里我确实标了"这是推断"，这没错；错的是把它放进了
"最可能的根因"这个位置，而它当时没有任何测量支撑。

对比之下，M1/M2/M6/M7 那几条之所以可信，是因为**每条都有对照实测表**
（原版 vs 补丁版，数字摆在那里）。

**一条推断无论多自洽，在拿到实测之前都不该被当成根因。**

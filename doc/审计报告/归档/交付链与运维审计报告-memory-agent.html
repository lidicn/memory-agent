H1 · docker-compose.yml 内嵌了硬编码的 JWT_SECRET 默认值 高

位置docker-compose.yml:37 — JWT_SECRET: "${JWT_SECRET:-<内置默认值>}"（默认值长度 28、纯字母数字，本报告不引用其值）。

触发条件 部署方的 .env 未设置 JWT_SECRET 时，compose 变量插值取该内置默认值，容器以这个已随公开仓库发布的固定密钥签发/校验会话令牌。

实际影响 任何拿到仓库的人都能用同一密钥伪造合法 JWT，绕过认证拿到管理员面（服务把 JWT 作为 WebUI 会话凭据）。install.sh:35-44 只在不存 .env 时复制 .env.example，而 .env.example:32 的 JWT_SECRET 也是一个固定占位串——两个默认值叠加，意味着「照文档装完」极易带上可预测密钥。

修复建议 去掉默认值，改强制提供：JWT_SECRET: "${JWT_SECRET:?JWT_SECRET 未设置，请写入 .env}"；或在入口脚本里随机生成并落盘后再启动。同时把 .env.example 的占位串替换为明确的「必须生成」提示并在 install.sh 里校验非空。

H2 · deploy_nas.sh 的部署前核验行已经过期，在 set -e 下会中止部署 高

位置deploy_nas.sh:56-58，其中第 57 行 grep -n 'repo:rw' docker-compose.yml。脚本第 3 行是 set -e。

触发条件 该脚本在 git checkout -f origin/main -- .（第 52 行）之后、docker compose up -d --build（第 61 行）之前执行这三条 grep 自检。实测 findstr /C:"repo:rw" docker-compose.yml 退出码为 1（无匹配）：compose 第 45 行已注明「在线更新已停用」，卷挂载里没有 repo:rw。第 56 行 grep -n git Dockerfile、第 58 行 grep -n vlm_endpoint_path src/memory_agent/config.py 均能命中，唯独第 57 行必然失败。

实际影响 set -e 下失败的命令直接终止脚本。于是这条「备份→同步→核验→重建→启动」的部署链会在核验段退出，备份与代码同步已发生、但容器重建/重启永远不会执行，得到「看似部署了、实际还在跑旧镜像」的半成品状态，且退出码非零容易被当成失败而不是「卡在中途」。同一根因还波及文档：README.md:175 仍写「docker-compose 已配置 .:/repo:rw」，与 compose 现状矛盾（并入 M7）。

修复建议 删除或改写第 57 行（该挂载已废弃），或把三条核验改成不会因无匹配而中断的写法（如 grep -q ... || echo "核验未命中"）；同时把「核验」整体移到 up --build 之后，避免任何自检失败就把部署卡在中间态。

H3 · Node-RED 净水器流程解析的字段与后端返回结构完全对不上 高

位置 流程侧 nodered/water_purifier_flow.json:84（名为「格式化报告」的 function 节点函数体）；后端侧 src/memory_agent/api/nr_routes.py:207。

触发条件 流程 HTTP 节点固定 POST http://192.168.2.200:8086/api/analyze/water_purifier（流程第 58 行），拿到后端 JSON 后由 parse_result 解析。

实际影响 后端 analyze_water_purifier 返回 ok({"message":"分析完成","data": result})，result 是列表，每项键为 date / count / total_volume_l / avg_tds_in / avg_tds_out / tds_reduction_pct（nr_routes.py:193-206）；无历史数据时返回 ok({"message":"无历史数据","data":[]})（第 152 行）。而流程函数读的是 data.entity_id / data.start_time / data.end_time / data.total_records / data.days / data.daily，并且逐日取 day.total_l——这些键后端一个都不返回。逐条后果：

  • 表头几个字段渲染成 undefined（如「实体: undefined」「记录: undefined条 / undefined天」）；
  • for (const day of data.daily) 因 data.daily 为 undefined 直接抛 TypeError，function 节点报错，后续 ui_text_water、debug 全部收不到结果——即题目所问的「界面调不通」；
  • 即便容器取值不炸，单位键也错位：流程期待 day.total_l，后端给的是 total_volume_l。

修复建议 二选一对齐：① 改流程函数（推荐，后端注释 nr_routes.py:7 明确「响应结构不许变更」），把 data.daily→data.data、day.total_l→day.total_volume_l，并删除后端不提供的 entity_id/start_time/end_time/total_records/days 或改为本地推导（daily.length / 数据条数=Σcount）；② 或在后端补一个兼容层返回流程期望的字段。改完必须回归一遍该流。

H4 · 仓库内提交了真实可用的服务令牌 高

位置scripts/test_ingest.sh:3（TOKEN="…"）、scripts/test_ingest_auth.sh:3（TOKEN="…"）、scripts/investigate_token_loss.sh:27（token = "…"，写在内嵌 python 里用于 store.verify()）。本报告不引用其值。

触发条件 这三个脚本随 git 入库并推到远端。

实际影响 令牌是真实的服务令牌（用于调用 /api/metrics/ingest 等），且 investigate_token_loss.sh 里的那枚被用于验证服务端 ServiceTokenStore.verify()——说明它是能通过校验的活令牌。仓库一旦公开/被拉取，令牌即可被用来冒充调用方写入指标。.dockerignore:12-14 试图用 scripts/*token* 之类的规则把它们挡在镜像外，但这两条文件名不含 token/secret/debug，规则匹配不到；而且 Dockerfile 根本不 COPY scripts/（见 L4），所以那道防线两头都不成立。

修复建议 立即在服务端吊销/轮换这三枚令牌；脚本改为从环境变量读取（TOKEN="${MA_INGEST_TOKEN:?}"）；把令牌从 git 历史中清除（git filter-repo / BFG），并加一条 pre-commit/CI 的密钥扫描（如 gitleaks）作为长期闸门。

M1 · CI 永久忽略 4 个测试文件，"绿"不覆盖它们 中

位置.github/workflows/ci.yml:39-42：--ignore=tests/test_mqtt_bridge.py、test_ha_assist.py、test_quality_gates.py、test_vlm_gate.py。

影响 这 4 个文件在 CI 里永不执行，CI 绿灯对它们等于「没跑」。其中 test_quality_gates.py 正是 homesdk 门禁的入口（见 M5），双重失效：既被 --ignore 排除，门禁本体也已在 gates.yml 降级。

修复建议 逐个给出忽略理由与恢复计划：能跑的补齐依赖后从 ignore 列表移出；确实依赖外部环境的，标注 @pytest.mark.skipif 并在 CI 里显示 skip 计数，而不是无声 --ignore。

M2 · 全新环境下 bind-mount 的 ./data 归属可能阻断首次启动 中

位置Dockerfile:28-33（mkdir -p /data/... && chown -R 10001:10001 /data /app，随后 USER 10001:10001）；docker-compose.yml:43（./data:/data）；install.sh 全程不预处理 data/。

触发条件 干净机器上首次 docker compose up，宿主机没有 ./data 目录时，Docker 会自动以 root:root 创建它并覆盖镜像内已被 chown 的 /data。

实际影响 以 uid 10001 运行的进程对挂载进来的 /data 可能无写权限，SQLite 建库/写 WAL 失败，服务起不来。需运行时确认（本机无 docker、生产在 NAS，未能实测；NAS 上能跑，可能因为该目录是手工预建并改过属主）。

修复建议 在 install.sh / deploy 脚本里预建并赋权：mkdir -p data && chown -R 10001:10001 data（或在 compose 里用命名卷 + 镜像内 chown）；README「一键安装」补一条「首次需确保 data/ 属主为 10001」。

M3 · 端口绑定写死到 192.168.2.200，"一键安装"实际不可移植 中

位置docker-compose.yml:8（"192.168.2.200:8086:8000"）、第 63-64 行（192.168.2.200:9080:80 / 192.168.2.200:9443:443）。

影响 绑定的源地址是一个具体主机 IP。在任何不是 192.168.2.200 的机器上，docker compose up 会因 cannot assign requested address 失败——而 install.sh:53 却承诺 WebUI 在 http://<本机IP>:8086、README.md:77 同样写 http://<宿主机IP>:8086。文档承诺的「一键安装给任意人用」与 compose 的实际写法冲突。

修复建议 改为可参数化："${BIND_IP:-0.0.0.0}:8086:8000"，默认绑全部网卡；需要避开 Tailscale 冲突时再由 .env 覆盖。caddy 的 9080/9443 同理。

M4 · 两个同名 deploy_nas.sh 语义不同，且根脚本内嵌个人路径/固定 NAS 地址 中

位置 根 deploy_nas.sh（在 NAS 上、cd /vol1/1000/docker/memory-agent 后 git checkout -f origin/main -- . 全量覆盖，第 4/48-52 行）；scripts/deploy_nas.sh（在 Windows 本机、scp 增量推送，第 13-20 行硬编码 C:/Users/lidicn/.ssh/...、lidicn@192.168.2.200、基线 BASE="a879dd3"）。

影响 同名两脚本、运行位置与策略相反（一个全量覆盖、一个增量 diff），运维时极易互串；scripts/deploy_nas.sh 把用户名、内网 IP、SSH 私钥路径写死在仓里，既不可移植也泄露内网拓扑；基线 ref a879dd3 是写死的提交号（实测存在），一旦基线漂移增量范围就失真。

修复建议 重命名以区分（如 deploy_local_to_nas.sh / deploy_on_nas.sh）；把 SSH/IP/基线改为环境变量或参数；README 里指明「在哪台机跑、用哪个」。

M5 · gates.sh 依赖的外部门禁 CLI 已不存在，本地门禁与 CI 脱节 中

位置gates.sh:12 homesdk-gates . --no-smoke；.gates.toml、.gates-baseline.txt 为其输入；对照 .github/workflows/gates.yml:7-8 注释「原 homesdk-gates AST 规则门禁因 homesdk 尚未发布到 GitHub 而暂时降级为 compileall + pyflakes」。

修复建议 要么删除 gates.sh + 两个 .gates* 文件，要么在脚本开头显式检测 homesdk-gates 不可用时给出清晰报错并指向 CI 的 pyflakes 门禁，避免「本地绿/CI 口径不一致」的错觉。

M6 · 净水器模板文档的解析口径与后端实现不一致 中

位置templates/water_purifier_daily.md:4-6,19-27 vs src/memory_agent/api/nr_routes.py:156-167。

影响 模板写：属性名是 出水数据，格式 开始-结束-出水量mL-入水TDS,出水TDS，且代码示例从 parts[2] 取 volume、从 parts[3] 取 tds_out、从 parts[2].split(",")[1] 取 tds_in。后端实际：属性名 out_data（nr_routes.py:159）、要求 state == "on"（第 156 行）、volume 取 parts[2]、TDS 对取 parts[3].split(",")（第 165-167 行）。按模板写的解析器拿不到 TDS（键名与切分位置都不同），会得到空/零值统计。

修复建议 以代码为准更新模板（属性名 out_data、补 state=on 条件、按 parts[3] 切 TDS），或反过来在代码注释里锁定口径并让模板引用它。

M7 · README 把已停用的「WebUI 在线更新」描述为可用 中

位置README.md:61（特性列表）、README.md:165-175（专节，明确要求 .:/repo:rw 挂载）；对照 docker-compose.yml:45 注释「在线更新已停用：改由宿主 deploy_nas.sh 承担」且无 /repo 挂载；src/memory_agent/api/system_routes.py 与 static/js/api.js:271-273 仍保留 /api/system/update* 端点与 UI。

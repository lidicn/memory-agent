## 一、P1：同一 7 天窗口，四个工具四个 total_events（D31）

窗口均为 2026-10-01 08:00 至 2026-10-08 08:00：

| 工具 | total_events |
|---|---|
| get_data_coverage(days=7) | 209964 |
| get_behavior_summary(days=7, behavior_only=false) | 209968 |
| get_behavior_insights_compare(compare_days=7).current | 210141 |
| get_user_persona(days=7)（R1 实测） | 210254 |

**最大差 290 条**（210254 - 209964）。四个工具、四个数字、同一个窗口。

使用者无法回答一个最基础的问题：**这 7 天到底有多少条事件？**

差异来源未披露：是采样上限、是遥测过滤口径不同、还是时间边界取法不同——工具都没说明。这与 R3-D20（avg_per_day 分母不一致）同根，但更严重：这里是**总量**不一致。

## 二、P1：days=7 却返回 8 天（D32）

    get_data_coverage(days=7)
    → total_days: 8, active_days: 8
    → days: [10-01, 10-02, 10-03, 10-04, 10-05, 10-06, 10-07, 10-08]
    → day_coverage: 1.0

请求 7 天，返回 8 天，且判为「覆盖完整 1.0」。同一问题在 R3-D20 的 `get_behavior_insights_compare` 也出现过（active_days=8 而 avg 按 7 除）。

**两个独立工具都犯同一错误**，说明这不是单点 bug，而是**时间窗口切分的公共实现问题**。

另注：10-08 只有 0-7 共 8 小时（窗口截断），hour_coverage=0.875，但 day_coverage 仍报 1.0。

## 三、P2：房间命名分裂（D33）

    get_behavior_summary 房间分布：
      主卧:    9625
      主卧室:  1815      ← 疑似同一房间的另一种写法
      房间:    2565      ← 一个叫「房间」的房间
      杂物间:     8

同时存在「主卧」与「主卧室」，另有名字本身就是「房间」的区域。

对照 R3：`mine_behavior_process` 的 reviewed_rooms 含「主卧室浴室」，skipped_rooms 含「主卧室」——同一实体体系里，房间名**没有规范化**。

**危害**：任何按房间聚合的统计（房间分布、room_distribution 归因、房间移动规则）都会被拆分到多个别名下，指标系统性偏低。R5-D27 里「房间移动」召回率仅 31.4%，房间名分裂是可能的诱因之一。

## 四、P2：模板产物已知损坏，复查未修（D34）

    list_analysis_templates() → 5 个模板
    xbox_daily_usage:
      default_days: 2

R1 的 bug 库已记录 `bug_15685edda3`：该模板 duration 指标计算失败（can't compare offset-naive and offset-aware datetimes），`{total_human}` 渲染为空，输出「累计游戏约 。」

**本轮复查：模板仍在列，未被删除也未修复。** 用户若按此模板出报告，会拿到一句语法残缺的话。

另一个模板 `study_room_work_duration` 的 `default_days: 0`——0 天的默认窗口语义未定义，未传 days 时的行为不可预期。

## 五、P2：behavior_only 的过滤语义无法自证（D35）

    get_behavior_summary(days=7, behavior_only=false)
    → telemetry_excluded: 0
    → top_entities: 前 20 全部为 sensor.*
    → hint: \"⚠️ 含遥测数据：功率传感器每分钟一条，小时分布会被拍平，建议 behavior_only=true\"

问题：`telemetry_excluded=0` 在两种情形下取值相同——

1. 请求了不过滤（behavior_only=false）
2. 过滤了但恰好没有遥测可剔

调用方**无法区分**这两种情况。而工具自己在 hint 里承认「含遥测」，说明它知道数据被污染，只是没有把「本次未过滤」这个事实编码进 `telemetry_excluded`。

与 R1-D3、R3-D18、R4-D22 同根：遥测污染在全链路反复出现，各工具的应对策略互不一致。

## 六、P3：技能与实际能力脱节（D36）

    list_skills() → 3 个
      insight v4, updated_at 2026-08-06
        description: \"...通过 memory-agent 的 MCP 工具获取服务端已算好的洞察，
                      不要自己拉原始事件硬算。\"

该技能的核心指令是「信任服务端洞察」。但 R1-R5 已证明服务端洞察存在：

- infer_activities 语义层 0 命中（R3-D18）
- infer_behavior_intent 直接报错（R3-D19）
- 画像结论随窗口漂移（R1-D9）
- 规则召回率 0（R5-D27）

**技能在教 Agent 信任一个不可靠的数据源**，且技能版本停留在 2026-08-06，两个月未更新。

### 修复（不采纳"整体切回 legacy"）

README 的最高优先级建议是把 `insights/__init__.py` 的 `InsightService` 指回 legacy，
"一行改动换回四条功能线"。**实测数据不支持这个做法**：

```
公开方法：新 36 / legacy 31 / 同名 28
同名 28 个里 24 个实现路径不同（AST 比对 return 调用点，不是键位全等比对）
仅新实现有的 8 个方法，生产侧调用点：7 个为 0，refresh 仅 1（包内 parser/entity.py:186）
```

即：一行切回会同时改掉 **28 个同名公开方法**的行为，而它真正要救的只有 11 个成员。
改为**组合 + 显式转发**，把改动面压到"恰好恢复生产在用的那条缝"：

| 文件 | 改动 |
|---|---|
| `insights/api.py` | `InsightService` 增 `self.store`、`self.legacy = LegacyInsightService(raw_config, store)`；新增模块级 `LEGACY_CONTRACT_MEMBERS` 清单 + 10 个显式转发方法。**转发方法一律不套 `_degrade`**——契约成员失败必须抛，不许再降级成空信封 |
| `activity_inference.py:_tags_of` | 去掉 `hasattr` + `except: pass` + `return set()`，直接用规范实现 `insights.utils.tags_of`（顺带消掉一条门禁基线） |
| `activity_inference.py:_iter_events` | 去掉 `hasattr` 分支与被截断的 `query_events(limit=…)` 兜底，直接 `iter_all_events(store.query_events, …)` 真分页 |
| `tests/test_insights_facade_contract.py`（新增，9 条） | 见下 |

**没用 `__getattr__` 动态转发**，这是刻意的：动态派发会让"属性永远存在"，
而 P0-5 的病根正是"看起来存在、实际返回空"。契约测试要能被静态扫描抓住，就必须是真的方法。

### 三条属于"跑一次全绿、上线后冻站"的根因（对方只报了症状）

1. **P0-6 不是 GROUP BY 慢，是 `MAX(room)` / `MAX(domain)` 逐行回表**。同一个库上拆开量：
   只 `COUNT(*)` 114.4 ms；`GROUP BY entity_id + COUNT` 554.4 ms；加 `MAX(ts)` 723.1 ms；
   加 `MAX(room)` **14,959.7 ms**；加 `MAX(domain)` **20,911.0 ms**。
   所以三个候选修法的实测是：`NOT INDEXED` 1,356.0 ms / 覆盖索引 **452.7 ms** / 两段式 513.3 ms。
   选覆盖索引；写放大代价实测含覆盖 2,638.0 ms vs 不含 2,753.1 ms（每 5000 行）——**在噪声内**。
2. **复合视图不吃谓词下推**：`SELECT … FROM unified_events ORDER BY server_ts LIMIT 100`
   必须物化三路全部候选再排序。改成三路各自 `WITH _ueN AS (… ORDER BY … LIMIT ?)` 再外层归并，
   页查询从 1.4–2.5 s 降到 86 ms。SQLite 语法坑（都在 3.45.3 上撞过）：
   `FROM ((A ORDER BY …) UNION ALL (B …))` 是解析错误；裸复合查询里各分支不能带 `ORDER BY`；
   **只有 CTE 形式能同时保留"分支内 Top-N + 全局 Top-N"**，且全局 Top-N 在每一支的 Top-N 之内。
3. **锁的代价不在查询本身，而在它持锁的时间**：并发探针实测——
   旧读循环下读者 6 秒只完成 2 次、写入最大延迟 **4,203 ms**；
   新查询下读者完成 **57 次**、写入最大延迟降到 **575 ms**（P95 升到 89.1 ms，因为锁被更频繁地短暂占用）。
   无并发基线写入 P50 = 0.27 ms。

### 17.3 实现选了什么口径，为什么不选另一个

| 决定 | 理由 |
|---|---|
| 时钟用**家庭墙钟**，不用 `time.monotonic()` | 单调时钟从进程 0 起算：冷却配得比 uptime 大就永久吞掉首次触发——第一轮审计 P1-1（`announcer` / `perception_rules` 的 `0.0` 哨兵）就是这个形状。墙钟没有 uptime 依赖，且与 `rule_trigger_history.triggered_at` **同一个框**，重启后能直接续上。墙钟口径沿用 `store.now_local(tz_offset_hours)`，不引入 UTC/机器时区混算（BUG-TZ1 同源缺陷）。 |
| 实时路径按「现在」判、并从触发历史续窗口；**批量回放按事件自身墙钟判、不读历史** | 与 `count` 触发窗口同一个 `now_ts is None` 分界（`match_event` 的既有语义）。历史行的 `triggered_at` 是**当时**的真实墙钟（≥ 事件时刻），拿它判「事件时刻」会把整轮 dry_run 回放吞成 0 触发——`live=` 那道闸由 `M2` 变异证明是承重的。 |
| 坏数值（`""` / `"abc"` / 负数）读成「不冷却」 | 拿坏数据抑制触发 = 静默丢掉家里的告警，比多播一条危险。`None` 走不到盘上（该列 `NOT NULL`），只在纯内存字典层读成 0。 |
| 冷却在**派发前**记账，试运行同样占窗 | 与 `perception_rules` 同口径：动作执行失败不该让下一条事件立刻重播；观察期的触发计数因此等于转正后实际会发出的条数，而不是原始命中次数。 |
| 窗口是半开区间 `[触发, 触发+冷却)` | 满窗那一帧放行（`12:30:00` 对 `cd=1800` 触发），并把窗往后挪。用例把 `12:29:59 / 12:30:00 / 12:31:00` 三帧都钉住了。 |

不出事件载荷、不出凭据。

## 十九、周期 sweep 的 `database disk image is malformed`：FTS 幽灵索引，坏索引启动即自愈（`c7aab24`）

### 19.1 症状与定位链

告警字面是「数据库损坏」。实测**主库没坏**，坏的是挂在它上面的关键词索引：

| 判据 | 读数 |
|---|---|
| `PRAGMA integrity_check`（主库） | `ok` |
| FTS5 自己的 `INSERT INTO agent_memories_fts(agent_memories_fts) VALUES('integrity-check',1)` | 抛 `database disk image is malformed` |
| `agent_memories_fts_docsize` 行数 | **0**（真被索引的文档数 = 0） |
| `agent_memories_fts_data` 行数 | 2（只有表头形状，没有倒排数据） |
| `SELECT COUNT(*) FROM agent_memories_fts` | **247** ← 骗人的读数 |
| `/data/config.json` → `agent_sweep_interval_seconds` | 60（代码默认 86400 且无 env 映射，所以生产每 60 秒撞一次） |
| 48 小时窗口内 `周期 sweep 异常` | **664 次，成功 0 次**；单个探针窗口连续 59 轮全失败 |
| 48 小时窗口内 `FTS5 rebuild 完成` | **0 次** |

因果闭合：外部内容表（`content='agent_memories'`）的索引是空的，但 `_au`/`_ad` 触发器照常装载，
它们的 `'delete'` 分支要按 rowid 去索引里删旧条目——索引里没有 → SQLite 报 malformed。
于是 **`agent_memories` 上每一条 UPDATE/DELETE 都必失败**，而 INSERT 不受影响
（这就是为什么建库、写记忆看起来一切正常，只有状态迁移路径在流血）。

### 19.2 死守卫从哪来：一句写进审计文档的建议

`增量审计_FTS5索引失效_20260930.md:62` 当时这样建议：

> 首次建表时该语句为空操作；仅在已有数据时回填，代价 O(索引)。
> 若担心大库耗时，可改为「仅当 FTS 行数为 0 且主表非空时 rebuild」。

同一份文档 `:67` 记录了"实际代码中不存在 rebuild 调用"。修复时把这句建议照抄成了条件：

```python
_fts_count  = SELECT COUNT(*) FROM agent_memories_fts      # 外部内容表 → 走的是内容表
_main_count = SELECT COUNT(*) FROM agent_memories
if _fts_count == 0 and _main_count > 0:                    # 247 == 0 永假 → 守卫永不成立
```

**`COUNT(*)` 打在 external-content FTS5 上是由内容表服务的**：索引完全空也返回主表行数。
所以 `_fts_count` 永远等于 `_main_count`，两个条件互斥，rebuild 一行都不会执行——
上一轮"按建议加了优化"，实际是把唯一的自愈路径焊死了。这也是 12 个测试文件和 1000+ 条用例
都没抓住它的原因：现有用例只做 INSERT（触发器新写的那部分索引确实是对的），
没有任何一条断言 UPDATE/DELETE 能活着走完，更没有断言**重启之后**还能。

### 19.3 修复

判据换成 FTS5 自己的话，重建无条件执行：

- `Store._fts_index_healthy(conn)`：跑 `integrity-check`，通过才算健康（缺表也算不健康）。
  docstring 里写死了"判据不许换成 `COUNT(*) FROM agent_memories_fts`"和原因。
  检查前先 `conn.commit()`，失败才 `rollback`——否则一次索引检查会连带丢掉同事务里别的迁移语句。
- `Store._rebuild_agent_memory_fts(conn)`：三条触发器先 DROP → DROP 表 → 按
  `trigram`→`unicode61` 重建 → **无条件 `rebuild` 回填** → 再跑一次 `integrity-check` 才算成。
  注释写明"新建的 external-content 表索引是空的，不回填就会让写触发器的 `'delete'` 分支

## 二十三、`_sanitize_pii` 的片段残留：PII 审计 S1 的"结果仍是全掩"实测不成立（2026-10-04）

按"审计里未闭环项"逐条复核时捡回的一条。`反馈PII脱敏审计_20261001.md` §四 S1 当年的结论是

三个成因，各自独立：
1. **手机号规则没有数字边界守卫**——`(1[3-9]\d)\d{4}(\d{4})` 会在 18 位身份证**内部**命中 11 位，
   把它拦腰咬断。同仓 `feedback_pack.py:20` / `negative_samples.py:51` 早就写了 `(?<!\d)…(?!\d)`，
   只有 `store.py` 这份没有——两份实现分头演化就是这个形状的来处。
2. **身份证规则是裸的 18 位数字** `(\d{6})\d{8}(\d{4})`，不校验世纪/月/日，所以任何 ≥18 位数字串都被咬走 18 位、留尾巴。
3. **邮箱规则的 `[\w.]*` 里 `\w` 认中文**，且 `{2}` 下限把单字符本地名整条放过。

修法（`store.py:4708-4719`，只做收紧、不放宽）：手机号加两端数字边界并容忍 `-`/空格分隔；
身份证按真值形状匹配（世纪 + 月 + 日 + 末位含 X）；邮箱本地名字符集限定 ASCII。
docstring 同步改成描述**真实**行为（"整段掩掉，原串每一位都不保留"），

### 修复（不采纳"整体切回 legacy"）

README 的最高优先级建议是把 `insights/__init__.py` 的 `InsightService` 指回 legacy，
"一行改动换回四条功能线"。**实测数据不支持这个做法**：

```

同名 28 个里 24 个实现路径不同（AST 比对 return 调用点，不是键位全等比对）
仅新实现有的 8 个方法，生产侧调用点：7 个为 0，refresh 仅 1（包内 parser/entity.py:186）
```

即：一行切回会同时改掉 **28 个同名公开方法**的行为，而它真正要救的只有 11 个成员。
改为**组合 + 显式转发**，把改动面压到"恰好恢复生产在用的那条缝"：

| 文件 | 改动 |
|---|---|
| `insights/api.py` | `InsightService` 增 `self.store`、`self.legacy = LegacyInsightService(raw_config, store)`；新增模块级 `LEGACY_CONTRACT_MEMBERS` 清单 + 10 个显式转发方法。**转发方法一律不套 `_degrade`**——契约成员失败必须抛，不许再降级成空信封 |
| `activity_inference.py:_tags_of` | 去掉 `hasattr` + `except: pass` + `return set()`，直接用规范实现 `insights.utils.tags_of`（顺带消掉一条门禁基线） |

**没用 `__getattr__` 动态转发**，这是刻意的：动态派发会让"属性永远存在"，
而 P0-5 的病根正是"看起来存在、实际返回空"。契约测试要能被静态扫描抓住，就必须是真的方法。

### 三条属于"跑一次全绿、上线后冻站"的根因（对方只报了症状）

1. **P0-6 不是 GROUP BY 慢，是 `MAX(room)` / `MAX(domain)` 逐行回表**。同一个库上拆开量：
   只 `COUNT(*)` 114.4 ms；`GROUP BY entity_id + COUNT` 554.4 ms；加 `MAX(ts)` 723.1 ms；
   加 `MAX(room)` **14,959.7 ms**；加 `MAX(domain)` **20,911.0 ms**。
   所以三个候选修法的实测是：`NOT INDEXED` 1,356.0 ms / 覆盖索引 **452.7 ms** / 两段式 513.3 ms。
   选覆盖索引；写放大代价实测含覆盖 2,638.0 ms vs 不含 2,753.1 ms（每 5000 行）——**在噪声内**。
2. **复合视图不吃谓词下推**：`SELECT … FROM unified_events ORDER BY server_ts LIMIT 100`
   必须物化三路全部候选再排序。改成三路各自 `WITH _ueN AS (… ORDER BY … LIMIT ?)` 再外层归并，
   页查询从 1.4–2.5 s 降到 86 ms。SQLite 语法坑（都在 3.45.3 上撞过）：
   `FROM ((A ORDER BY …) UNION ALL (B …))` 是解析错误；裸复合查询里各分支不能带 `ORDER BY`；
   **只有 CTE 形式能同时保留"分支内 Top-N + 全局 Top-N"**，且全局 Top-N 在每一支的 Top-N 之内。
3. **锁的代价不在查询本身，而在它持锁的时间**：并发探针实测——
   旧读循环下读者 6 秒只完成 2 次、写入最大延迟 **4,203 ms**；
   新查询下读者完成 **57 次**、写入最大延迟降到 **575 ms**（P95 升到 89.1 ms，因为锁被更频繁地短暂占用）。
   无并发基线写入 P50 = 0.27 ms。

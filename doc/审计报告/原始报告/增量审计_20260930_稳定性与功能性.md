## 一、新增发现

### 【NEW-P0-1】learning_store 独立 SQLite 连接，完全游离于 store 锁体系之外

- **位置**：`src/memory_agent/learning_store.py:67`
  ```python
  self._conn = sqlite3.connect(db_path, check_same_thread=False)
  ```
- **与前序的区别**：20260918 P1-3 指出的是「store.py 自己的 `_lock` 不保护 execute」。本项是**第二个连接对象**：learning_store 自建 `sqlite3.Connection`，既不共用 store 的 `RLock`，也未设 `busy_timeout`，与主库并发写。
- **失败场景**：采集/学习任务高峰时，两条连接并发写同一 WAL 库 → `sqlite3.OperationalError: database is locked`，且**没有 busy_timeout 兜底**（store.py 用的是 `timeout=30.0`）。表现为 WebUI 随机 500 或学习结果丢失。
- **修复**：learning_store 复用 store 的连接与锁；或至少补 `timeout=30.0` + `PRAGMA busy_timeout=30000`。

### 【NEW-P1-1】`json.loads` 无保护，数据库 JSON 列一损坏即抛未捕获异常

- **位置**（部分，`json.loads(` 命中 30+ 处）：`agent_memory.py:370/512/513`、`arena.py:131/171/212`、`behavior_predictor.py:44/102/175`、`candidate_promotion.py:121/763`、`learning_store.py:111/143`、`patterns.py:112`、`ha_db.py:193`、`intent_inference.py:142/171` 等
- **失败场景**：`tags_json` / `source_refs_json` / `entities_json` / `events_json` / `attrs_json` 等列在迁移或并发写中若被截断/写坏，`json.loads` 直接抛 `JSONDecodeError`。若调用点未包裹，则查询接口 500；若被宽泛 except 吞掉（本项目常见），则该行记忆**静默消失**——两种结局都不可接受。
- **修复**：统一一个 `safe_json_loads(s, default)` 辅助函数，解析失败记 WARNING 并返回默认值，让坏数据可见但不断链。

### 【NEW-P1-2】backup.py 以 `mode=ro` 打开 WAL 库，备份快照可能过期或直接失败

- **位置**：`src/memory_agent/backup.py:65`
  ```python
  conn = sqlite3.connect(f"file:{db_path}?mode=ro", uri=True)
  ```
- **失败场景**：主库是 WAL（`store.py:513`）。只读连接要看到已提交数据，必须能读 `-wal`/`-shm`。若权限不足或未做 WAL checkpoint，备份**读到旧快照**（丢最近写入）或报 `unable to open database file`。备份是最后一道防线，读到旧数据危害极大。
- **修复**：改用 `VACUUM INTO` 或 `sqlite3` 的在线备份 API，产生一致性快照，兼容 WAL。

### 【NEW-P1-3】动态 SQL 片段拼接（列名/子句），空集合或非法标识符即语法错误

- **位置**（均 `f"...{var}"` 拼接）：
  - `store.py:3011` `f"UPDATE members SET {cols} WHERE id = ?"`
  - `store.py:3285/3314/3360/3397` `f"... WHERE 1=1 {where}"`
  - `store.py:3640` `f"SELECT * FROM ({' '.join(sql)}) ..."`
  - `store.py:3716` `f"UPDATE collect_jobs SET {', '.join(sets)} WHERE id = ?"`
  - `store.py:3965/4093` `f"SELECT * FROM agent_memories {where_sql} ..."`
  - `rule_engine.py:358` `f"UPDATE active_rules SET {', '.join(updates)} WHERE rule_id = ?"`
- **与前序的区别**：20260918 P1-5 讲的是 `LIKE` 通配符未转义，P1-6 讲的是分页语义。本项是**结构拼接**：`SET {cols}` 若 cols 为空 → 生成 `SET  WHERE` 语法错误；`{where}` 若含 API 传入的排序/过滤键 → 非法列名直接报错或注入面。
- **修复**：列名/方向走**白名单映射**，值一律参数化；集合为空时短路返回。

### 【NEW-P2-1】运行环境双 Python 版本字节码 + `.bak` 残留

- **证据**（目录列举实测）：`src/**/__pycache__/` 同时存在 **cpython-311 与 cpython-313** 两套 `.pyc`；`src/memory_agent/candidate_promotion.py.bak` 与正式文件并存。
- **影响**：双版本字节码说明运行环境在 3.11/3.13 间漂移过，是隐蔽的稳定性风险源（依赖行为差异）；`.bak` 可能被误打包/误导入。
- **修复**：CI 与容器固定单一 Python 版本，清理 `.bak` 与 `__pycache__`。

### 【NEW-P2-2】遥测域过滤导致行为分析静默漏数

- **位置**：`store.py` `TELEMETRY_DOMAINS = (sensor, number, weather, sun, update, button, select)`，行为聚合默认 `behavior_only=True` 排除。
- **失败场景**：若某设备被 HA 误配 domain（如插座报为 `sensor`），其行为**永远不进行为分布**，热力图/预测静默偏空，且无任何提示。
- **修复**：增加「被排除实体」审计视图，运维可核对哪些实体因 domain 被排除。

### 【NEW-P2-3】语音缓存淘汰键在时钟异常下不确定

- **位置**：`store.py` `_VOICE_CACHE_MAX`（默认 2000），「超过则按创建时间淘汰最旧 10%」。
- **失败场景**：同秒创建或系统时钟回拨时，「最旧 10%」排序不稳定，可能误删热数据。
- **修复**：淘汰键改为 `(created_at, rowid)` 复合排序，保证确定性。

### 【NEW-P2-4】配置测试端点把底层错误原文回传客户端

- **位置**：`api/config_routes.py:395`
  ```python
  return error("HA MariaDB 连接失败：" + str(result.get("error", "未知错误")))
  ```
- **与前序的区别**：20260918 P0-7/P0-8 讲的是该文件的 SSRF 与密钥错发；本项是**错误信息外泄**：底层 DB 错误原样返回，暴露内部结构且可能塞入超长栈信息。
- **修复**：对外返回统一错误码，细节仅进日志。

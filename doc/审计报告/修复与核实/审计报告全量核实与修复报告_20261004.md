## 三、本轮修复的 5 个 Bug 详情

### Bug 1：P0-6 entity_catalog 全表扫描持锁阻塞

**来源**：第三轮数据库审计 P0-6
**文件**：`src/memory_agent/insights/repository.py`
**严重度**：P0（性能阻塞）

**问题描述**：
`entity_catalog()` 每次调用都对 82 万行事件表做全表 `GROUP BY` 聚合（实测 621ms），且在全局 RLock 内执行，导致其他写操作被阻塞。该函数被 insights API 高频调用，形成性能瓶颈。

**修复方案**：
- 新增 `_catalog_cache` 字典，TTL 60 秒
- cache key 包含 `(rooms, domains, limit)` 三元组，确保不同参数不串数据
- 命中缓存直接返回，未命中才执行查询并写入缓存
- 缓存仍在锁内更新，但查询频率从"每次"降为"每 60 秒每参数组合一次"

**代码变更**：
```python
# 新增类属性
_catalog_cache: dict = {}
_CATALOG_TTL = 60.0

# entity_catalog 内
cache_key = (tuple(rooms or []), tuple(domains or []), limit)
now = time.monotonic()
cached = cls._catalog_cache.get(cache_key)
if cached and (now - cached[0]) < cls._CATALOG_TTL:
    return cached[1]
# ... 执行查询 ...
cls._catalog_cache[cache_key] = (now, result)
```

**验证**：py_compile 通过；NAS 部署后服务健康。

### Bug 2：P1-3 nr_routes 净水器统计时区错位

**来源**：元宝第一轮审计 P1-3
**文件**：`src/memory_agent/api/nr_routes.py:125`
**严重度**：P1（数据错误）

**问题描述**：
净水器 7 天统计窗口使用 `datetime.now()`，容器运行在 UTC 时区，导致：
- 凌晨 0-8 点（北京时间）的"今天"实际是昨天
- 7 天窗口起止时间整体偏移 8 小时
- 用户看到的"今日用水量"与实际日期不符

**修复方案**：
改用 `now_local(rt.store.tz_offset_hours)` 获取本地时间，与项目中其他时间窗口处理保持一致。

**代码变更**：
```python
# 修复前
now = datetime.now()
# 修复后
now = now_local(rt.store.tz_offset_hours)
```

**红线遵守**：仅修改内部时间获取逻辑，端点路径与响应结构未变更。

**验证**：py_compile 通过；NAS 部署后服务健康。

### Bug 3：P2-5 KEYWORD_DOMAINS 重复定义覆盖

**来源**：元宝第四轮审计 P2-5
**文件**：`src/memory_agent/insights/utils.py`
**严重度**：P2（功能失效）

**问题描述**：
文件内存在两个 `KEYWORD_DOMAINS` 定义：
- 第 742 行：完整版，包含中英文关键词映射（含 switch/climate/media/sensor/tv/aircon 等 7 个英文关键词）

Python 后定义覆盖前定义，导致第 742 行的 7 个英文关键词全部失效。自然语言查询中使用英文设备类型（如 "switch"、"climate"）时无法正确路由到对应 domain。

**代码变更**：
```python
# 第 742 行（保留，补充注释）
# 中英文合并版：自然语言查询的关键词→domain 映射唯一真源
# 禁止在文件其他位置重复定义 KEYWORD_DOMAINS（后定义会覆盖前定义）
KEYWORD_DOMAINS = {
```

### Bug 4：P2-7 MCP 技能读取路径遍历

**来源**：元宝第八轮审计 P2-7
**文件**：`src/memory_agent/mcp_server.py`（get_skill + res_skill 两处）
**严重度**：P2（安全漏洞）

**问题描述**：
`get_skill(name)` 和 `res_skill(name)` 使用 `os.path.join(rt.config.skills_dir, name, "SKILL.md")` 读取技能文件，`name` 来自 MCP 调用方输入，无路径净化。攻击者可传入 `../../etc/passwd` 等路径，通过 `os.path.join` 逃出 `skills_dir` 读取任意文件。

**修复方案**：
两层防护：
1. **输入层**：拒绝包含 `..`、以 `/` 或 `\` 开头、包含 `:` 的 name
2. **realpath 二次校验**：计算 `os.path.realpath(skill_path)`，确认必须以 `os.path.realpath(skills_dir) + os.sep` 开头，防止符号链接等绕过

**代码变更**（get_skill 示例，res_skill 同口径）：
```python
if ".." in name or name.startswith(("/", "\\")) or ":" in name:
    return {"ok": False, "error": "name 含非法路径字符"}
skill_path = os.path.join(rt.config.skills_dir, name, "SKILL.md")
_real = os.path.realpath(skill_path)
_base = os.path.realpath(rt.config.skills_dir)
if not _real.startswith(_base + os.sep):
    return {"ok": False, "error": "skill 路径越界"}
```

**验证**：py_compile 通过；NAS 部署后服务健康。

### Bug 5：P2-10 _pinned_entities 查询失败静默撤销用户手动拆分

**来源**：元宝第十四轮审计 P2-10
**文件**：`src/memory_agent/identity.py:390`
**严重度**：P2（数据丢失 + 可观测性缺失）

**问题描述**：
`_pinned_entities()` 查询用户手动固定的实体拆分关系时，若数据库查询失败（锁超时、连接断开等），原代码返回空 `set()`。调用方 `_cluster()` 将空 set 解释为"用户没有固定拆分"，于是按自动聚类重新合并所有实体，**用户手动拆分的结果被静默撤销**，且无任何日志记录。

**修复方案**：
1. 查询失败时返回 `None`（而非空 set），区分"查询失败"与"用户确实没有固定"
2. 打印错误日志，记录异常信息，保证可观测性
3. `_cluster()` 遇到 `None` 时采取保守降级：所有实体独立成簇，不做自动合并，保护用户手动拆分不被覆盖

**代码变更**：
```python
# _pinned_entities
try:
    rows = db.execute(...).fetchall()
    return {row[0] for row in rows}
except Exception as e:
    print(f"[identity] _pinned_entities 查询失败，保守降级: {e}")
    return None  # None 表示查询失败，空 set 表示用户无固定

# _cluster
pinned = self._pinned_entities(db)
if pinned is None:
    # 查询失败：保守降级，所有实体独立成簇，不自动合并
    return [{eid} for eid in entity_ids]
```

**验证**：py_compile 通过；NAS 部署后服务健康。

## 一、核心发现（R2-D16）execute_intent_actions 未被权限门覆盖

这是 R2 最重要的发现，属安全边界缺口。

### 实测对照

同一 read-only 令牌下，14 个写工具被拦截：

| 工具 | 结果 |
|---|---|
| teach_signal | DENIED 无 write 权限 |
| add_semantic_memory | DENIED |
| create_member | DENIED |
| write_self_diary | DENIED |
| define_activity | DENIED |
| sweep_promote_candidates | DENIED |
| report_bug | DENIED |
| feedback_memory | DENIED |
| confirm_candidate_rule | DENIED |
| revoke_memory | DENIED |
| rollback_agent_memory | DENIED |
| trigger_collection | DENIED |

唯独 execute_intent_actions 放行：

    execute_intent_actions(intent=watch_tv, dry_run=true)
    → ok=true

    execute_intent_actions(intent=nonexistent_intent_r2_probe, dry_run=false)
    → ok=true, actions=[], summary={total:0, executed:0, skipped:0, need_confirm:0}

### 为什么这是缺陷

1. 该工具文档明确写 dry_run=false 时会执行 auto=true 的动作（TTS 播报、告警），即它本质是写工具。
2. read-only 令牌本应禁止一切写操作，但它未受拦截。
3. 我在 read-only 令牌下以 dry_run=false 调用，系统接受了该请求（虽然因 intent 不存在而无动作）。
4. 若传入合法 intent 且存在 auto=true 动作，read-only 令牌将可能触发实际播报，违背最小权限原则。

### 期望

execute_intent_actions 应与其他写工具一致纳入 write 权限门；或明确其分类为只读预览工具并禁止 dry_run=false。

## 二、次要发现（R2-D17）无副作用写入的返回语义模糊

不存在 intent 时返回 ok=true 且 actions=[]，用户无法区分：

- 意图识别成功但无匹配动作
- 意图根本不存在（拼写错误）

当前两条路径都返回同样的 total=0 空结果。建议对未知 intent 返回 NOT_FOUND 或提示可用 intent 列表。

---

## 三、应予肯定

权限门本身设计良好：

- 14 个写工具全部拦截，无一遗漏（除 execute_intent_actions）。
- 拦截信息高度可解释：明确给出令牌名、缺失权限、修复路径（WebUI MCP 接入切到读写）。
- 拦截以 mcp_tool_result_error + retryable=false 返回，调用方可明确判定为永久拒绝而非临时故障。

这表明权限框架是存在且有效的，execute_intent_actions 属配置遗漏而非设计缺陷。

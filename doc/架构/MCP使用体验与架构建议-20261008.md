# memory-agent MCP 使用体验与架构建议

- 评审对象：memory-agent MCP 服务器（约 90 个工具，14 个工具组）
- 评审视角：真实使用者 / Agent 调用方
- 评审日期：2026-10-08
- 证据来源：16 轮黑盒审计 + 工具目录取证 + insight skill 拉取
- 关联文档：doc/审计报告/memory-agent-MCP-十六轮黑盒审计汇总报告-20261008.md

---

## 一、总体判断

memory-agent 的**定位正确、方向先进**：把「时长、作息、异常」在服务端算好，调用方只拿结论，
这是相对「给一堆原始事件让 Agent 自己算」的降维打击。insight skill v4 明确写了
「它是行为洞察层而非事件数据层」，理念清晰。

但当前**工具面严重过度暴露**：90 个工具平铺下发，把本该服务端内部完成的确定性工作、
运维工作、离线挖矿工作一并交还给 Agent，导致「服务端做厚」的理念在实际接口上被稀释。

一句话：**理念是服务端做厚，接口却是 90 个工具让 Agent 选边站。**

---

## 二、90 个工具会影响使用吗？会，且是当前最大问题

### 2.1 固定开销

MCP 工具定义会注入系统提示词。按每工具 schema+description 约 250-400 token 估算：

| 工具数 | 每轮固定开销（估算） |
|---|---|
| 90 | 约 27000 token |
| 50 | 约 15000 token |
| 30 | 约 9000 token |
| 20 | 约 6000 token |

无论用户问什么，这 2.7 万 token 都要付一遍。

### 2.2 选择困难

实测证据：本轮审计中，Agent 多次选错工具——例如选了已损坏的 query_device_usage
而非可用的 get_device_usage。业界经验：工具数超过 50 后选择准确率明显下滑，
20-30 是舒适区。90 个已远超。

### 2.3 结论

工具数应从 90 砍到 **20-25**，靠「粗粒度 + 意图化」合并。

## 三、有重复的 tools 吗？大量重复，至少 8 组

| 组 | 重复工具 | 问题 |
|---|---|---|
| 设备用量 | get_device_usage / query_device_usage / get_device_usage_summary | 3 个做同一件事，口径互相矛盾（开关次数 2 vs 3） |
| 行为总览 | get_behavior_summary / get_behavior_insights / get_room_behavior_summary / get_behavior_insights_compare | 4 个都在看行为，total_events 口径不一致 |
| 事件查询 | query_events / search_events / query_unified_events / query_behavior_events | 4 个查事件，边界模糊 |
| 设备健康 | get_device_health / list_device_health / get_data_quality | 3 个都报健康，stale 口径 0 vs 6 |
| 目录 | get_entity_catalog / list_rooms_entities | 后者崩溃，功能被前者覆盖 |
| 规则查看 | list_candidate_rules / list_rule_channel / list_rule_lifecycle_audit | 3 个都在列规则 |
| 记忆读取 | list_agent_memories / retrieve_agent_memories | 边界可合 |
| 漂移异常 | get_behavior_drift / list_behavior_drifts / refresh_behavior_drift / list_behavior_anomalies / refresh_behavior_anomalies | 5 个围绕同一主题 |

结论：**超过 1/3 的工具是冗余的**。

---

## 四、token 消耗会起飞吗？已经起飞

三重放大：

1. **工具定义**：90 个 x 约 300 token = 约 2.7 万/轮（恒定成本）
2. **返回值膨胀**：get_behavior_insights 返回逐房间 x 24 小时直方图，单次可上万 token
3. **纠错重试**：口径不一致导致 Agent 常需多次对拍（同一问题反复调 3-5 个工具）

典型一轮问答 token 构成（估算）：工具定义 27000 + 工具返回 12000 + 纠错重试 8000 + 用户内容 500。

## 五、设计不合理之处

### 5.1 职责倒置（最严重）

大量「确定性批处理 / 运维」工作被塞给 Agent，其实服务端自己定时跑就行：

| 工具 | 为什么不该给 Agent |
|---|---|
| refresh_behavior_anomalies | 定时重算落库，应 cron 自动跑 |
| refresh_behavior_drift | 同上（且依赖 river 还崩） |
| refresh_rule_recall_gaps | 离线挖矿任务，非交互式 |
| trigger_collection / trigger_incremental_collection | 采集是服务端守护进程职责 |
| sweep_promote_candidates | 自动晋升扫描，应内部调度 |
| generate_self_diary | 定时生成，不该要 Agent 触发 |
| agent_memory_health / get_collect_status | 监控指标，应在 dashboard/告警 |
| report_bug / list_bug_reports | 元运维，不该占工具位 |
| save_skill / list_skills / get_skill | 技能注册表是网关内部事 |
| get_session_trust | 内部信任分，Agent 无需干预 |
| delete_analysis_template / delete_member | 危险写操作，应走 WebUI 二次确认 |

约 **15-20 个工具属于 server-side job**，让 Agent 调用既增 token 又增误操作风险。

### 5.2 写接口红线不统一

- add_semantic_memory / teach_signal 的 dry_run 语义失效（审计已证实 dry_run 仍写库）
- 但同时把 promote / advance / revoke 等真正危险的规则操作也暴露给 Agent

### 5.3 定位重叠

- route_question 与 ask_memory 都是「自然语言 -> 计划」，且 route_question 还要求
  Agent「拿到计划后再调工具」，等于绕了一圈。

### 5.4 命名无规律

get_ / list_ / query_ / search_ 四种前缀混用，同一语义三种前缀，Agent 更难选。

### 5.5 文档与实现漂移

- get_data_coverage 声称「最近 N 天」实际返回 N+1 天
- list_device_health 文档未提 state=all，却是唯一能出数据的值
- insight skill 教导先调 get_data_coverage 确认窗口，但该工具本身有 off-by-one

### 5.6 依赖缺失静默上架

get_behavior_drift 依赖 river 未安装，仍上架，调用时才崩。

### 5.7 无分层

把「读数据 / 算洞察 / 写规则 / 运维 / 元审计」混在同一平面，无命名空间或权限分层。

## 六、根本不需要 Agent 完成的任务（服务端自己能做）

除 5.1 列出的工具外，还有一类「Agent 在替服务端做本该服务端做的事」：

1. **多工具对拍才能得出一致口径**：Agent 被迫交叉验证 summary/insights/compare，
   而这些口径本该服务端统一后直出。
2. **窗口完整性自检**：Agent 要先 get_data_coverage 再取数，本该由每个数据工具
   自己返回 no_data/window_complete 标记。
3. **实体 ID 解析**：Agent 要先 catalog 再取数，本该由工具内部完成（query_device_usage
   的设计初衷是对的，可惜实现失效）。
4. **规则晋升的门槛判断**：evidence 是否够、观察期是否满，应服务端自动判定并只推结果。

## 七、改进建议（按优先级）

### P0 架构层

1. **工具从 90 收到 20-25**：按意图合并，如设备用量只留一个 get_device_usage
   （吸收 summary/query 两个）。
2. **把 15-20 个 server-side job 移出 MCP**，改为内部定时任务 + WebUI 页面。
3. **保留 ask_memory 作为唯一入口**，其余工具作为其内部实现，不下发到 Agent；
   route_question 可保留为调试面。

### P1 契约层

4. **统一指标口径**（total_events / 峰值小时 / 开关次数 / stale），建单一真源函数。
5. **写接口 dry_run 必须真不落库**；危险操作（delete/promote/revoke）移出 MCP。
6. **窗口语义统一**：要么全部 days=N 覆盖 N 天，要么全部 N+1 并写清文档。

### P2 体验层

7. **统一命名前缀**：读 get_ / 写 set_ / 任务 run_。
8. **大返回值默认分页或摘要**，提供 summarize 开关（search_events 已有，应推广）。
9. **每个数据工具自带 no_data / window_complete 标记**，免除 Agent 前置自检。

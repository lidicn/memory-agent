# 交接卡：行为洞察模板「校验 + 自动修复」机制（v0.7 增量）

- **日期**：2026-09-10
- **范围**：修复模板统计 bug、新增模板校验与分档处置、自动/半自动修复、内置模板停用、WebUI 呈现
- **目标**：让模板从「静默失效仍被当正常使用」变为「失效可检出、原因可解释、能修的自动修、不能修的明确拦下」

---

## 一、修掉的 3 个 bug（都在净水器模板上）

| # | 位置 | 问题 | 后果 |
|---|---|---|---|
| 1 | `insights.py` `water_purifier_usage()` | `if record.get("state") != "on": continue` —— 该 event 实体的 state 是**时间戳**，HA 里根本没有 `"on"` | 所有记录被跳过，统计**恒为 0** |
| 2 | 同上 | `attrs.get("out_data")` —— 实际属性名是中文**「出水数据」** | 取不到值，同样恒为 0 |
| 3 | `templates.py:390` | `d["total_volume_ml"]` —— 但 `water_purifier_usage` 返回的 days 项键是 `total_volume_l` | 一旦有数据就抛 `KeyError`（此前因 days 恒为空而未暴露） |

> 第 3 个是典型的「被静默归零掩盖的隐藏 bug」：前两个 bug 让 `days` 永远是空列表，列表推导不执行，所以 KeyError 一直没被触发。**修好前两个才把第三个炸出来。**

修好后的实测值（7 天窗口）：**3.36 升 / 20 次**。

## 二、统一了错误模型（不再用 0 糊弄）

- `water_purifier_usage`：新增 `skipped_reason` / `no_records`，区分「真没出水」与「有记录但解析不了」。
- `run_template` 的每个实体结果新增 `has_records` / `last_data_ts` / `no_data`，调用方能识别「实体有效但近期无数据」。

## 三、新增模板校验机制

### 状态机（多实体模板取最严重）

| 状态 | 含义 | 处置 |
|---|---|---|
| `ok` | 实体有效且窗口内有数据 | 正常执行 |
| `no_data` | 实体有效、窗口内无数据 | **仅警告**（可能真的没活动） |
| `stale` | 身份层判定已失效（约 30 天未见） | **硬阻止** |
| `missing` | 数据仓库与身份层均查无此实体 | **硬阻止** |
| `disabled` | 用户已停用 | 不参与列表与调用 |

优先级：`disabled` > `missing` > `stale` > `no_data` > `ok`

### 校验时机
- **启动后后台异步校验一次**（延时 90s，避开首轮采集）+ **每 6 小时复验**；
- WebUI「行为洞察」页顶部提供**「重新校验」**按钮（`POST /api/templates/validate`）；
- 列表只读缓存（`data/template_state.json`），**不阻塞**请求。

### 执行闸门（三处统一）
`run_template` 的调用方全部接入 `check_executable()`：
- `POST /api/insights/query`（template 分支）→ 失效返回 **409** + 原因
- MCP 工具 `run_analysis_template` → 失效返回 `ok=false` + `status` + `suggestions`
- `no_data` 仅在结果里带 `warning`，照常返回

## 四、可修复情况清单（回应「还有类似可修复的情况吗」）

### 已能自动修（v0.2 身份层既有能力，本次复用）
1. **HA 重登/改名**导致 entity_id 漂移，但存在同名同类新实体 → `A1 重匹配` 自愈。
2. **双集成冗余**（如小米电视同时接入 xiaomi miot 与 xiaomi home）→ `A2 自动合并`为同一逻辑设备并按「在线→引用频次→优先级」选主；**模板改用逻辑引用后任一集成下线都不影响**。
3. 模板写死某候选实体、该实体失效，但所属逻辑设备仍有活跃候选 → 换用其它候选。

### 需人工/AI 确认（给候选+置信度，不自动写）
4. 实体已不存在，但存在名称相似的真实实体（是否同一设备需确认）。
5. **属性名/写法不匹配**（如 `out_data` 与「出水数据」）—— 属配置错误，非实体问题。
6. 语义漂移：模板意图与实际数据维度不再对应。

### 不可修复（必须重新定义）
7. **占位/示例实体**（如 `binary_sensor.bedroom_motion`），无任何同名真实实体可换。
8. 设备已物理移除且无替代。

### 本次实现的修复能力
- 校验为 `missing`/`stale` 时**主动找候选**：① 所属逻辑设备的其它候选（置信 0.9）；② 名称相似度模糊匹配（≥0.5）。
- 有候选 → 标记 `fixable`，WebUI 给出「修复建议」可**一键应用**；
- 无候选 → `needs_manual=true`，提示需人工指定（占位示例名就是这类）。

## 五、内置模板停用

- 内置模板**不可删除**，但可通过 WebUI 一键**停用/恢复**（`POST /api/templates/disable`）。
- 停用状态存在 `data/template_state.json` 的 `disabled` 列表，**不改代码常量**（`BUILTIN_INSIGHTS`）。
- 停用后：列表淡化显示、执行被拒（409）。

## 六、接口与前端

| 类型 | 变化 |
|---|---|
| `GET /api/templates` | 裸数组契约**不变**，仅新增 `validation_status` / `disabled` |
| `GET /api/insights` | 列表项新增 `validation`（缓存）/ `validation_status` / `disabled`；顶层新增 `validation_summary` |
| `POST /api/templates/validate` | 全量或单个校验（body `{template_id?}`） |
| `POST /api/templates/disable` | 停用/恢复（`{template_id, disabled}`） |
| `POST /api/templates/fix` | 应用修复（`{template_id, entity_index, new_ref?, auto?}`） |
| `static/js/pages/insights.js` | 卡片校验徽章、顶部「重新校验」+ 最近校验时间、详情逐实体明细与原因、修复建议区、停用/恢复按钮 |
| `static/js/api.js` | 新增 `validateTemplates` / `disableTemplate` / `fixTemplate` |

## 八、遗留与下一步

1. **`sleep_time_pattern` 仍不可用**：它引用的是**示例占位实体**，没有候选可换，需要人工指定真实的卧室人体传感器/灯实体（WebUI 会提示 `needs_manual`）。
2. **`study_room_work_duration` 为 `no_data`**：其 `switch.*` 实体存在但窗口内无新数据；另注意此前发现的「未闭合 on 导致超长时长」属设备上报问题，未在本次改动范围内。
3. 修复审计存在 `template_state.json` 的 `fixes`（保留最近 200 条），可追溯。

## 九、回滚

- 源码改动均为源码级（bind mount），`scp` 回退旧文件后 `docker restart memory-agent` 即可。
- 停用状态可通过 WebUI 一键恢复；`data/template_state.json` 删除即回到「未校验」状态（不影响模板定义）。
- 修复保留原值至 `fixes` 审计，可据此手工改回。

## 十、部署备注

- 本次为纯源码改动，`scp` + `docker restart memory-agent` 即可，**无需 build**。
- 仍须遵守既有纪律：**禁止 `deploy_nas.sh`**；改 `.env` 用 `docker compose up -d`；MA 启动约 2 分钟，验证等待窗口 >180s。

## 二、本轮唯一的 P0 修复：BUG-TZ1 时区口径

**事实**：生产 `events.ts` / `server_ts` 是**naive 家庭墙钟（UTC+8）字符串**，由 `store.now_local(tz_offset_hours)` 写入；而容器时钟是 **UTC**（实测 `date` = `Thu Oct 1 00:40:15 UTC 2026`，同库 `max(ts)` = `2026-10-01T08:34:08`）。任何用**机器本地时区**做的 epoch↔墙钟换算都会整体错位 8 小时。

**症状**：`openshs` 的 `sleeping` F1 只在容器里=0、本地正常；场景图 `minutes` 过滤在容器里返回 0 行。两个"测试环境问题"其实是同一个生产功能缺陷。

**修法（单点真源）**：`insights/models.py` 新增 `HOUSE_TZ` / `house_ts` / `house_dt` / `house_now`，与 `repository._to_iso/_to_iso` 早已假定的 +8 互逆；`parser/timeframe.py`、`service.py`、`activity.py`、`api.py`、`utils.py` 全部改用它。回归 `tests/test_insights_house_timezone.py` 用 2016 年固定时刻构造，**在非 +8 机器上才会咬**，所以它同时是环境无关性证明。

**未闭环**：家庭时区是否上提到 homesdk 作机制层唯一入口 —— 见 DCD 补充申请（§四）。MA 目前自带 `HOUSE_TZ`，跨仓各写各的风险仍在。

## 三、本轮新发现的两个真实缺陷（都已修）

1. **候选规则两套状态字**（`fd24390`）。WebUI 走 `set_candidate_rule_status`（白名单 `staging|accepted|rejected`）只改 `status`、从不碰 `user_confirmed`；MCP 走 `update_candidate_rule_status` 写 `"confirmed"`，而 `user_confirmed=1` 只认这个字面量。后果：MCP 确认的规则不进 WebUI 的 accepted 列表（`api/behavior_routes.py:112` 按 `status='accepted'` 查），WebUI 接受的规则红线位恒 0 —— DCD 裁定 7 的红线位与真实审批状态脱钩。归一为 `store.py:32` 的 `CANDIDATE_ACCEPTED`，两方法共用一条 UPDATE，并补 `test_candidate_rule_status_vocabulary_is_single_sourced`。顺带去掉该处 `time.strftime`（机器本地时间，与 BUG-TZ1 同因）。生产库 23 条候选规则全为 `staging/0`，无历史 `accepted/confirmed` 行，故不做回填、不留兼容分支。
2. **pyflakes 基线按行号比对**（`6dfb6af`）。任何一次上方插入都会把同一条目同时算成"新增"和"已修"，`NEW_COUNT>0` 直接误判红——本轮实测总条数仍是 71 却报 4 新增 4 已修。新键为「文件: 消息」，并把 pyflakes 消息自带的 `from line N` 一并归一。抗漂移已实证：`store.py` 编辑前的扫描与编辑后的新基线互比 = 0 新增 0 已修。

另修自己引入的一处：`TestViewSqlMirror` 用 `__file__/../src` 定位镜像，容器里指向不存在的 `/tmp/src`，本地 12 passed 而容器 2 failed（`51b26d0`）——**本地绿不等于权威环境绿**，这是本轮第二次撞到同一条规律。

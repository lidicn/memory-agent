# P1 算法内核 spike 结论（hmmlearn / pm4py / river）

> 日期：2026-09-17 ｜ 对应路线图：《路线图_主动感知_v2.0》并行轨道 P1
> 代码：`src/memory_agent/algo_kernel.py`、`benchmarks/algo_kernel_spike.py`
> 报告 JSON：`benchmarks/data/algo_kernel_spike.json`

## 一、spike 要回答的问题

路线图 P1 的原始假设是：「行为推断层（`activity_inference.py`）全是手写规则 + 朴素
n-gram，无概率/无学习/无不确定性度量；应直接引入 `pm4py` / `river` / `hmmlearn`
做**替换式**升级。」

本 spike 用**带真值的公开数据集**做三方对照，检验该假设是否成立：

```
手写规则(activity_inference)  vs  HMM(hmmlearn)  vs  数据真值
```

## 二、实验设计

| 项 | 设置 |
|---|---|
| 数据 | OpenSHS 公开数据集 2 周（105 万行 @1Hz，2021-03-01 → 03-14），粗粒度 7 分类标注 |
| 事件流 | 边沿触发 → 1717 条事件（复用 `benchmarks/openshs_convert.py`） |
| 观测 | 9 类标签（door/light/climate/computer/presence/media/cover/appliance/other）→ 分钟级位掩码，空洞补零 → 18849 桶 |
| 真值 | 234 个活动片段 |
| 手写规则 | 75 个活动片段（`InferenceActivities`，与线上同一套逻辑） |
| 切分 | 前 70% 训练 + 隐状态语义投票，后 30% 评估（n=5655 桶） |
| 指标 | 桶级一致率、**非 idle macro-F1**（桶级一致率会被 idle 主导，必须看这个）、逐活动 F1 |
| 参照基线 | 多数类（全猜 idle） |

> **为什么要专门看"非 idle macro-F1"**：14 天里绝大多数分钟都是空闲，全猜 idle 就能
> 拿到 0.776 的桶级一致率。MA 对用户真正的价值是「今天做饭了吗/工作了吗/几点睡的」，
> 所以必须看非空闲活动的 F1。

### 关键工程修正：观测词表必须稠密化

初版直接把 9 位位掩码（2⁹=512 个符号）喂给 `CategoricalHMM`，4 个隐状态 → 2059 个
自由参数，而训练样本仅 987 → hmmlearn 直接警告
`Fitting a model with 2059 free scalar parameters with only 987 data points will result in a degenerate solution.`

修正：按**训练集频次**取 top-N 观测做稠密下标、其余归 `other` 兜底符号
（`HmmActivityModel.max_symbols`，默认 32），参数量降到 `K×32` 量级，与家居数据规模匹配。
这是"直接用库"必须做的适配，否则结论无效。

## 三、结果

### 3.1 全局对照（测试区间 n=5655）

| 方法 | 桶级一致率 | 非 idle macro-F1 | sleeping F1 | cooking F1 |
|---|---|---|---|---|
| 多数类基线（全猜 idle） | **0.776** | 0.000 | 0 | 0 |
| **手写规则** | 0.482 | **0.160** | **0.735** | 0.064 |
| **HMM（规则映射）** | 0.767 | 0.010 | 0.000 | 0.051 |
| HMM 上界（真值映射语义） | — | **0.000** | 0.000 | — |

观察：

1. HMM 桶级 0.767 看似逼近基线 0.776、远超规则 0.482 —— **这是假象**：HMM 把几乎
   所有桶都判成 idle，靠"平凡正确"刷高一致率。
2. 一旦看非 idle macro-F1，**规则 0.160 完胜 HMM 0.010**。
3. **上界实验（用真值给隐状态投票语义）也是 0.000** —— 说明问题不在"状态→活动语义
   映射"，而在**隐结构本身没有学到活动区分**。
4. 规则在 `sleeping` 上 F1=0.735（P=0.988 / R=0.585），HMM 为 0。

### 3.2 按房间的二元活动检测（排除"全屋聚合"干扰）

担心"全屋标签混在一起"是 HMM 失败的唯一原因，故再做一次按房间切开、只用该房间事件
建观测序列、只判断"本房间是否在做它的主活动"的实验：

| 房间 / 主活动 | 正样本占比 | 手写规则 F1 (P/R) | HMM F1 (P/R) |
|---|---|---|---|
| 卧室 / sleeping | 1194/18849 | **0.735** (0.988 / 0.585) | 0.000 (0 / 0) |
| 厨房 / cooking | 347/17412 | 0.080 (0.044 / 0.384) | 0.027 (0.222 / 0.014) |
| 客厅 / watching_tv | 2559/17775 | 0.097 (0.077 / 0.130) | 0.054 (0.417 / 0.029) |
| 卫生间 / bathing | 402/17808 | 0.000 | 0.000 |

**按房间切开后 HMM 仍然全线不敌规则**。这否定了"只是聚合粒度问题"的辩解。

### 3.3 过程挖掘 ✅

把（房间·天）当 case、`tag_on` 当活动，用 DFG + 稀有边判据（可选叠加 pm4py 一致性），
**零额外标注**即产出可解释的行为异常 case——这正是"一致性检验 = 异常"。

**关键工程教训：必须先做时间桶聚合**。初版逐事件建轨迹，OpenSHS 得到 55 case / 异常 17，
但变体长这样：`light_on → door_on → presence_on → light_on → door_on`（长度 5、语义混乱）。
换成 10 分钟桶 + "只在标签相对上一桶新出现时记一步"后：

```
case=53（房间·天）  一致性=0.736  异常=14   库所/变迁=18/22
变体 x11: door_on → light_on → presence_on
变体 x6 : door_on → light_on → presence_on → light_on
变体 x5 : light_on → presence_on → media_on
异常 厨房|2021-03-02: ['rare_edges']  door_on → presence_on → light_on → appliance_on → ...
```

变体从"看不出是什么"变成**真实可读的行为模式**（进房间 / 看电视），异常也从 17 降到 14
（去掉的是纯噪声）。这一条在真实 MA 库上被放大到极致：家庭事件是**秒级交替**的
（电视/在场来回刷），逐事件建轨迹会产出上百步、变体支持度恒为 1、稀边遍地，
异常完全被噪声主导 —— 桶聚合不是可选项而是前提。

### 3.4 在线异常 + 概念漂移（river）✅

```
n=18849 桶  异常=477  分均值=0.0212  峰值=0.9913  漂移=True(11 个点)
漂移@2021-03-01T13:46:00 / 2021-03-02T08:58:00 / ...
```

Half-Space Trees 在线增量学习 + ADWIN 监测行为活跃度分布突变，**零标注**给出
477 个异常桶与 11 个漂移点，天然适配"行为随时间演变"。

### 3.5 真实 MA 家庭库试跑（补充，仅供参考）

在 NAS 容器内对家庭真实库（`/data/memory_agent.db`，近 14 天）跑同一套 harness：

```
事件 5000 条（= query_events 的 LIMIT 硬上限，见 store.py:2530）
观测序列 186 桶        手写规则活动片段 3 段
HMM vs 规则一致率 = 0.929（= 多数类基线 0.929，四个隐状态全被投票成 working）
过程挖掘：跳过（容器内未装 pm4py）
在线异常：n=186 异常=0 分峰值=0.0   ← Half-Space Trees 的 window_size=250 > 186 样本，
                                       全程处于冷启动，故无分数
```

**为何不足以作为判据**（如实记录，避免被误读成"真实数据也支持/否定 HMM"）：

1. `query_events` 单次上限 5000 条，14 天真实事件被截断，样本远小于 OpenSHS 的 18849 桶；
2. 仅 186 桶说明绝大多数 MA 事件没有落到 9 类行为标签上（遥测/传感器居多），
   观测覆盖率天然偏低——这是 MA 当前标签体系的现状，不是算法问题；
3. 规则只产出 3 段，HMM 只能把 4 个隐状态全投票成同一类，对照没有区分度；
4. river 的 HST 需要 ≥ `window_size`（250）样本才产出分数。

**结论**：真实库可跑通链路，但**权威判定以 3.1–3.3 的 OpenSHS 标注数据为准**。
若要用真实库做同类对照，需先把 MA 的行为标签覆盖率提上去（与 P1.4「规则召回提升」同源）。

### 3.6 P1.1 落地：真实库调参（2026-09-17）

spike 的结论落到 MA 生产后，真实家庭库（11 个房间 / 14 天 / 136 条房间-日轨迹）
又逐层暴露 5 个问题，全部以真实数据为判据修复：

| # | 现象（真实库实测） | 根因 | 修复 |
|---|---|---|---|
| 1 | 单日轨迹上百步、变体支持度恒为 1、稀边遍地 | 家庭事件是**秒级交替**（电视/在场来回刷），逐事件建轨迹 | 10min 时间桶 + 只在标签**相对上一桶新出现**时记一步 |
| 2 | 出现「未分区」等伪房间 case | HA 未分区实体 | `skip_rooms` 过滤 |
| 3 | 30 天窗口只看到 **3** 个 case（比 14 天还少） | 遥测域（功率/温湿度）占绝大多数行，吃满 60000 分页上限，窗口只覆盖最早几天 | 取数排除 `TELEMETRY_DOMAINS` → cases_all **19 → 136** |
| 4 | 37% 房间-日被判异常 | 房间只有 1-2 天历史，**不存在"常态"可偏离**，按比例判稀边必然全判异常 | `min_cases_per_room` 门槛，不足则显式跳过并回报 `skipped_rooms` |
| 5 | **50% 房间-日误报** | DFG 在**全局**算：厨房的日常被当成"相对客厅的稀有事" | 一致性检验改为**房间内**比对（每房间自建 DFG） |

**修复效果（真实库 14 天）**：

| 指标 | 修复前 | 修复后 |
|---|---|---|
| 轨迹数 | 19 | **136** |
| 一致性率 fitness | 0.50 | **0.853** |
| 异常数 | 68 | **20** |
| 候选规则 | 0 | **3** |

候选规则已具备可读语义，例如 `过程变体[厨房]: light→presence→appliance`（支持 3）、
`过程变体[卧室]: cover→climate→media`（支持 3）。异常也落在合理的位置——例如
`主卧室 2026-09-11: climate_on→door_on` 稀边，而该日正是此前 P6 实测中空调连续运行
33 小时的那一天。

> **方法论提醒**：这 5 个问题没有一个是"算法选错"，全是**口径/粒度/聚合维度**问题。
> 统计方法落地时，"在哪一层聚合、按什么维度分组"比"用哪个模型"更决定成败。

## 四、结论

| P1 子项 | 判定 | 说明 |
|---|---|---|
| **hmmlearn 替换手写规则** | ❌ **不成立**（朴素路线） | 观测重叠 + 无监督 + idle 主导 → 隐状态塌缩到 idle；上界为 0 证明隐结构无区分力 |
| **pm4py 过程挖掘 + 一致性检验** | ✅ **有价值** | 零标注产出 17 个可解释异常 case + 过程模型变体 |
| **river 在线异常 + 漂移** | ✅ **有价值** | 零标注 477 异常桶 + 11 漂移点 |
| 手写规则现状 | ⚠️ **高精确 / 低召回** | sleeping P=0.988 / R=0.585；规则仅覆盖 75 段而真值 234 段 |

### 最重要的反直觉发现

> 手写规则**不是"不够统计"，而是"召回不足"**。规则在它触发的时刻几乎总是对的
> （sleeping 精确率 0.988），只是大量时段它不敢下结论（召回 0.585）。
> 因此正确的下一步不是"用 HMM 替换规则"，而是"**用统计方法补规则的低召回**"
> ——过程挖掘/在线异常发现候选模式，规则做高置信裁决。

## 五、对路线图的修订建议

1. **P1.1 落地 pm4py 过程挖掘**（✅ 推荐）：`mine_sequences` 升级为"过程模型 + 一致性异常"，
   产出候选规则（已有 `candidate_rules` 审核流）与行为异常清单。
2. **P1.2 落地 river 在线异常 + 漂移**（✅ 推荐）：行为异常评分 + "作息有变化"提示，
   可挂到现有 `insights` 出口。
3. **P1.3 hmmlearn 暂缓**（⏸ 降级为探索）：直接替换不成立。若仍要探索，必须先做
   特征工程（房间级观测 + 时间-of-day + 状态持续时长 + 用规则标签做弱监督），
   且改任务定义为"规则未覆盖时段的活动插补"，而非"逐桶分类"。
4. **新增 P1.4 规则召回提升**（由本 spike 推出）：以过程挖掘/异常检测发现的高频模式
   反向提示规则缺口（如"卧室 presence 持续 30min 但规则未判 sleeping"）。

## 六、复现方式

```bash
# 真实标注数据集（粗粒度）
PYTHONPATH=src python -m benchmarks.algo_kernel_spike \
    --csv benchmarks/data/openshs_real.csv --map coarse --bucket-sec 60 --states 4

# 自带小样本
PYTHONPATH=src python -m benchmarks.algo_kernel_spike

# 真实 MA 库（无真值，只跑 HMM-vs-规则 + 过程挖掘 + 在线异常）
PYTHONPATH=src python -m benchmarks.algo_kernel_spike --db /data/memory.db --days 14
```

依赖：`pip install -e ".[algo]"`（未安装时 `algo_kernel` 各能力自动跳过，不影响主服务）。
